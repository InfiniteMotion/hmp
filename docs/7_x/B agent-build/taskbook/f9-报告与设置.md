## 2.1 F9-T0 · 用户认识模块（前置）

**为什么插在最前面**：`agent-architecture.md` 有两处承诺零实现 —— Master system prompt 规格写着「persona + **偏好画像** + 曲库概况 + 认识进度」，组件图画着 `AgentMemory（持久化，跨会话）`（全仓搜 `AgentMemory`/`agent_memory`/`UserProfile`/`SeedProfile` 无命中）；另有 `f5` 登记的「Feedback → Recall → 推荐闭环」在 F6 被电台的会话内方案事实上取代，既没实现也没标废弃。**F9-T0 把它正式认领。**

**定位**：agent 的**长期用户模型** —— 从曲库、播放记录、状态快照与对话中归纳「这个用户是谁」，以**侧写**形式表达，持久化在本地，为所有 agent 提供决策依据。隶属 `MasterAgent`，是其常驻模块；**不是** SubAgent（不派活、不参与 Scheduler 竞态）。

**为什么它是 F9-T1/T2 的前置**：① 给 T1 供数据 —— 报告叙事段本质是「对用户的一段事实摘要」，是画像读取面的第一个消费方，**且两者共用同一条取数管线**；② 给 T2 供内容 —— 「记忆与信任 / 记忆管理」两区要列出伙伴对用户的每一条认识。

**契约**：`../design/agent-profile.md`（**单一事实来源，v3.8 定稿** —— T0/T0a/T0b 全量落地后的收口版，演进史见契约版本记录）。要点摘要：

- **两层结构** —— 侧写层（产品面向：预设骨架 + 槽位闭集 + 证据反链）+ 证据层（审计面向）。侧写负责"整体印象"，证据负责"你凭什么这么说"
- **两个平级建模器** —— `LibraryModeler`（曲库，按**认知深度**成熟：形态 → 内容两阶段）+ `BehaviorModeler`（行为与状态，按**数据积累**成熟）。两者只产证据，侧写统一由 `PortraitComposer` 派生（**只有一条派生路径**）
- **曲库两阶段** —— 扫描完成 → **形态建模**（规模/歌手集中度/专辑完整度/**路径分类结构**/时长倾向，0.4）；覆盖率达标 → **内容建模**（流派/情绪/年代/语言分布，0.55）。**阶段二是纠正而非补全**（形态分不出"口味集中"与"人集中但风格分散"）
- **行为建模不细到单个操作** —— 定时读 `PlaybackHistory` 即可（时段 / **跳过点位置** / 完播 / 重复度），**零新埋点**；状态快照（收藏 / 评分 / 手工歌单 / 标签修正 / ID3 编辑 / 隐藏文件夹 = `Music.isDeleted`）走同一定时任务的 diff。⚠️ **复核核正**：`PlaybackHistory.source` 实为**播放切换原因**（`Manual`/`Next`/`Resume`…，且两端不一致），**不是**"推荐 / 自己点 / 电台"，故「来源构成」槽位取消
- **分级记忆 L1/L2/L3** —— 当下态（内存）/ 情境态即短时人格（天~周带衰减）/ 性情态即人性（月~年）。**值钱的是跨层流动规则**（晋升靠跨会话重复度与持续时间），不是分级本身；**反例保护**：单次极端行为只进 L2
- **对话侧写门槛已放开** —— 允许从对话**推断**音乐偏好，但配三条约束：落闭集槽位 / `T2_DIALOGUE` 0.35 落 L2 **不自动升 L3** / **被行为确证才升**。即「**对话给假设，行为给确证**」。**底线**：推断「音乐选择」可以，推断「人 / 处境」不行
- **认知准入标准** —— 唯一标准是「能不能改变 agent 的某个具体动作」。A 类 5 个（曲库/时间/口味/听法/探索）+ B 类 3 个（秩序/情绪强度/注意力，**只能以「你在音乐里表现出的…」表述**）+ C 明确不做
- **明确拒绝类型学** —— 不可确证（听 300 小时古典推不出 INTJ）+ 巴纳姆效应 + 信任一次性透支；其功能位由**侧写组合**取代
- **消费面** —— 认知面（给 agent，读槽位原值）与消费面（给用户，侧写组合 → 人格命名 + 人话 + 凭什么）**共用同一份数据**。做**自有音乐人格卡**而非借 MBTI（查证：注册商标 + 官方禁止用其数据做商业开发 + 受限量表需人工咨询）。**边界：消费面不得回流决策面**
- **C2 定稿（放开）** —— 画像**可以**进会话上下文（开播种子与逐步判断都能看到），但**只作为「仅供参考」的背景、不作为指令**（契约 §7.1 规定注入首行自述性质）。理由：画像进的是 `ContextAssembler` → `buildChatSystemPrompt()`，**整场任务每轮共用同一份 system prompt**，"会话内不读"在实现上做不到 —— 一条做不到的纪律比没有更糟
- **隐私已收敛** —— 不承担隐私设计，唯一动作是**端点配置页一句提醒**；三条纪律保留但理由都不是隐私（呈现层级 / 工程卫生 / 上下文纪律）
- **Room v5 → v6**（两张新表 + 证据表唯一索引，**无列变更**；契约 §2.3 附完整 DDL），迁移测试先行。证据行带**自增主键**（侧写反链 `evidenceRefs: List<Long>` 才有 Long 可指），并拆出 `distinct_sessions` 承载 L1→L2 的**跨会话**计数（原单靠 `evidence_count` 语义过载）

**实施分档**：`T0a`（地基 + MVP，判据 = 新用户导入曲库后第一次对话就有内容）→ `T0b`（人格卡优先，然后 B 类侧写、`profile_read`、设置页两区、对话自动抽取）。**F9-T1/T2 的依赖只挂 T0a。**

**待拍板**：`agent-profile.md` §13 的 PF1-PF12。

## 2.2 F9-A0 · Capability 统一化（插叙，2026-09-16 · ✅ 完成）

### 为什么必须做

F6/F7/F8 完成后 SubAgent 体系稳定了，但暴露了两个架构债：

1. **DJ 工具绕路** —— RadioSubAgent 有 8 个 `dj_*` 工具直接暴露给 LLM（队列替换 / 下一首 / 跳过 / 播指定曲 等），这些工具在 `ToolRegistryView.radio()` 白名单里单独注册，Master 视图看不到。问题是：**LLM 操作电台内部队列不经过 MasterAgent 调度，与 `start()`/`stop()` 生命周期控制是两条独立通路**——一旦 race condition，状态不可预测。
2. **状态查询缺口** —— LLM 有 `playback_state` 查播放器，但没有统一接口查「后台能力状态」（电台正在 BUILDING？富化是否还在 RUNNING？Hello 是 PAUSED 还是 UNREGISTERED？）。每个 SubAgent 各有自己的状态类型（`RadioState` / `AgentRunState`），MasterAgent 持有 `_subAgents` 但不对外暴露。

T0 落地后这两个债显得更突出——画像已能进 system prompt，但 LLM 仍然不知道自己能调的后台能力处于什么状态。

### 做了什么

| # | 改动 | 说明 |
|---|------|------|
| 1 | **新建 `Capability` 接口**（`domain/agent/runtime/Capability.kt`） | 强制实现 `capabilityName` + `stateFlow`（暴露能力状态）；`start()`/`stop()` 可选（默认抛 `UnsupportedOperationException`，不强迫富化/Hello 实现）。状态定义 `CapabilityState`（`IDLE`/`BUILDING`/`RUNNING`/`PAUSED`/`COMPLETED`/`ERROR`）+ `detail: String` |
| 2 | **三个 SubAgent 实现 `Capability`** | Radio / Enrich / Hello 各自把内部状态（`RadioState` / `AgentRunState` / 门面状态）映射到 `CapabilityState`，加 `stateIn(scope, SharingStarted.Eagerly, ...)` 保证非空初始值 |
| 3 | **删除 DJ 工具（8 个）** | `DjTools.kt` 删除；`ToolNames` 里 8 个 `DJ_*` const 清除；`ToolRegistry.create()` 不再注册 DJ 组；`ToolRegistryView.radio()` 白名单更新；测试辅助函数 `writeQueueCall`（引用 `DJ_QUEUE_REPLACE_NEXT`）删除 |
| 4 | **新增 `CapabilityStatusTool`** | SILENT 权限，`ToolNames.CAPABILITY_STATUS`；通过 `capabilitiesProvider: () -> Map<String, Capability>` 延迟取值（避免 Koin 循环依赖）；可选 `name` 参数查单个能力，不传返回全部 |
| 5 | **`ToolRegistry.bindCapabilityTools()`** | 动态绑定方法，MasterAgent 构造完后调——`ToolRegistry.create()` 只注册 28 基础工具，`bindCapabilityTools` 追加 `CapabilityStatusTool`。这样静态/动态注册分层清晰，Fixture 测试也能适配 |
| 6 | **`MasterAgent.capabilities` 派生 getter** | 从已有的 `_subAgents` 过滤出实现 `Capability` 的实例 → `Map<String, Capability>`。**不改变 SubAgent 生命周期管理**（`start()`/`stop()` 内建意图路由不变），只是暴露能力面 |
| 7 | **Koin 接线** | `ChatKoinModule` 里 MasterAgent 构造完成后，`.also { get<ToolRegistry>().bindCapabilityTools { master.capabilities } }` |

### 架构变化

```
Before:
  ToolRegistry.create() → 28 工具（含 8 个 dj_* 绕路）
  LLM ──dj_queue_replace──▶ RadioSubAgent 内部队列（绕过 MasterAgent）
  LLM ──playback_state──▶ 播放器（看不到电台 BUILDING）

After:
  ToolRegistry.create() → 28 基础工具（无 dj_*）
  MasterAgent 构造完 → bindCapabilityTools(capabilities) → +CapabilityStatusTool
  LLM ──capability_status──▶ MasterAgent.capabilities → Radio/Enrich/Hello stateFlow.value
  电台控制权完全收归 RadioSubAgent.runLoop + MasterAgent 内建意图路由
```

### 关键设计决策

- **为什么 `start()`/`stop()` 是可选的？** EnrichSubAgent 是"每次 start 新建实例、跑完自动销毁"的模式，HelloSubAgent 是门面状态不需要 start/stop。强迫它们实现只会空壳。用 `UnsupportedOperationException` 做默认实现，真正需要生命周期管理的 Radio 才覆盖。
- **为什么 `capabilities` 从 `_subAgents` 派生而不是在 Koin 里单独注册？** 避免 Koin 循环（SubAgent → ToolRegistry → MasterAgent → capabilities 又是 SubAgent 的子集）。派生 getter 天然跟随 `_subAgents` 的变化。
- **为什么 DJ 工具能删？** T0 落地期间 RadioSubAgent 的 runLoop 已重构为模型直接返回队列→内部替换，dj_* 工具只出现在测试辅助函数 `writeQueueCall` 里（已删除）。真实运行路径无调用方。

### 2.3.1 解决的问题

`UserUsageDataScreen` 原实现有三个系统性问题：

| # | 问题 | 表现 |
|---|------|------|
| 1 | **数据源分裂** | 6 个 UI 块里只有 2 个（叙事段、时段柱图）是真·时间窗口数据，其余 4 个消费 `getUserUsageAnalytics()` 的**全量累计**。用户切「本周」时只有叙事段和柱图变化，其他数字纹丝不动，但标签还写着「本周」——**UI 宣称的时间范围与数据真实时间范围矛盾** |
| 2 | **叙事与数字重复说一件事** | 叙事卡说「本月听了 60 小时」，概览卡显示「38472 分钟」——同一屏两句话数字矛盾 |
| 3 | **职责边界模糊** | 「长期画像」块与「时间敏感统计」块混在一个滚动 `Column` 里，一个时间切换器通吃 |

根因在 **DAO 层缺口**：`MusicRepository` 只有一个全量口径的 `getUserUsageAnalytics()`，没有任何窗口版聚合方法。`HelloSubAgent.buildStatisticsNarrative` 拿到的 analytics 也是全量的——所以叙事段说「本月主打摇滚」实际是**全曲库累计主打摇滚**，只有时长是真窗口。

### 2.4.1 设计原则与演进方向

`agent.md` §7.2 选型 6 原文：「代码即配置 —— 人格预设/工具白名单为编译期常量，与工具类型安全绑定」。这是 v0 的正确选型——引擎从零搭建时，编译期常量保证了类型安全和零配置漂移。

但 `CompanionProfile.kt` 注释已标注演进方向：「B6/M7 存 DataStore、用户可改滑杆/名字/代词、自定义 persona」。**当前 F9 正是从 v0 代码即配置演进到 v1 运行时可配置的关口**。

**核心思路**：不推翻「代码即配置」，而是让它**退居为出厂默认值**。DataStore 只存用户的覆盖值（diff），未覆盖的字段自然回落代码默认。这样做三个好处：
1. **零迁移** —— 老用户首次启动时 DataStore 为空，全部回落代码默认，行为与此前完全一致
2. **可恢复** —— 「恢复默认」只需要清空 DataStore 对应 key，不需要知道默认值是什么
3. **代码仍是单一事实来源** —— 默认值的定义和演进仍在代码里，DataStore 只是覆盖层

### 2.4.3 配置模型设计

**不新建独立 Config 类**。原因：`AgentPolicyConfig` 已证明 per-Agent DataStore key-value 模式可行（"master"/"enrich" 作为 role key）。直接**扩展 AgentPolicyConfig**，在 trustLevel/alwaysAllow 基础上追加 temperature、runtimeParams、promptOverrides、personaOverride 四个可选字段。

```kotlin
// AgentPolicyConfig 扩展后
data class AgentPolicyConfig(
    var trustLevel: Int = TrustLevel.SUGGEST,
    val alwaysAllow: MutableSet<String> = mutableSetOf(),
    // === 新增：运行时参数（行为相关）===
    var temperature: Float? = null,          // null = 回落 EngineConfig 默认
    val runtimeParams: MutableMap<String, String> = mutableMapOf(),
    // === 新增：Prompt 覆盖 ===
    val promptOverrides: MutableMap<String, String> = mutableMapOf(),
    // === 新增：人格覆盖（仅 Master role 有意义）===
    var personaOverride: CompanionProfile? = null,  // null = 使用 DefaultCompanionProfiles 选中的预设
) {
    /** 出厂回落版本：把所有 null/空值替换成代码默认。 */
    fun resolvedFor(role: String): ResolvedAgentConfig = ResolvedAgentConfig(
        trustLevel = trustLevel,
        alwaysAllow = alwaysAllow.toSet(),
        temperature = temperature ?: EngineConfig.defaultTemperatureFor(role),
        runtimeParams = RuntimeParams.resolve(role, runtimeParams),
        persona = if (role == "master") (personaOverride ?: DefaultCompanionProfiles.DEFAULT) else null,
    )
}

/** 解析后的不可变快照——SubAgent 构造时或每次 LLM 调用前取一次。 */
data class ResolvedAgentConfig(
    val trustLevel: Int,
    val alwaysAllow: Set<String>,
    val temperature: Float,
    val runtimeParams: RuntimeParams,
    val persona: CompanionProfile?,
)
```

### 2.4.4 Prompt 暴露方案

**暴露粒度**：只暴露每个 Agent 的**主 system prompt**。Hello 内部各卡型的小 prompt（共 8 处）耦合业务逻辑（「用 ≤40 字写开场总述」这种指令），暴露给用户改风险高且价值低。后续如果有需要可以追加 key，但 v1 只暴露主 prompt。


**编辑护栏**：

| 护栏 | 实现 |
|------|------|
| 模板占位符 | system prompt 里保留 `{{userPersona}}` / `{{libraryStats}}` / `{{targetCoverage}}` 等占位符。用户编辑时看到的是含占位符的完整模板，运行时由 ContextAssembler 替换。**占位符不能被删除**（删除会导致运行时注入失败 → 自动回落默认 prompt） |

| 默认按钮 | 每个 prompt 文本框旁边有「恢复默认」 |
| 即时预览 | 编辑时可预览替换占位符后的最终效果（可选，v1 可不做） |

## 4. 经验与踩坑

- **「组件完成度 ≠ 功能可用度」在本族再次应验**：T1 把双轴筛选的表层做完了（DAO → Repository → ViewModel → UI 四层全通），但 `WindowedBundle.narrative` 这条支线**字段建了、取数没接**（§2.3.3），叙事段最终由顶部累计画像区承担而非设计稿的「概览卡自然语言标题」。**接线只做一半时，未接的消费点必须显式标出来。**
- **方案稿会与实现漂移，且漂移方向通常是「实现更省」**：T1 的 4 个独立路由变成 1 个带参路由、T2 的 4 个 Agent Screen 变成 1 个通用 Screen。整合过程稿时必须逐条核代码，不能照抄。
- **DAO 层新增 SQL 容易漏单测**：T1 新增 6 条窗口 SQL，`PlaybackAndListeningDaoTest` / `MusicLabelDaoTest` 均无对应用例，最终靠编译 + 人工验收过关。**SQL 类改动应强制配 DAO 级用例**（`runCatching` 兜底只能防崩溃，防不住返回错值）。
- **契约先行在本族是划算的**：T0 契约走了九版（v1→v3.8），**决策成本主要花在文档而非编码**；落地前那次「先重新 review 一遍设计」查出五类问题（5 处错误引用 / 3 处数据模型硬伤 / 1 处架构冲突），若直接开工返工量远大于重写契约。
- **`days = -1` 表示「全部」用 10 年前时间戳近似**是有效简化，但这是**隐式契约** —— 新调用方不知道 `-1` 的特例语义，建议在 DAO/Repository 的 KDoc 里写死。
