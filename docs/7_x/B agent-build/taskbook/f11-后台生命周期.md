## 1. 阶段定位

**让 agent 体系在后台活下来。**

方向 B 的 F1–F9 全部围绕"前台能用"建设，**从未指定"谁来持有运行时的生命周期"**。结果是：应用退到后台、进程被系统回收后，agent 连同全部内存态（电台队列 / 会话 / 恢复缓存）消失，回到前台需从零重开。这既是用户可感知的体验缺陷（"RadioAgent 退后台不存活"），也是一条**未落实的设计假设**——`agent-radio.md` C3「退后台不算关闭、会话保留」隐含假设"前台播放服务会保住进程"，而该假设在 Android 上从未成立。

本阶段是**收尾性质**：不改 agent 的决策能力，只补"生命周期所有者 + 平台保活"两件事。设计细节见 [`../design/agent-lifecycle.md`](../design/agent-lifecycle.md)，本文件只记推进与验收。

> **边界（D3 裁决，2026-09-19）**：**不做电台状态持久化**。进程被杀 = 电台丢，是**已接受行为**而非缺陷；跨会话认知走 `UserMemory` 正门。理由见 `../design/agent-lifecycle.md` §5。

## 5. 严格不做什么

- ❌ 不动 agent 的决策能力（`RadioSession` / 编排逻辑 / 工具层零改动）
- ❌ 不做 F10 语音会话（独立阶段）
- ❌ 不为"agent 独立于播放长期存活"另开第二个前台服务（除 Enrich 周期任务另议）
- ❌ 不追求"iOS 无音频时长期常驻"（平台不允许，明确降级预期）
- ❌ 不做跨会话历史恢复（F9-T2 已覆盖）；快照只保"当前这一档电台"
- ❌ **不做电台状态持久化**（不落盘 DataStore / Room，不存对话档案）——含"只落队列骨架"这类极轻变体。跨会话认知唯一入口是 `UserMemory`（可审计、过闸门）。**进程死 = 电台丢，明确接受**
- ❌ 不因"不落盘"放松 L2：`不落盘` 成立的前提正是"活跃期进程不被回收"，所以 L2 必须做扎实（含 R1 真机核验）

## 7. 经验与踩坑

- **跨平台运行时缺一个明确的生命周期所有者**：F1–F9 的能力都齐了，但没人对"进程该不该活着"负责。与 F8 的"组件完成度 ≠ 功能可用度"同源——**接线（消费点）要单独维护，生命周期所有者也要显式指定**。
- **"绑定服务"不等于"自持服务"**（RC2 的根）：`bindService(BIND_AUTO_CREATE)` 的服务生命周期**绑在 Activity 上**，退后台被回收即消失；只有 `startService`/`startForegroundService` 的服务才自持（`START_STICKY`）。排查后台存活问题，先看**服务是 bind 还是 start**——本项目此前只 bind，且仅通知按钮路径 start 过。
- **`startForegroundService` 有 5s 前台契约**：服务必须在 5 秒内 `startForeground()`，否则抛异常。原实现"只有在播曲目才 startForeground"，一旦在无曲目时被 `startForegroundService` 拉起即违约 → 必须**无条件**先前台化（无曲目用占位通知）。
- **前台"占位通知"是保活无音频窗口的必要代价**：电台构建中/等模型时没有可展示的曲目，但进程需要保护——用一条低优先级占位通知换取进程存活，是可接受的权衡。
- **"技术上可持久化" ≠ "应该持久化"（L4 撤销的教训）**：把 RC3「零持久化」当成缺陷去"闭环"，是**把边界误当缺口**。判据是两问 —— ① 这份状态是**情境**还是**记忆**？（电台的队列/台账/在播曲是情境，几小时后必然失效）；② 项目**是否已有记忆载体**？（有，`UserMemory`，且它可审计、过闸门）。两条都指向"不该由电台自己落盘"。**过早引入第二条记忆通路，比缺少这条通路代价大得多。**
- **"不落盘"是一个有依赖的决策**：它成立的**前提**是 L2 真的把"活跃期进程不被回收"做到了（否则被杀频率高到体验受损）。**接受一个边界，必须同时接受支撑它的那条假设必须被验证**——所以 L2 的真机核验（含 R1）不是可选项。
