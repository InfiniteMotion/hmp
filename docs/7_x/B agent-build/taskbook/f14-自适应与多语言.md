# F14 · Agent 界面自适应与多语言（横切加固）

> **定位**：方向 B（agent-build）收尾后的**横切加固章**。F1–F13 建完了能力与结构，
> 本章解决"agent 界面的**交付质量**"两件事：**看得舒服**（自适应显示适配）与**看得懂**（字符串资源收拢 + 14 语言）。
> **性质**：横切加固。不改任何交互逻辑与信息架构，只调布局形态与资源组织。
> **依赖**：F13（页面清单在其结构收敛后固定；`AgentVisuals` 等共享件已就位）。
> **用户裁定**（2026-09-21）：**先做 T1 UI 适配，再做 T2 字符串收拢**；多语言**本轮 14 语言全量交付**；自适应范围为**全部 agent 页面**。
> **范围扩展**（2026-09-21 二次裁定）：基建排查发现另一批"设施已建、agent 绕行"的同构欠账，用户裁定四项并入本章 → **T3 组件基建对齐**（①表单基础件 ②空态/状态件 ③尺寸令牌 ④状态色散点）；⑤ AgentNoticeBar 经调查为**死组件**（挂载但事件源零实装），**不并入**——补活属功能工作，调查结论见 §3.3。

***

## 0. 为什么立

两个问题都是 F13 收尾盘点（`taskbook/README.md` 已知验收缺口）里挂账的：

1. **自适应欠账**：agent 页面全部诞生于"手机竖屏优先"的开发节奏，
   布局按单档宽度写死。而项目早有窗口分级基础设施
   `common/layout/WindowSizeClass.kt`（Material3 三档断点 + 全局 `LocalWindowSizeInfo`），
   电台控制台（`RadioConsole`）也已自适配 —— **但 agent 的其余页面 0 消费**：
   - 桌面端宽窗（Expanded ≥840dp）下，对话页 / 看板 / 设置表单**拉满全宽**，
     可读性差（行长过长是排版大忌）；
   - 看板六卡固定"每行两个"，宽窗下右侧大量留白。
2. **本地化欠账**：agent UI 约十几批页面把界面文字**硬编码在 Kotlin 里**。
   实测（2026-09-21）：`ui/agent` 子树 **344 处**中文文案字面量（全 ui 树 426 处，agent 占八成）；
   而项目 14 语言资源设施齐全（`composeResources/values*` × 14，各 474 键，`stringResource` 用法成熟）。
   硬编码 ⇒ 非 zh 系统语言下 agent 界面**整页中文**，14 语言设施对 agent 形同虚设。

**本章产出不是新能力，而是"agent 界面在任意窗口尺寸、任意系统语言下都达到既有页面的交付水准"。**

***

## 1. 判据（三条，勿混）

1. **自适应 = 消费既有分级，不发明新断点。**
   只用 `WindowSizeClass.kt` 的三档（Compact <600 / Medium 600–840 / Expanded ≥840 宽；
   高 Compact <480 / Medium 480–900 / Expanded ≥900）与 `isLandscape` 等既有派生量。
2. **收拢 = 只收 UI 面向文案。**
   判据：**这段文字最终渲染给用户看的吗？** 是 → 进 `strings.xml`；
   发给 LLM 的消息、领域层回退文案、日志/调试文本 → **保留原样**（翻译它们反而污染模型输入）。
3. **翻译 = 14 语言全量交付。**
   每个新键在 14 个 `strings.xml` 中同时存在；占位符（`%1$s` 等）在各语言中**一个不少**。

**实施中的两个技术要点（踩坑记录）**：

1. **`Dp.Unspecified` 是零 diff 的关键**。`widthIn(max = Dp.Unspecified)` 是**无约束**（不是 `max=0`），因此 Compact 分支下布局与改造前逐像素一致 —— 这直接满足验收条件「不改变任何 Compact 行为」。比"Compact 给一个很大的 dp"更严谨：后者在超宽手机上仍会触发约束。
2. **`IntrinsicSize.Max` 与 `weight` 分属不同轴，可以共存**。看板六卡靠 `Row.height(IntrinsicSize.Max)` + 卡 `weight(1f)` 实现「同行等高 + 等宽」：`IntrinsicSize.Max` 约束的是**纵轴**（取同行最高内容作行高），`weight` 分的是**横轴**，二者互不干扰。改造只是把「写死两行 Row」换成 `chunked(columns)` 的数据驱动网格，等高语义不变。（原 `fillMaxHeight()` 随之去掉——高度已由 `IntrinsicSize.Max` 钉死，卡内 `Column` 无需再撑满。）

**回归验证**：`HelloCard*`（含 `HelloCardRotator`/`HelloCardStack`）与 `RadioConsole` **未触碰**（`git diff` 可证），符合 §3.1「仅回归验证」的定位 —— 卡片按固定卡宽设计随容器自适应，控制台已走 `BoxWithConstraints`。T3 事项（④）顺带收口，T3 其余三项留待 T3 阶段。

> 经验（与 §3.5 同源，互补）：
> - **`fillMaxHeight()` 与 `aspectRatio` 互斥地影响卡片"形状"**：前者让高随容器（形状不可控），后者让高随宽（形状可控）。**内容型卡片（有图文排布）应优先可控**，仅在容器高度本身有语义时才用 `fillMaxHeight()`。
> - **`Modifier.weight(f)` 默认 `fill = true`，是"隐形撑满器"**：父容器用 `Arrangement.Center` 想居中，却因某个子项 `weight(1f)` 把余量全吃掉而使居中失效。**要"可增长但不必填满"用 `weight(f, fill = false)`**。这是"内容顶到两端、中间大空"类布局问题的通用成因。

### 3.7 Hello 卡升级 3D 表现 —— 第一版（Pager 改造，**已废弃**）

> ⚠️ **本节的实现已被 §3.8 取代**。保留于此**仅作踩坑记录** —— 它记录了一条"看起来可行、实测走不通"的路径，以及三个具体的技术障碍。**结论：不要试图在 `VerticalPager` 上做 3D 堆叠。**

**触发**：§3.6 把比例修到 1.11 后，用户再次反馈"还是不算协调"，并提出**换掉 Pager、用更高级的表现方式（3D 卡片）**。经讨论选定**垂直 Coverflow**（理由：原始卡形是 10:9 **竖长**，横向铺开会与卡形打架；垂直方向才贴合）。

**技术路线裁定**：**伪 3D（`graphicsLayer` 透视变换）**，不引入真 3D 渲染（Filament / SceneView 等）。理由：① 项目已具备能力（`graphicsLayer` 在 `FusionSidebar`/`BottomFusionBar` 已有使用），`transformOrigin`/`cameraDistance` 均在 `ui-graphics` 内，**零新依赖**；② 9 种卡型（ANCHOR/RADIO_STATUS/GREETING/RECOMMEND/DISCOVER/FORGOTTEN/ANNIVERSARY/ENRICH_TRACKING/NARRATIVE）**全部自动生效** —— 只换外层变换，`FamilyDispatch` 分发的卡内容零改造。

**做法**：在 `RotatingPersistentCards` 的 `VerticalPager` 上叠加变换 —— 偏移量保留符号、`rotationX = signedOffset × 32°`、`cameraDistance = 14f`、`contentPadding = 容器高 × 18%`、`beyondViewportPageCount = 2`、`.zIndex(1f - absOffset)`、indicator dots 改主题色。

**实测结果（用户两次截图验证）**：**失败**。邻卡只露出约 48dp 的**无内容色条**（正好是卡的顶边/底边留白区），看不到任何信息，视觉上像"两块装饰色块"，Coverflow 语义完全没有兑现。

**失败根因（量算确认，非猜测）**：`VerticalPager` 的三个布局机制与 3D 堆叠互相冲突 ——

| # | 机制 | 冲突点 |
|---|---|---|
| ① | `contentPadding` **双重作用** | 它既**缩小卡高**（卡高 = 容器高 − 2×padding），又**缩短页间距**（槽位高 = 卡高）。两个效果方向相反：想多露邻卡就得加大 padding，但加大 padding 又把邻卡中心拉近、反而遮得更死。**参数不存在可行解** —— 枚举 18%/22%/26% × spacing(10,0,−20) × scale(0.78/0.85/0.9) 共 27 组，**全部露出量 ≤48dp**，且多数为负值（完全不可见） |
| ② | `pageSpacing` 负值被钳制 | 想让邻卡内收只能用负 spacing，但 Pager 的测量逻辑对负值支持不稳，行为不直观 |
| ③ | 绘制顺序按页序 | Pager 后页压前页 ⇒ 上邻卡会盖住中卡，必须靠 `zIndex` **事后纠正**（而非天然正确） |

> 经验（三条，对后续任何"在 Pager 上做非常规布局"的尝试都适用）：
> ① **`contentPadding` 不是"留白"，是"缩小页面 + 缩短间距"的复合操作** —— 想用它制造 peek 是典型的误用；
> ② **一个控件若要靠 `zIndex` 事后纠正层序，说明它本身的绘制模型与需求不匹配**；
> ③ **参数枚举能快速证伪一条路线** —— 27 组组合全不可行，就不该再调参，该换实现。

### 3.8 HelloCardCoverflow —— 横屏专用自绘 3D 堆叠（2026-09-22 五轮，最终方案）

**决策**：用户在看到 §3.7 的失败后裁定 —— **"最好不复用这个 VerticalPager，针对横屏重写一个组件"**。

**架构：数据组装与渲染解耦**。`HelloCardStack.kt` 原本把 5 路数据源（agent 产物 / ANCHOR / RADIO_STATUS / ENRICH / NARRATIVE）+ Pager 渲染糅在一个函数里。现拆为：

```
rememberHelloCardsState()  →  HelloCardsState(cards, permanentLock)   ← 数据组装（5 路，与渲染无关）
     ├─ RotatingPersistentCards   （竖屏 Compact：Pager 轮播，原样保留）
     └─ HelloCardCoverflow        （横屏宽窗左栏：自绘 3D 堆叠，本轮回写）
```

拆分的必要性：两种渲染必须看到**完全一致**的卡列表，否则会出现"换个断点卡就变了"的怪 bug。`rememberHelloCardsState()` 是 `internal`，两个渲染组件共用。

**新组件 `HelloCardCoverflow.kt` 的设计**：

| 维度 | 做法 |
|---|---|
| 布局 | **不用 Pager**。`BoxWithConstraints` 量容器 → 自己算每张卡的位置，用 `Modifier.layout { placeRelative(x, y) }` 显式摆放（y = 中心偏移 + `d × stepPx`） |
| 尺寸 | **卡高 = 容器高 × 0.66**（上限 520dp）。卡形 **9:8**（宽:高），卡宽 = 卡高 × 9/8 并受容器宽约束。**不再解不动点**（见下"尺寸方案的两次迭代"） |
| 步长 | 相邻卡中心距 `step = cardH × k`，**`k` 取固定常数 1.02**（不再由露出量反推，见下） |
| 3D | `graphicsLayer`：`rotationX = ±30°×eased`（上方卡后仰、下方卡前倾）、`cameraDistance = 14f`、邻卡 `scale 0.88` / `alpha 0.45` |
| 层序 | `.zIndex(10f - absD)` —— **显式**排（不再靠事后纠正） |
| 手势 | `detectVerticalDragGestures` 上下拖拽切页（阈值 70px）+ `Animatable` 弹性动画（`spring(dampingRatio=0.85)`） |
| 轮播 | 4s 自动轮播 + 用户操作后 5s 临时锁（**语义与 Pager 版完全一致**）；电台激活时只停轮播、不禁拖拽 |
| 渲染裁剪 | 只渲染焦点 ±2 张（Coverflow 无需渲染全部） |
| 循环滚动 | **无限循环**（用户裁定"锁定也循环 / 自动轮播也统一无限"）。`offset` **不钳制**，通过取模映射真实卡号。三个关键函数：`ringDelta`（环形最短有符号距离）/ `normalize`（静态归一化防精度劣化）/ 渲染层"展开索引算 d、取卡才取模"。见下 |
| 指示点 | 右侧竖排，`MaterialTheme.colorScheme.onSurfaceVariant`（浅底可见）；高亮判据同样走 `ringDelta`（直接 `|index−offset|` 在循环下会跳） |

**无限循环的实现要点（三处必须一致，缺一即穿帮）**：

1. **`offset` 不钳制**。手势拖拽 `snapTo(offset - delta/stepPx)` 与自动轮播 `animateTo(offset+1f)` 都**不做 `coerceIn`**；自动轮播也不再判断"是否到尾"。
2. **渲染用"展开索引"，只有取卡时才取模**。`rawIndex = base + step`（连续序列，**不取模**）→ `d = rawIndex - center` 永远落在 ±2 内，位置/缩放/旋转自然连续；`cardIndex = ((rawIndex % n) + n) % n` 才映射到真实卡。**若反过来先取模再算 d**，`n=5、center=4、要看第 0 张`时会算出 `d = -4`（卡飞到屏幕上方很远处），而正确值是 `d = +1`（从底部滑上来）——这正是循环 Coverflow 最容易穿帮的地方。
3. **`key(cardId)` 包裹 `FamilyDispatch`**。取模会让**同一槽位**在不同时刻轮到不同卡；不给 key 时 Compose 按槽位复用节点，归一化（`5.0→0.0`）那一刻槽位换卡，卡内状态（如 `AsyncImage` 已加载的封面）会被错误继承或重置。用 `cardId` 作 key 保证"同一张卡无论滚到哪个槽位"都复用同一 composition。

**锁定语义的弱化**（用户裁定下）：电台激活时**只停自动轮播 + 滑到 RADIO_STATUS**，**不限制用户拖拽**（原实现是 `pointerInput` 里 `if (locked) return`，现已去掉）。滑到电台卡用 `ringDelta` 取环形最短路径 —— 从第 1 张到第 n−1 张应**往回**走一格而非绕一整圈。

**数学校验**（Python 复刻，非运行时）：`n=5` 时 `center 4.0→5.0` 中卡卡号 `4→0` 且邻卡序列连续；`center 0.0→-1.0` 中卡 `0→4`；`normalize` 前后卡号序列完全一致（`5.0/10.0/-5.0 → 0.0` 均为 `[3,4,0,1,2]`）；正向滚 20 次回到 0、反向滚 7 次落在 3，无累积漂移。

**关键约束：`k > 0.5 + scale/2`（不是 `k < 1`）**。这是本节最容易踩错、也最反直觉的一点。设邻卡中心偏移 `s = cardH × k`，则露出量

```
vis = s − cardH×(scale/2) − cardH×(1/2) = cardH × (k − scale/2 − 0.5)
```

`k = 0.78`（"叠得紧"的直觉值）时 `vis = cardH × (0.78 − 0.44 − 0.5) = −0.16×cardH` ⇒ **负值，邻卡被中卡完全遮住**，屏幕上根本没有邻卡。Coverflow 的露出量**恰恰要求 `k` 略大于 1**，因为邻卡还额外缩了 `scale`。本节第一版的"看不见邻卡"就是这个符号错误的直接后果。

**尺寸方案的两次迭代（第二次由用户截图触发）**：

- **第一版（已废弃）：解不动点**。硬约束定为"d=±1 的邻卡必须完整落在容器内"，几何上即 `cardH×(1+k) = H`，而 `k` 又含 `露出/cardH` 项 ⇒ 需解不动点，迭代 24 轮收敛。**实测观感问题**：`k` 里含"露出量 ÷ 卡高"这一项，导致 **k 越大卡越小**的正反馈 —— 容器 576dp 时收敛出卡高仅 246dp（**远低于 520dp 上限**，说明卡不是被上限限制，而是被公式自己压小），在左栏里显得又小又孤立。
- **第二版（现行）：直接给比例 + 固定 k**。用户截图反馈"卡片之间空白可以小一些、卡片可以更大、比例也可以改变"，并裁定**"卡大为主，允许邻卡被裁"**。两条改动：
  - `cardH = H × 0.66`（上限 520dp），**放弃"邻卡完整"约束**。邻卡被容器边缘裁掉一点本就是 Coverflow 的正常观感（iOS 同理）。
  - `k` 改**固定常数 1.02**。这一点很关键：若仍用"目标露出 dp ÷ cardH"反推，则小窗口下 `露出/cardH` 变大、`k` 被推高、邻卡几乎全出画（实测容器 500 时邻卡只露 43dp、占卡高 13%，**越小越糟**）。改用常数后**邻卡可见高度 = 卡高的固定比例**（k=1.02 时恒为 ~16%），**与窗口大小无关** —— 这才是 Coverflow 该有的尺度无关性。

| 容器高 H | 旧：卡高 | 新：卡高 | 旧 k | 新 k（常数） | 旧邻卡可见 | 新邻卡可见 |
|---|---|---|---|---|---|---|
| 576（1104×680 窗口） | 246 | **380** | 1.244 | 1.02 | 25dp（10% 卡高） | 59dp（16% 卡高） |
| 620 | 270 | 409 | 1.233 | 1.02 | 28dp | 63dp |
| 800 | 361 | 520（触上限） | 1.189 | 1.02 | 41dp | 98dp |

（同窗口下卡高 **+54%**、卡宽 **+57%**。）

**HomeScreen 接线**：宽窗左栏 → `HelloCardCoverflow(Modifier.weight(0.8f).fillMaxHeight())`；Compact → `HelloSlideCardStack`（**恢复原 `aspectRatio(10f/9f)`**，Pager 版不改）。
宽屏 Row 的 padding 为 `start/end 32dp, top 16dp, bottom 88dp` —— **bottom 88dp 是为悬浮播放条预留**（`MiniPlayerBar` 是 AppRoot 层浮层，不占布局高度；原只留 16dp，导致下邻卡被播放条吃掉一半）。

**卡内间距修正（同轮）**：3D 堆叠把卡放大到最高 520dp，暴露了三个卡内布局的存量问题：
- `FamilyNarrativeCard` / `FamilyEnrichTrackingCard`：外层 `Column(fillMaxSize, Arrangement.SpaceBetween)` 但内容只有"上段 + 可选的短脚注"，`SpaceBetween` 把首尾硬推两端、**中间留下贯穿全卡的空白带**。改 `Arrangement.Center` + 显式 `spacedBy`。
- `FamilyNarrativeCard` / `FamilyGreetingCard`：正文 13sp、行高 22–23sp 在大卡里显得"飘"，上调至 15–16sp / 25–27sp。
- `FamilySingleTrackCard`：`Modifier.weight(1f)` → `.weight(1f, fill = false)`（详见 §3.6）。

**回归安全**：`HelloCardRotator.kt` **已 `git checkout` 还原至改动前**（§3.7 的所有改动撤销）。竖屏路径与改造前逐像素一致，`Compact 零 diff` 在该文件上恢复成立。

> 经验：**当"调参"超过 2 轮仍不奏效，问题通常在架构而不在参数**。§3.7 花了大量精力枚举 27 组参数试图让 Pager 就范；换成自绘后，同一组视觉参数一次到位 —— 因为自绘把位置/缩放/旋转/层序从"要绕过的副作用"变成了"可以直接写的表达式"。

> 经验（尺寸方案）：**"约束"要选对，否则会自我反噬**。§3.8 第一版把"邻卡必须完整可见"当硬约束，推出一条 `cardH = H/(1+k)` 的公式 —— 而 `k` 里含 `cardH`，形成"卡越小 → k 越大 → 卡被除得越小"的正反馈，最终卡高远低于上限（被公式自己压小，不是被上限限制）。**判定信号：算出来的尺寸离上限很远，说明卡是被别的约束限制的，不是被上限限制的。** 第二版放弃该约束（用户接受"邻卡可被裁"）+ 用常数 `k`，问题消失。

### 3.9 HomeScreen 宽窗右栏间距节奏修复（2026-09-22 六轮）

**触发**：用户第五次截图（卡放大后）反馈右栏问题。用户明确定义了问题边界 —— **"空无所谓，主要是间距不合理，而且与左侧间距太小"**。即：留白本身不是缺陷，**间距的层级关系**才是。

**根因①：右栏用单一 `spacedBy(16.dp)` 平铺所有元素**。原代码是 `Column(spacedBy(16.dp))` 内部再插一个硬编码 `Spacer(32.dp)`，实际间距变成：

| 相邻元素 | 原间距 | 问题 |
|---|---|---|
| 搜索框 → 「为你推荐」标题 | 16 + 32 = **48dp** | 太远 |
| 标题 → 它的卡片组 | **16dp** | 太近，标题"贴"在卡上 |
| 卡片组 → 「探索」标题 | **16dp** | 太近 |
| 标题 → 三卡 | **16dp** | 太近 |

关键错误：**标题↔它的内容** 与 **上一块内容↔下一个标题** 用了**同一个值**。于是标题既不属于上面、也不属于下面，视觉上"飘"在中间，区块边界完全糊掉。

**修法：区分组内 / 组间两级间距**。

| 层级 | 值 | 用于 |
|---|---|---|
| 组内（标题 ↔ 它的内容） | **12dp** | 标题紧跟内容，明确"属于"关系 |
| 组间（内容 ↔ 下一个标题） | **28dp** | 比组内大一倍多，区块才分得开 |

实现上**去掉 `verticalArrangement`**（默认零间距），逐段用 `Spacer` 手控 —— 因为需要的是**非均质**间距，`spacedBy` 的均质模型表达不了。

**根因②：两栏间距太小**。`spacedBy(24.dp)` 在左栏卡放大到 428dp 宽后，两栏挤在一起。改 **44dp**（约右栏卡内 padding 的 3 倍）。

**为什么左栏权重必须保持 0.8:1**：实测若改成 0.72:1（想给右栏更多空间），你的窗口（1104 宽）下左栏只剩 **417dp**，而卡宽需要 **428dp** —— 卡会被 `cardWidthFraction` 截掉。0.8:1 + 44dp 间距在 1104–1600 宽下都放得下：

| 窗口宽 | 间距 | 左栏 | 右栏 | 卡宽 | 放得下 |
|---|---|---|---|---|---|
| 1104 | 44 | 443 | 553 | 428 | ✓ |
| 1280 | 44 | 521 | 651 | 428 | ✓ |
| 1600 | 44 | 663 | 829 | 428 | ✓ |

> 经验：**间距是层级信号，不是填充物**。同一组元素内用同一个值、跨组用更大的值 —— 这条规则比"调大/调小某个 padding"更能解决"看起来不协调"。当出现"标题不知属于哪一块"的观感时，先查是不是**所有间距都被拉平成了同一个数**。

**第二轮（同日）：探索卡压扁 + 横向间距统一**。用户第七次截图后，发现两个残留问题：

**① 「探索」三卡被比例撑得过高**。`FeatureEntryRow` 的 `FeatureEntryCard` 用 `aspectRatio(1.2f)`，右栏宽 553dp 时三卡各约 174dp 宽 ⇒ 卡高 **145dp**，而内容只有 24dp 图标 + 一行 14sp 文字（约 50dp）。**注意这不是"留白多"的缺陷**（用户已说"空无所谓"），而是**卡被比例撑高**导致的尺寸失衡 —— 与上方入口卡（82dp）的比值只有 **0.57**，两组卡不像一个系统。

修法：`aspectRatio(1.2f)` → **`1.9f`**（卡高 145 → **91dp**，比值 0.57 → **0.90**）；`Arrangement.SpaceEvenly` → **`Arrangement.Center` + 固定 `Spacer(10.dp)`** —— 原来的 SpaceEvenly 把"图标"和"文字"当两个独立元素在剩余高度里均分，卡一变扁它们就被拉开、不成组；Center + 固定间距让它们始终作为一个整体居中。

**② 横向同级间距不统一**。区域②卡间是 20dp、区域③卡间是 20dp，但与本区"标题→内容"的 12dp 只差 8dp，层级区分不明显。统一为 **横向同级 16dp**（两处都改），与纵向的 12/28dp 一起构成完整的三档体系：

| 关系 | 值 | 用在哪 |
|---|---|---|
| 横向同级卡间 | **16dp** | 区域②卡组 · 区域③三卡 |
| 纵向组内（标题 → 它的内容） | **12dp** | 「为你推荐」↔ 卡组 |
| 纵向组间（区块 ↔ 区块） | **28dp** | 搜索框↔区块 · 区块②↔区块③ |
| 两栏间距 | **44dp** | 左栏 ↔ 右栏 |

效果：右栏总高 518 → **465dp**（省 53dp），两组卡片高度都落在 80–90dp 量级。

> 经验：**"留白多"和"卡片过大"是两个问题，别混为一谈**。用户说"空无所谓"时，指的是**不必为填满而加内容**；但如果卡是被 `aspectRatio` 撑高的，那就是**尺寸缺陷**，该改比例而不是加内容（加内容会动信息架构）。判据：**内容高度 ÷ 卡高 < 0.5 且卡与同级卡量级差异大 → 是比例问题**。

**第五轮（同日）：探索卡恢复 1:1 + 横屏组间间距重调**（用户："恢复探索卡片的 1:1 比例"）。上一轮把 `aspectRatio` 从 1.2 → 1.9（压扁）以避免右栏过长；本轮用户裁定**恢复 1:1 方形**（与上方「今日推荐」卡组形态更一致）。**代价**：探索卡高 = 卡宽（900 窗口下 ≈133dp、1104 下 ≈171dp、1366 下 ≈220dp），比 1.9 时（90dp 量级）**高了 40–130dp**，直接把右栏撑爆 —— 实测**三档全部溢出 41–59dp**，而溢出会触发 `verticalScroll`、**垂直居中随即失效**。

**重调组间间距分档**（右栏固定项 344dp + 探索卡高 = 卡宽）：

| 窗口宽 | 组间间距 | 900×600 | 1104×680 | 1366×768 | 余量 |
|---|---|---|---|---|---|
| < 1100dp | **6dp**（原 30） | ✓ 余 7dp | — | — | 最紧 |
| 1100–1300dp | **26dp**（原 60） | — | ✓ 余 9dp | — | — |
| ≥ 1300dp | **46dp**（原 72） | — | — | ✓ 余 8dp | — |

窄档 6dp 是**实测约束**：900×600 可用高 496dp，减去固定项 344 + 卡高 133 后只剩 19dp，两个组间各 6dp 才留 7dp 安全余量（8dp 只剩 3dp，字体行高稍有出入就溢出）。

> 经验：**改一个"看起来局部"的尺寸前，先算它对最紧约束的传导**。`aspectRatio` 从 1.9 → 1 是个"卡片形状"决定，但探索卡高 = 卡宽，右栏宽又由窗口宽决定 —— 于是**这个比例选择直接决定了窗口能容纳多少组间间距**。"恢复 1:1"表面是改一行，实际把右栏间距档值全部推翻重来。**尺寸参数之间是耦合的：动上游（卡形）必须重算下游（间距档）**。

**第三轮（同日）：垂直居中 + 拉开组间距**。用户第八次截图（"**让右侧内容垂直居中然后在各个部分之间增加间距**"）。此时右栏内容顶对齐，内容总高 465dp 而可用 576dp ⇒ **下方留下约 110dp 死区**（上方仅 16dp），上下严重失衡。

**两个修改（必须一起做）**：

1. **垂直居中**：右栏外层加 `Box(weight(1f).fillMaxHeight(), contentAlignment = Alignment.Center)`。
   ⚠️ **不能直接给带 `verticalScroll` 的 Column 加 `verticalArrangement = Center`** —— 滚动会把高度约束变成**无界**，此时不存在"剩余空间"，Center 是空操作。必须拆两层：外层 `Box` 提供确定的可用高度，内层带滚动的 Column 在其中居中；只有内容超出时滚动才生效，两者不冲突。
2. **组间间距 28 → 40dp**（组内仍 12dp）。

**为什么必须一起做**：居中是**位置**修正，拉开间距是**密度**修正。只居中不拉开 → 内容挤成一坨沉在中间；只拉开不居中 → 死区只是从下面挪到上面。两件事一起做，上下留白才对称（44dp / 44dp）。

| | 调整前 | 调整后 |
|---|---|---|
| 内容对齐 | Top | Center |
| 组间间距 | 28dp | 40dp |
| 上方留白 | ~16dp | 44dp |
| 下方留白 | ~110dp（死区） | 44dp |
| 上下均衡 | ✗（16 vs 110） | ✓（44 vs 44） |

> 经验：**`verticalScroll` 与 `Arrangement.Center` 不兼容**。滚动容器的高度约束是无界的，任何"在剩余空间里分配"的 arrangement（Center/SpaceBetween/SpaceAround）都会退化为空操作。想"内容少时居中、内容多时滚动"，必须用 `Box(contentAlignment=Center) { Column(verticalScroll) }` 两层结构。

**第四轮（同日）：间距全面加大 → 发现溢出 → 改为自适应组间**。用户第九次截图后要求"**整体给右侧组件之间增加间距**"，选定"全面加大（含组内/底部）"：横向同级 20dp / 组内 16dp / 组间 **52dp** / 底部 24dp。

**但写死 52dp 会溢出**。逐项实测右栏基础高：

| 项 | 高 |
|---|---|
| `HomeSearchBar`（HMPTextField） | 56dp |
| 「为你推荐」`titleLarge` | 28dp |
| 组内 spacer | 16dp |
| 推荐区 `Row(height(180.dp))` | 180dp |
| 「探索」`titleLarge` | 28dp |
| 组内 spacer | 12dp |
| `FeatureEntryRow`（探索卡） | 90dp（1.9f 时；**第五轮改 1:1 后 = 卡宽，见 §3.9 第五轮**） |
| 底部 spacer | 24dp |
| **基础高合计** | **434dp** |

各横屏窗口可用高 = 窗口高 − top16 − bottom88，留给两个组间的余量：

| 窗口 | 可用高 | 余量 | 组间上限 | 写死 52dp 时（总高 538） |
|---|---|---|---|---|
| 900×600 | 496 | 62 | **31dp** | **溢出 42dp** ⚠️ |
| 1000×620 | 516 | 82 | 41dp | 溢出 22dp ⚠️ |
| 1104×680 | 576 | 142 | 71dp | 留 38dp ✓ |
| 1280×720 | 616 | 182 | 91dp | 留 78dp ✓ |
| 1440×800 | 696 | 262 | 131dp | 留 158dp ✓ |

**关键**：一旦内容超出，`verticalScroll` 生效 —— 而**滚动一出现，上一轮的"垂直居中"立刻失效**（退回内容顶对齐）。也就是说，**写死大间距等于把居中改坏**。

**修法：组间间距按窗口宽度分三档**（用户裁定"高度自适应太复杂了，就适应不同窗口尺寸就行"；随后又提"expanded 下右侧间距还可以放大一些"，故档值二次上调）。用 `AppWindowSizeInfo.widthDp` 直接判档，**零测量、零状态、无 `BoxWithConstraints`、无 `onSizeChanged` 测量回路**：

```kotlin
val widthDp = LocalWindowSizeInfo.current.widthDp
val groupGap = when {
    widthDp < 1100f -> 30.dp   // ⚠️ 已过时：第五轮（探索卡恢复 1:1）改为 6.dp
    widthDp < 1300f -> 60.dp   // ⚠️ 已过时：第五轮改为 26.dp
    else            -> 72.dp   // ⚠️ 已过时：第五轮改为 46.dp
}
```

> **⚠️ 上表与本段为第四轮（探索卡 1.9f、基础高 434dp）时的推导，已被第五轮推翻。** 探索卡恢复 1:1 后基础高不再固定（含卡宽项），档值重调为 **6 / 26 / 46dp**，详见本节末「第五轮」。

| 窗口宽 | 组间 | 总高（= 434 + 2×组间） | 最紧窗口校验 |
|---|---|---|---|
| < 1100dp | **30dp** | 494dp | 900×600（可用 496）余 **2dp** ✓ |
| 1100–1300dp | **60dp** | 554dp | 1104×680（可用 576）余 22dp ✓ |
| ≥ 1300dp | **72dp** | 578dp | 1366×768（可用 664）余 86dp ✓ |

窄窗给紧值（高度通常也紧）、宽窗给满值，**所有档位零溢出、居中永远生效**。

**为什么用 `widthDp` 数值而非 `WindowWidthSizeClass` 三档**：横屏两栏布局下窗口宽普遍在 900–1600dp，而 `WindowWidthSizeClass` 的 `Expanded` 阈值是 840dp —— 1000dp 和 1600dp 会被归为同一档，区分度不足。故按 dp 数值自定义分档点（1100 / 1300）。

**档值上调记录**：初版 30/44/52dp；用户看实机截图后要求"expanded 下还能放大一些"，中档 44→**60dp**、宽档 52→**72dp**（`<1100` 档上限仅 31dp 已顶格，保持 30dp 不动）。分档点 1080→**1100**，确保用户 1104 宽的窗口稳落中档。

**中间被推翻的中间方案（记录以免重复踩）**：曾先实现"按可用高度连续自适应"—— `BoxWithConstraints` 拿 `maxHeight` + `onSizeChanged` **成对**保存 `(实测总高, 当时 gap)`，还原基础高后把余量平分给两个组间，`coerceIn(20, 52)`，2 轮收敛、效果正确但**代码太绕**，被用户否掉。实现中抓出的三个坑仍有参考价值：①**测量↔间距循环依赖**（量的是含当前 gap 的高，直接反推会形成负反馈震荡，必须成对保存以还原纯基础高）②**系数写错**（`40 + slack*0.5/2` = 40+slack×0.25，本意是余量平分 `slack/2`，导致仍溢出 42dp）③**下限须低于字体放大后的需求**（`base=434dp` 是常规字体下的值，放大后会涨）。

**同轮：注释精简**（用户："清理一下注释，不要写这么多"）。`HomeScreen.kt` 注释 52 → **37 行**，最长连续注释块 11 → **7 行**（仅保留 `groupGap` 分档依据这一处实质说明）。删除的是：已废弃方案的历史考古（`addAllToPlaylistInOrder` 的旧写法剖析）、反复重述同一结论的"①②③"式分点、以及装饰性分隔线（`═══` / `───`）。

> 经验：**"内容能在容器里放得下"是居中的前提**。任何"居中 / 均分 / 对齐"的布局技巧，一旦内容超出触发滚动或裁剪，全部失效。当用户要求"加大间距"时，不能只改常量 —— 必须先算出**最窄目标窗口的容量上限**，再决定写死还是分档。**固定值在"最宽窗口好看"和"最窄窗口不崩"之间永远只能二选一，分档（或自适应）才能兼得**；但两者都能解决时，**优先选分档** —— 可读性远高于连续自适应。
>
> 经验：**注释记"为什么"和"边界值"，不记"曾经是什么"**。本次清理的主力是"已废弃方案的历史剖析"——这类注释在方案定型后价值骤降，却占据大量篇幅、还容易与现状矛盾。真正该留的是**非直觉的约束**（如"440dp 基础高 + 900×600 可用 496dp ⇒ 组间上限 31dp"），因为它解释了"为什么不能更大"——这是改代码的人最需要的。

### 3.10 竖屏改为自绘堆叠 —— 横竖屏统一（2026-09-22）

**触发**：用户问"竖屏的 pager 可以做循环滚动吗"。调研后确认 **Compose 官方 Foundation 的 `VerticalPager` 至今（2026-09）没有任何循环能力** —— 参数表里只有 `pageCount`/`pageSpacing`/`contentPadding`/`beyondViewportPageCount`，没有 `loop`/`infinite` 开关；Wear OS 版同样没有，其"无限旋转"实际靠 `Int.MAX_VALUE` hack 实现。用户裁定"**竖屏也改成自绘**"。

**做法：`HelloCardCoverflow` 参数化**，而非复制第二份实现。横竖屏的差异**只有几个视觉数**，循环/手势/轮播/锁定/指示点逻辑完全一致，分开写会变成两份要同步维护的代码。

新增 `CardStackTuning`（`HelloCardCoverflowTuning.kt`），两个预置：

| 字段 | `Landscape` | `Portrait` |
|---|---|---|
| 尺寸模式 | `fillContainer = false`（按容器高算） | `fillContainer = true`（**卡填满容器**） |
| 卡形 | 9:8（组件内算） | 10:9（**由调用方 `aspectRatio` 定**） |
| `stepFactor` k | **`leanNeighbors` 斜倚堆叠（步长恒 1.0 卡高）** | **1.0** |
| `cardSpacingDp` 卡间距 | 0（斜倚靠内缘贴合，间距会破坏贴合） | **12**（卡与卡拉开，滚动时有分隔感） |
| `exitScale` 离开缩小 | 0.8 | **1.0**（不缩，"纯位移"） |
| `neighborRotation` 倾角 | **72°**（绕内缘斜倚） | **0°**（不转，免眩晕） |
| 邻卡位置 | 中心距 1.0 卡高，**绕内缘翻转** → 外缘整体入容器（余 2–7dp） | 中心距 **1.0 卡高 + 12dp** → 邻卡整体越出视口（"一页一卡"） |
| 切换效果 | 3D 斜倚堆叠（层次语言） | **纯位移 + 淡入淡出**（单页翻页语义） |
| 邻卡 scale / alpha / 倾角 | **0.8** / 0.65 / **72°**（2026-09-22 第七轮，见 ⑦） | 1.0 / 0 / 0° |

**① 竖屏 `stepFactor = 1.0` 的原理**（此处曾误用 0.94，见下）：相邻卡中心距 = 卡高 × k，即 **k = 1.0 时邻卡正好落在"下一个容器高度"处**，加上邻卡缩放后的半高（scale/2 = 0.44 卡高），其区间为 **[+0.56, +1.44] 个卡高**，视口半高只有 0.5 —— **整体越出视口**，静止时就是干净的一张卡，等价于原 Pager 的"页与页平铺"（`PageSize.Fill` + 页间距）。

⚠️ **易错点：不要用"可见性临界 0.5 + scale/2 = 0.94"来追求"不露邻卡"**。这个临界回答的是**另一个问题**——"邻卡是否被中卡遮住"（堆叠语义）：k > 0.94 才露出，k = 0.94 取等号意味着**邻卡几乎完全重叠在中卡后面**，渲染出来是"一坨叠在一起的卡"（相邻中心只隔 0.94 卡高，但卡本身有 1.0 卡高），而**不是**"一张卡 + 后面空着"。两个判据必须分清：
- **"被遮住"**（堆叠）：`k > 0.5 + scale/2`（≈0.94）；
- **"不进视口"**（一次只显示一张）：邻卡区间下界 `k − scale/2 ≥ 0.5` ⇒ `k ≥ 0.94`，取 **k = 1.0** 才有安全余量。

**①' 必须裁剪容器**：竖屏卡与容器等高（`fillContainer`），k = 1.0 时 d = ±1/±2 的邻卡被摆到**容器外一到两倍卡高**处。若容器不裁，这些卡会画到容器外、盖住下方内容（如"为你推荐"）。故给 `HelloCardCoverflow` 的内层 `Box` 加 `Modifier.clipToBounds()`。横屏不受影响：`cardHeightFraction = 0.66` 使邻卡露出量仅 58–93px，本就在容器内。

**③ 竖屏卡纵向内缩 16dp**（用户："卡片不要充满容器，给一个四周的 padding 16.dp"，随后澄清"应该是卡片垂直方向给"）。竖屏调用点 `HelloSlideCardStack` 的 modifier 加 `padding(vertical = 16.dp)` —— **只缩纵向**，横向保持 `fillMaxWidth`（与上方搜索栏同宽，不破坏列对齐）。两个易错点：
- **`padding` 必须在 `aspectRatio` 之前**：若 `aspectRatio` 在前，padding 从已定比例的**两维各减 32**，卡形漂成 1.123（=329×292.9）而非 10:9 的 1.111；`padding` 在前则卡本身严格 10:9（=361×325）。
- **下方原有 `Spacer(16.dp)` 须删掉**：卡的 bottom padding 已经提供 16dp，与既有 Spacer 叠加会变成 32dp、与上方 16dp 不对称。删掉后上下都是 16dp。

**④ 卡与卡的虚拟间距 `cardSpacingDp`**（用户："卡片之间能添加虚拟的间距吗"）。新增 `CardStackTuning.cardSpacingDp`，步长改为 `stepPx = 卡高 × k + cardSpacingDp`。**竖屏取 12dp**（滚动时卡与卡有清晰分隔感）、**横屏取 0**（保持 Coverflow 露出量不变）。为什么可行：间距只是**叠加在步长上的平移量**，竖屏 k = 1.0 时邻卡本就在视口外，加间距只会把它推得更远（"一次只显示一张"更稳）；横屏加间距则是**减小**露出量（900×600 下 0→24dp 令露出 58→34px），是控制 Coverflow 强弱的旋钮。拖拽"跟手"系数 `delta / stepPx` 自动跟随新步长，无需另调。

**⑤ 离开缩小 / 进入放大 `exitScale`**（用户："能不能做一个离开时缩小的效果，进来放大"）。原实现 scale 在 `|d| ≥ 1` 后**饱和在 neighborScale**（0.88），再往外不再缩 —— "离开"没有持续变化。改为**两段连续缩放**：
- 段① `|d| ∈ [0,1]`：`1 → neighborScale`（中心 → 邻卡位，即原有逻辑）；
- 段② `|d| ∈ [1,2]`：`1 → exitScale`（邻卡位 → 更外侧，**新增的"离开继续缩小"**）。

两段相乘，故 `|d| = 1` 处恰为 `neighborScale`、`|d| ≥ 2` 处为 `neighborScale × exitScale`。**横屏 `exitScale = 0.75`**（1 → 0.88 → 0.66，克制以免破坏 Coverflow）。**alpha 只走一段**（到邻卡位即降到 `neighborAlpha` 后不再淡）—— 再往外已基本出画，继续淡无视觉收益、反而让横屏露出的邻卡过透。

**⑥ 竖屏切换效果改回"纯位移 + 淡入淡出"**（用户："目前切换效果似乎在竖屏上不太合适，可以运用其他的效果吗"，裁定"平滑位移+淡入淡出"）。**为什么原来的效果在竖屏不合适**：3D 翻转 + 大幅缩放是**为横屏"叠卡 Coverflow"设计的** —— 在横屏里它表达"两张卡的前后层次"；但竖屏是**单页翻页**语义、卡占满一整屏，把整屏大卡 `rotationX 24°` 翻转、`exitScale 0.55` 缩到一半，观感是"整页缩没了"，**夸张且眩晕**。故竖屏改为 `neighborScale = exitScale = 1f`（不缩）、`neighborRotation = 0f`（不转）、`neighborAlpha = 0f`（d=0 全显 → d≥1 全隐）。卡只做**上下平移**，靠 alpha 完成新旧交替 —— 最接近原生翻页。

> 几何校验：`stepPx = 卡高 + 12dp ≈ 337`，拖动到 `offset = 0.5` 时两张卡区间为 `[-331,-6]` 与 `[+6,+331]`（视口 `[-162,+162]`）—— **上下分离、不重叠**，各占半屏且 alpha ≈ 0.5，中点的交叉淡出自然。

> 经验：**同一个参数在不同"交互语义"下含义不同**。`rotationX`/`scale` 在"堆叠 Coverflow"里是**层次语言**（告诉用户后面还有卡），在"单页翻页"里却成了**夸张的形变**（用户看到的是"整页在翻跟头"）。**复用一个组件时，视觉参数要按语义分组、而不是按组件分组** —— 这正是 `CardStackTuning` 两套预置存在的意义。

**⑦ 斜倚堆叠 `leanNeighbors` —— "中卡不动、邻卡 0.8、角度实现"**（2026-09-22 第七轮，两轮迭代；用户截图："之前上下两个卡片是可以显示完整的"，裁定"保持主视角卡片的大小，上下卡片可以缩放一下，角度调整一下"，看过 0.29 版后改口"**缩小的有点过分了，控制在 0.8 吧，通过角度实现**"）。

**问题**：k = 1.02 时邻卡中心距 456dp，而容器半高仅 339dp —— 邻卡被容器上下边缘横切，只露 106dp（24%）。用户要的是**邻卡不被切、完整可见**。

**几何硬约束**：中卡占容器高 66%（`cardHeightFraction = 0.66`），上下各只剩 **17% 的余量带**（约 115dp）。压小 k 无解（卡高 447dp 时即使 k = 0.8，三卡总高 1163dp 仍是容器的 1.7 倍）。

**第一版（被否）：贴合式步长 `snugNeighbors`，邻卡缩到 0.29**。步长 = `卡高×(1+s)/2`（缩放后邻卡内缘贴中卡外缘），联立外缘约束（`rotationX` 投影 `cos45°`）得 `s ≤ 0.302`，取 0.29 —— 邻卡完整入画但只剩 92dp 高，用户："**缩小的有点过分了**"。

**第二版（现行）：`leanNeighbors` 斜倚堆叠，scale = 0.8 + 绕内缘翻转**。洞察：邻卡不必"居中定位 + 旋转"，可以让它**绕自己的内缘（贴中卡那条边）翻转** —— `transformOrigin` 从 `Center` 移到内缘（上邻卡 `(0.5, 1)`、下邻卡 `(0.5, 0)`），缩放与旋转都绕这条边，**内缘位置被轴钉死**（恰好贴住中卡外缘，步长恒为 1.0 卡高），外缘随倾角向后收。外缘入容器约束：

```
frac × (0.5 + scale × cos(倾角)) ≤ 0.5
⇒ 倾角 ≥ arccos((1/(2·frac) − 0.5) / scale)
  = arccos(0.2576 / 0.8) = 71.2°   → 取 72°
```

`frac=0.66` 不动（**中卡尺寸不变** ✓）、`neighborScale = 0.8`（用户指定 ✓）、`neighborAlpha = 0.65`（斜倚卡是完整视觉层）、`exitScale = 0.8`。600–1080 全窗口校验外缘余 2.3–6.7dp（透视还会把向后收的外缘再拉进来，实际更大）。**过渡形态**：拖动时上/下卡分别从中心线向上/下"展开"——两张卡像书本开合，中点交会淡切。

> 经验：**"位置 + 旋转"放不下的东西，换"轴点 + 旋转"往往放得下**。第一版把邻卡当刚体平移（中心距决定一切），能动的只有 scale；把 `transformOrigin` 钉到内缘后，旋转本身就承担了"收进容器"的职责 —— **变换的参考点也是布局资源**。另一面：轴点选取要服务的恰是"必须不动的那个点"（这里 = 与中卡的贴合边）。
>
> 承 §3.8 第一版教训的回声："邻卡完整可见"与"中卡占 66%"在**中心定位**下不可兼得；轴点变换是第三条路。

**② 竖屏尺寸为什么必须 `fillContainer`**：最初给竖屏也用"按容器高算"（`cardHeightFraction = 0.78`），静态推演发现会产出**畸形卡** —— 393dp 宽的窗口算出卡高 640dp（封顶）、卡宽却只有 361dp（被容器宽截断），比例 1.77 而非 10:9。
根因：**横屏容器宽而矮、竖屏窄而高，瓶颈刚好相反**。
最终回归本质：**原 Pager 版的卡形从来不是算出来的** —— `VerticalPager` 默认 `PageSize.Fill`（占满容器），卡形由外层 `HomeScreen` 的 `aspectRatio(10f/9f)` 决定。故竖屏改为 `fillContainer = true`，卡直接填满，卡形交给调用方的 `aspectRatio` —— **与原实现完全一致**。

**删除**：`RotatingPersistentCards`（Pager 版轮播，已无调用方）。`HelloCardRotator.kt` 仅保留 `FamilyDispatch`（8 卡型分发，仍为横竖屏共用）。全仓核查确认 `heightDriven` / `cardWidthFraction` / `CF_NEIGHBOR_*` / `CF_STEP_FACTOR` 等旧符号**引用数全部为 0**。

**顺带清理**：`HelloCardCoverflow.kt` 移除未使用的 `androidx.compose.ui.unit.min` import；`HelloCardStack.kt` 移除 `Box` / `fillMaxSize`（改用自绘后不再需要）。

> 经验：**"复用"与"统一"是两个不同的目标**。本次真正的收益不是"竖屏也能循环"，而是**渲染实现从 2 份收敛到 1 份** —— 参数化的边界选对了（只抽视觉常数、不抽逻辑），才能做到既统一又不互相牵制。判据：**若两处的差异能用一个 `data class` 表达完，就该参数化；若差异涉及控制流，才考虑分开**。
>
> 经验：**复刻旧观感时，先找旧实现的"事实来源"**。竖屏卡形一开始被我当成"该由新组件算"的问题，绕了一圈才发现它**从来就是外层 `aspectRatio` 决定的**。把定尺寸的责任还给原来那一层，复刻自然成立。

### 3.11 滑动效果与反馈整体优化（2026-09-22）

**触发**：用户"整体优化一下这个组件的滑动效果与反馈"。逐项审计手势链路，发现 **1 个功能缺陷 + 4 项手感缺失**。

**🐛 缺陷（最严重）：未过阈值时卡永久卡在半路**。旧 `onDragEnd` 把全部逻辑包在 `if (|acc| > 70px)` 里 —— 位移不足时**什么都不做**，而 `onVerticalDrag` 已经把 `offset` 改成了小数（如 `2.37`），于是卡就**永久停在两格中间**，既不翻页也不回位。修法：`onDragEnd` **无条件吸附到整数格** —— 过阈值翻一格、未过则回弹到最近整点。另补 `onDragCancel`（父级手势抢占等场景）同样吸附，否则同样卡半路。

**🐛 缺陷：翻页会跳两格**。修好吸附后暴露第二个坑：过阈值时若用 `offset.value.roundToInt() + dir` 算目标，`offset = 1.6` 时 `round → 2`、`+1 → 3`，**一次跳两格**。修法：在 `onDragStart` 记下**起点格** `startIndex`，`onDragEnd` 一律用 `startIndex + dir`。

**其余四项优化**：

| 项 | 旧 | 新 |
|---|---|---|
| **甩动翻页** | 只看位移（须拖满 70px） | 位移过阈值 **或** 速度超 `1.2px/ms` 即翻页（轻快一划也生效） |
| **落定动画** | `spring(0.85, 380)` 偏硬 | 统一 `settleSpec = spring(0.8, 420)`，略欠阻尼有"吸住"重量感 |
| **触觉反馈** | 无 | 拖拽起 `performDragStart()`、落定 `performGestureEnd()`（走既有 `rememberHapticFeedback()`） |
| **轮播抢焦** | 拖动时轮播动画仍在跑；且拖完 5s 锁一解除立刻自动翻页 | 拖拽起 `offset.stop()` 打断动画；拖拽同时重置 `lastAutoRotateAt`，锁解除后重新计满 4s |

**速度估计**：无官方 velocity 接口（`detectVerticalDragGestures` 只给 `dragAmount`），故用**相邻事件 `delta / Δt` 指数平滑**（`0.7×旧 + 0.3×新`），并忽略 `Δt > 100ms` 的间隔（停顿后的首个 delta 不代表速度）。

> 经验：**"没出事"的分支往往就是缺陷所在**。这个卡半路的 bug 藏了很久 —— 因为默认用法（拖满再松手）永远走"过阈值"分支，只有"轻轻一推又缩回"才会踩中。**审手势代码时，务必把每个 `if` 的 `else` 当作一等公民审一遍**：`else` 里若只是"什么都不做"，而此前已有状态写入，基本就是 bug。
>
> 经验：**修完一个坑要警惕它带出的下一个**。`startIndex` 这个坑正是"无条件吸附"修好后才暴露的 —— 因为旧代码在过阈值分支里 `round` 后再 `+1`，只在连续拖动时才会跳格。**改动改变了哪条路径的执行频率，就要重审那条路径**。

### 3.12 T1 页面横屏布局优化（2026-09-22，分页定制）

**触发**：用户"对于 F14-T1 中改造的页面要在横屏下做组件布局的优化做双栏或整体布局的优化，像首页这样"。此前 T1 除 `HomeScreen` 外，其余五页横屏适配**一律是「限宽居中」**（`widthIn(max=) + Box(TopCenter)`），实测 1104×680 窗口下**浪费 38–42% 宽度**（Chat/Audit 640、AI/Config 600，各留 400–440dp 空地）。

**可行性评估（逐页内容体量）**：

| 页面 | 限宽 | 分区数 | 双栏结论 |
|---|---|---|---|
| `AIScreen` | 600 | 4 | ✅ 双栏收益高（左 2 段 / 右 2 段，均衡） |
| `AgentConfigScreen` | 600 | 7 | ✅ 双栏收益最高（左 5 段短表单 / 右 Prompt 编辑器） |
| `AuditLogScreen` | 640 | 2 | ⚠️ 内容偏少 → 改「筛选 rail + 列表填满」 |
| `ChatScreen` | 640 | 1 | ⚠️ 对话本质单栏 → 抬高限宽至 840（不铺满，避免行长过长） |
| `AgentMonitorScreen` | 1080 | 2 | ⚠️ 网格已三列 → 仅补手机横屏（Medium 档落 3 列） |

**分页定制方案（用户裁定）**：不做统一改造，逐页按内容形态定制。

**① `AgentConfigScreen` 横屏双栏**（`agent/config/AgentConfigScreen.kt`）

- `if (isLandscape) Row { 左栏 weight(0.85) ; 右栏 weight(1.15) } else <原单栏>`；
- 左栏 = ① 身份 ② 模型语言 ③ AI 端点 ④ 权限信任 ⑤ 专属参数；右栏 = ⑥ System Prompt 编辑器（`weight(1f)` 内滚）+ ⑦ 底部操作固定在右栏底部。
- 抽出两个**无状态** Composable 复用卡片：`ConfigFormLeftColumn`（左栏 5 段）、`SystemPromptSection`（单/多卡两套 prompt 编辑器）。单栏分支保持原内联代码不动 → **Compact 零 diff**。
- 右侧 Prompt 编辑器（`SystemPromptSection`）的 `onRestoreFactoryPrompt`/`onDiscardPromptChanges` 两个回调把 `promptDirty` 的置位/清除收回调用方，修正原内联版"放弃改动"只能改文本、不能复位脏标记的边界。
- `wideRowMaxWidth`（原 720dp 宽行）在双栏下失效 → 改为 `isWide && !isLandscape` 才生效；双栏下 Prompt 编辑器宽度 = 栏宽。

**② `AIScreen` 横屏双栏**（`agent/config/AIScreen.kt`）

- `if (isLandscape) Row { 左栏 weight(1f) ; 右栏 weight(1f) } else <原单栏>`；
- 左栏 = 分区 1（AI 接入方式）+ 分区 3（语言和语音）；右栏 = 分区 2（Agent 管理）+ 分区 4（记忆管理）。两栏各自 `verticalScroll`。分页结构（`SectionHeader` + 各 Section）原样搬运，无状态重构。

**③ `AuditLogScreen` 横屏「筛选 rail + 列表」**（`agent/monitor/AuditLogScreen.kt`）

- 内容仅「筛选 + 列表」两段，撑不起双栏表单；改为左 `FilterRail`（竖排筛选 chip，160dp）+ 右列表 `weight(1f)` 吃满剩余宽度。列表行内含哈希/ID，宽一点更易读，恰好消化此前的居中留白。
- 抽出 `FilterRail`（竖向 chip 列）与 `FilterRow`（横向，竖屏用）**同一选中判据**，仅排布方向不同。

**④ `ChatScreen` 横屏抬高限宽**（`agent/chat/ChatScreen.kt`）

- 对话本质单栏，强行双栏无意义；`maxContentWidth` 在横屏取 **840dp**（而非铺满）—— 既消化限宽留白，又不让气泡行长失控。竖屏/Compact 保持 `Dp.Unspecified`。

**⑤ `AgentMonitorScreen` 补手机横屏**（`agent/monitor/AgentMonitorScreen.kt`）

- 原判据只看 `isExpanded`（≥840dp），手机横屏（约 812×375，宽 812 < 840 → **Medium**）落两列且不限宽 → 卡片被横向拉长。判据改为 `isExpanded || isLandscape`：横屏一律三列 + 限宽 1080dp。

**统一约束**：五个文件全部 `if (isLandscape) <双栏/定制> else <原代码>`,**单栏/Compact 分支逐字节保留**，确保"手机竖屏是基线，回归零 diff"（§4 验收条件第 2 条）。

> 经验：**"限宽居中"是宽窗的兜底，不是终点**。它解决了"行长过长"，但把宽度全变成两侧留白 —— 当页面有多个可并排的分区时，双栏才是正解。判据：**分区能否自然配成左右两组**（Config 5+2、AI 2+2 可，Chat 单栏不可）。

> 经验：**限宽值应由内容形态决定，不是一个 600/640 打天下**。表单 600dp（单行输入不宜更宽）、Prompt 编辑器 720dp（多行能吃宽）、对话 840dp（气泡需要呼吸），三者诉求不同。
