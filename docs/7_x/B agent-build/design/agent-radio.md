### 0. 一句话职责

**电台开启期间，持续收集用户的播放行为，只用「调整当前之后的播放队列」这一种方式，静默地把听感调准。**

由此推出的三条硬边界 —— 它们既是设计约束，也是这个 agent 的全部存在理由：

- **输入只有播放行为**：不看别的、不问用户、不依赖对话。
- **输出只有队列调整**：不发言、不碰播放控制、不改用户数据。
- **默认沉默**：没有观测输入就不动作；判不准也不动作。

##### 明确不做

| 不做 | 原因 |
| --- | --- |
| 说话 / 衔接语 / 报幕 / 主动提示 | 「静默调整」——DJ 的嗓音不是本期交付物 |
| 暂停、切歌、调音量、改进度 | 播放控制权归用户 |
| 加歌单、改标签、收藏、删歌 | 只写自己的会话状态，不碰用户数据 |
| 没有观测输入时「自我发挥」 | 无信号即无动作 |

### 1. 会话生命周期

```
点开（首页收音机卡 / 对话「来点电台」）
   │  ① 秒开：本地保底队列先出声（不等模型）
   ▼
运行中 ── 持续收集播放行为 ──▶ 静默调整队列（追加 / 替换当前之后）
   │
   ▼
关闭（用户关闭 / 明确「停电台」）
   └─ 播放停止 + 会话状态清空；不做告别、不做收尾动作
```

- **一次会话 = 点开到关闭。** 开启动作本身必须立刻出声 —— 秒开是硬承诺，模型决策可以慢。
- **关闭是幂等终态。** 关闭后不得再有任何队列动作，在途判断直接丢弃。
- **关闭只暂停，不清空播放列表**（2026-09-13 修正）：曾经多发一条 `SKIP_ALL`，
  会把用户（或电台）刚排好的队列一并清掉。关闭电台 ≠ 清空播放列表。

### 1.1 暂停状态机（用户从播放器操作时）

电台必须能感知**用户在播放器里（通知栏 / 耳机 / 播放页）**的操作，而不只是电台开关：

| 当前状态 | 用户动作 | 电台行为 |
| --- | --- | --- |
| 电台运行中 | 在播放器里**暂停** | 电台同步进入 `PAUSED`，**对话保留** |
| 电台启动中（`BUILDING`，如在等模型返回队列） | 在播放器里**暂停** | 在途模型结果**作废**（generation +1），收口后状态落 `PAUSED` 而不是 `PLAYING` |
| 电台已暂停 | 通过**电台开关**恢复 | 恢复电台（`resumeRadio`），接着上次 |
| 电台已暂停 | 在播放器里直接**播放** | **电台跟着恢复**（`resumeRadio` → `PLAYING`），会话保留 —— 2026-09-19 修订：**不再"用户接管退出"** |
| 电台运行/暂停 | 上一曲 / 下一曲 | 只累计观测（`trackChangeEvents`）、刷新门面，**不退出**（2026-09-19 明确） |

实现要点：
- 驱动信号是观测面的 `PauseEvent`（覆盖所有来源），不是 `trackChangeEvents`
- **暂停必须去抖**：切歌（下一曲/上一曲/`PLAY_BY_ID`）会让播放器先停旧曲再起新曲，
  发出一对 `pause → resumed` 瞬时事件（真机实测间隔约 100ms）。见事件就信会
  误把切歌过渡当"用户暂停"。
  因此 `!resumed` 只挂起核查，等 `PAUSE_DEBOUNCE_MS`（800ms）后**问播放器是否真在暂停**，
  真停着才切 `PAUSED`；窗口内来了 resumed 一律取消、当无事发生
- 电台自己下发的 `PLAY` / `PAUSE` **必须先静默观测**（`muteFor`），避免把自己的操作当成用户行为
- ~~「用户接管」走 `stopRadioInternal(pausePlayback = false)`~~ —— **已废除（2026-09-19）**：
  用户的播放 / 暂停 / 上一曲 / 下一曲**一律不退出电台**；电台只是跟着反映状态（暂停→`PAUSED`、播放→`PLAYING`）。
  会话终态**只有手动关闭**（电台开关 / 明确说"停电台"），与 **C3** 对齐
- `BUILDING` 期间的暂停走 `pausedDuringBuilding` 标志：generation 已 +1 使在途结果过期，
  收口时状态落 `PAUSED`；期间用户又点了播放则清除标志（照常收口为 `PLAYING`）
- **外部控制面（电台卡）不区分停止与暂停**（2026-09-19）：卡片只有「开 / 关」两态 ——
  已开启（`PLAYING`/`PAUSED`/`BUILDING`）时点击 = 关闭（`stopRadio`）、空闲时 = 开启
  （`startRadio` 内置 `tryResumeRetained` 自动判断续档 / 新开）。内部的 `PAUSED`
  仍保留（由"跟随播放器暂停"产生、可后续恢复），只是**不由卡片暴露**。看板 `AgentMonitorScreen`
  保留显式暂停/恢复/停止（调试面）

### 2. 观测面契约（第 1 步要落地的东西）

### 2.1 必须能观测到的事实

| 事实 | 记录内容 | 现状（2026-09-13 复查） |
| --- | --- | --- |
| 开始播放某首 | 曲目 | 端口有（`trackChangeEvents`），但**只走 agent 命令路径** |
| **听完**（自然播完） | 曲目 | **Android 已结算**（`MusicController.onPlaybackEnded` → `endCurrentPlaybackSession(isCompleted=true)`），只写库、未 emit |
| **跳过 + 已播时长** | 曲目 + 已播 ms / 总时长 ms | **Android 已结算**（`endCurrentPlaybackSession(isCompleted=false)` → `skipPlaybackSession(..., duration, ...)`），只写库、未 emit |
| **大幅前跳**（同一首内 seek） | 曲目 + 跳到位置 | 缺（可后补，非本期必要） |
| **重复播放** | 曲目 + 次数 | 缺（可从播放历史聚合，非实时） |
| **暂停 / 继续** | 时刻 | 缺（Android 有 `pauseMusic` / `playOrResume` 两个入口，加 emit 即可） |
| 队列剩余 | 剩余数 | 本地可粗估 |

**结论：观测面不是从零埋点，而是把已有的结算结果接出一条事件流。** 这推翻了初版「三端埋点是大工程」的估计。

### 2.1.1 已查明的既有资产

- **数据库已有完整事实**：`shared/.../data/database/PlaybackHistory.kt`
  → `PlaybackHistory(musicId, playedAt, playDuration, isCompleted, source)`，每首歌的结算都落库，**已含播放时长与是否播完**。
- **Android 端已有结算点**：`android/core-player/.../controller/MusicController.kt`
  - `onPlaybackEnded()`（服务回调）→ 自然播完 → `completePlaybackSession(...)`
  - `playNext()` / `playPrevious()` / `playAt()` / `playWith()` → `endCurrentPlaybackSession(isCompleted = false)` → `skipPlaybackSession(historyId, musicId, duration, true)`
  - 已有 `totalPlayedDurationInSession`（累计实际播放时长，暂停已扣除）、`playStartTime`
- **现有端口是残的**：`PlaybackCommandPort.skipEvents: Flow<String>` **只给曲名、不给进度**，且仅在
  `source == CommandSource.USER` 且命令经端口下发时 emit —— UI 直连控制器、通知栏、耳机按键的路径全都不在内。
- `android/core-player` 依赖 `:shared`（`build.gradle.kts: implementation(project(":shared"))`），
  所以观测接口可以定义在 `shared/commonMain`，由三端控制器各自 emit。

### 2.2 三条实现要求

1. **埋点下沉到三端播放控制器**，而不是只改 shared-ui 的 `PlaybackViewModel` —— 播放页是直连控制器的，只改 ViewModel 仍然是瞎的。**Android 落点即 `MusicController` 的会话结算点。**
2. **跳过必须带播放进度。** 这是本契约唯一的精度硬要求：没有进度就分不清「刚开就跳」（强负反馈）和「快听完才换」（几乎不算负反馈），后面的判断会系统性失准。
   —— 幸好 `MusicController` 早就拿到了这个数（`totalPlayedDurationInSession`），只是没往外传。
3. **记录只记事实。** 记「跳过 + 已播 12%」，不记「不喜欢」—— 极性 / 强度是判断，不是观测。
   ⚠️ 注意 `MusicController` 里已有 `skipThresholdMs = 20s` / `skipThresholdPercent = 15%` 两个阈值，
   那是**给播放历史统计用的**，本契约不得复用 —— 判断权在模型，观测层只交原始数字。

### 2.3 边界

系统状态（在播曲目、队列内容与剩余、当前主题）**不属于用户行为**，不进记录；它们是判断时附加的上下文。

### 2.4 Android 单端最小事件集（第 2 步的交付物）

在 `shared/commonMain` 定义观测端口，Android 由 `MusicController` 在会话结算点 emit。
**事件只有一条** —— 一首歌结束时结算一次，覆盖「听完」和「跳过」两种结局：

```
TrackSettled(
  musicId: Long,
  title: String,
  outcome: COMPLETED | SKIPPED_NEXT | SKIPPED_PREV | SWITCHED_AWAY | STOPPED,
  playedMs: Long,      // 实际播放时长（暂停已扣除）
  totalMs: Long,       // 曲目总时长
  atMs: Long,          // 单调时钟
)
```

外加两条低频事件（缺了会让「暂停后回来换歌」被误判，见 S5 反例）：

```
Paused(atMs) / Resumed(atMs)
```

**设计取舍**：不区分「谁触发的」（用户 / 系统 / agent）—— 结算点只知道结果，
追溯触发源要在三端各插一处，成本高且易漏。agent 自己的动作它自己知道，可以在记录时自行标注。

**不做的**：大幅前跳（seek）、重复播放。前者需要额外的位置突变检测，后者可从播放历史聚合；
两者都不是 S1-S7 任一剧本的必要条件，等真需要时再加。

### 3. 行动面契约

### 3.1 允许（只有这两件）

| 动作 | 语义 |
| --- | --- |
| **追加**（Refill） | 在队列末尾追加同风格曲目 —— 不替换、不打断 |
| **替换当前之后**（Reroute） | 只**移除当前播放曲之后的条目**并追加新的；当前曲及其之前的一切都不碰（见 §3.4） |

### 3.2 禁止

- 打断 / 跳过正在播放的那首
- 任何形式的**主动发言**：模型生成的衔接语、报幕、解释、寒暄
- **打扰式呈现**：toast / snackbar / 弹窗 / 聊天区插话 —— 不点进来也会撞到眼睛的都算
- 触碰播放控制（暂停 / 音量 / 进度 / 下一首）
- 修改用户数据（歌单 / 标签 / 收藏）

### 3.3 存在面：RadioCard（C1 决议）

「静默」约束的是**打扰与文案**，不是**不存在**。agent 的存在感有两个出口（2026-09-19 增补第二处）：

| 存在面 | 位置 | 性质 |
| --- | --- | --- |
| **`RadioCard`**（主） | 首页/资料库（`shared-ui/.../library/pages/components/RadioCard.kt`） | 常驻状态面，含全部状态与主播编排思路；用户不翻到那一页就看不到 |
| **伙伴胶囊电台态**（次，2026-09-19 新增） | 底栏常驻胶囊（`common/components/CompanionCapsule.kt`） | **只在电台开启期间**出现的状态位：图标换成 `radiowaves` 并恒定高亮；长按 = **唤起电台控制台**（关闭动作移入面板内确认，见下） |
| **电台控制台**（第三处，2026-09-19 设计待拍板） | 长按胶囊唤起的全屏面板（`agent-radio-console.md`） | **用户主动唤出**的详情面：节目单（每首带按语）+ 主播思路 + 「结束这一档」。不主动出现 → 不算打扰 |

**第三处：电台控制台**（2026-09-19 设计，见 [`agent-radio-console.md`](agent-radio-console.md)）——
长按胶囊唤起的**全屏详情面**：节目单（每首带主播按语）+ 主播思路 + 「结束这一档」。
它是**用户主动唤出**的（不主动出现），因此性质是"详情面"而非"存在面"，不算打扰；
但它把"手动关闭"从胶囊上的一个长按，改成了"看清这一档之后再收档"。

**第二处存在面的合规理由**：它不显示任何**文案**（只有一枚图标 + 高亮），不新增打扰（胶囊本就常驻），
且关掉电台即刻回落到常态 —— 属 C1 允许的"结构化状态"，不是"模型生成的呈现"。
它解决的是一个**可达性**问题：胶囊是"找伙伴=看左下角"的主锚点，电台运行期间用户不该为了停掉它而先翻到资料库那页。
（总纲 §5.2.1 原规划该位放「电台运行」徽标圆点。**徽标圆点方案已于 2026-09-19 整体废弃**——
它从未接线：事件发过、胶囊从未渲染。故电台态改为**整枚图标替换**；圆点在 24dp 图标旁既不明显，
又有语义打架的问题。**不要再按"圆点"思路设计胶囊状态**。）

| 允许显示 | 不允许显示 |
| --- | --- |
| 状态（启动中 / 运行中 / 已暂停） | 寒暄、询问、建议、需要用户回应的内容 |
| 「自动续歌中 · 共 N 首备选」 | 多句话的解说 / 电台台本式文案 |
| 「下首：xxx」 | toast / snackbar / 弹窗 |
| **主播的编排思路**（`reason` 一句，2026-09-13 决议：C1 放松动出口） | |

判据（2026-09-13 更新）：`reason` 是结构化 JSON 里可枚举的字段之一，上卡片 = 把该字段渲染进 `lastAdjust` 槽位（单句、截断、随卡片静态展示）= 合规；
把模型返回值**自由拼接**成面向用户的句子 = 破戒。判断阶段的输出仍必须是可枚举的结构。

### 3.4 队列调整必须是**增量**的，不能重建（2026-09-13 真机修正）

`REPLACE_QUEUE` 早期实现是 `clearPlaylist()` + 重建 + `playAt` + `seekTo` 去"恢复"当前曲。
这条路**必然打断**：清空那一刻播放就断了，之后无论怎么补偿都会顿一下。

正确做法是**只操作尾部**：

```
移除 currentIndex+1 之后的条目 → 追加新列表（过滤掉当前曲避免重复）
```

当前曲及其之前的条目完全不碰，播放与 position 天然不受影响，
也就不再需要 `playAt` / `seekTo` 去补救。

> 踩过的坑：实现里曾用「当前曲在不在新列表里」来决定是否保留它。
> 而我们在 §7.0 会主动把当前曲从列表里剔除，于是判定恒为 false → 必然走「切到新列表第一首」。
> **用「在不在列表里」当保留信号是脆弱的** —— 保留应当是实现无条件的，与调用方传什么无关。

### 4. 验收剧本（裁判）

| # | 场景 | 期望 | 反例（判错的形态） |
| --- | --- | --- | --- |
| S1 | 点开电台 | 1 秒内出声，队列已有后续曲目 | 先转圈等模型返回 |
| S2 | 连跳 3 首（每首只播了十几秒） | 换一批，风格明显不同；**在播那首不被打断** | 只微调顺序；或把正在播的也切掉 |
| S3 | 连听 5 首、全程不操作 | **队列一动不动** | 主动换批「求表现」 |
| S4 | 队列剩 ≤2 首，用户一直在听 | 静默补上同风格曲目，播放不中断 | 播完了才补（出现空档） |
| S5 | 听满 90% 才换下一首 | **不判为负反馈**，不换批 | 只看「跳过次数」就换批 |
| S6 | 用户关闭电台 | 播放停止、会话清空、之后无任何动作 | 关闭后仍在途调整队列 |
| S7 | 连跳 3 首触发换批 | 队列变化只体现为「下首」和「备选数」变了；无 toast、无弹窗、聊天区无内容 | 弹出「已为你换一批」提示；或把模型的原话显示出来 |

S2 / S3 / S5 是本期的核心分歧点：**同样的操作序列，只有带上播放进度才判得对。**
S7 是 C1 的裁判：**模型的输出永远不直接触达用户。**

### 6. 决议（C1-C5 已拍板 · 2026-09-13）

| # | 议题 | 决议 | 理由 |
| --- | --- | --- | --- |
| **C1** | 静默到什么程度 | **存在感走 RadioCard（主）+ 伙伴胶囊电台态（次，2026-09-19 增补）**：只显示结构化状态（状态 / 备选数 / 下首 / 队列已调整的固定标记）；禁止模型生成文案与一切打扰式呈现（toast / 弹窗 / 聊天插话） | 契约禁的是打扰与文案，不是不存在。RadioCard 常驻、不点进那页就看不到，代价为零。胶囊电台态只有一枚图标 + 高亮、零文案、零新增打扰，且解决"停电台要翻页"的可达性问题（详见 §3.3） |
| **C2** | 跨会话记忆 | **只做会话内**。关闭即清空，不写长期偏好 | 跨会话意味着衰减 + 冲突消解，正是刚删掉的那类机制；且没有验收剧本能证伪它 |

### 7. 决策内核（第 3 步形态）

### 7.0.0 开播前先看「现在有没有在播」

`startRadio` 分三条路，优先级从高到低：

| 情况 | 走哪条 | 关键行为 |
| --- | --- | --- |
| 命中复用条件（见 §7.1） | 复用 | 续上对话，跳过一切组装 |
| **有当前曲目**（在播**或暂停**） | `startAfterCurrent` | **当前这首继续放**，队列只接在它之后；种子默认取它的标签 |
| 什么都没在播 | 完整 Start | 本地队列起播（唯一一次改变播放状态）→ 模型定队列 |

第二条最容易做错：曾经不管有没有在播都先 `PLAY_BY_ID` 本地第一首，
**会把用户正在听的歌顶掉**。有声音时秒开承诺本来就满足，不需要抢播放器。

但「有当前曲目」≠「正在出声」：关闭电台只暂停了播放，这时重开若没命中复用
（换了主题 / 超窗口 / 队列被换过），就会以暂停的当前曲为起点 ——
**必须补一次 `PLAY` 起声**（AGENT_INTERNAL，恢复当前曲、不切歌），
否则电台"开着"却没有声音。

种子优先级（`extractSeedLabels`）：
① 用户通过对话指定的类型 → ② 当前在播曲目的标签 → ③ 曲库高频标签。

### 7.0 Start：秒开 + 模型定队列（D4）

**这是会话的第一轮**，也是**唯一一次允许改变当前播放状态**的地方。

```
① 本地算法生成队列（targetCount = 12）
② 推入播放引擎并开始播放        ← 唯一一次改变播放状态，秒开是硬承诺
③ 注入上下文：人格 + 曲库视图 + 开启情境 + 本地生成的队列
④ 模型返回最优队列（musicId 列表）
⑤ 替换「当前播放曲之后」的队列；在播那首必须放完
```

- **失败即保持**：模型失败 / 无端点 / 解析失败 → 保持①的本地队列（已在播，不中断）。**不需要兜底逻辑**。
- **输出必须是 `musicId` 列表，不是曲名** —— 曲名会幻觉、会写错字、会重名；`musicId` 可逐条校验，校验不过的丢弃。
- **收口**：去重 → 剔除在播那首 → 截断到 `targetCount` → 不足则用本地队列补齐。

### 7.0.1 注入的「开启情境」（按现有能力反推，不是拍脑袋）

| 情境 | 来源 | 状态 |
| --- | --- | --- |
| 触发来源（首页卡 / 对话） | `RadioTrigger` | 已有 |
| 用户给的种子（「来点蓝调」） | `startRadio(seed)` | 已有 |
| 开启前在播的曲目 + 其标签 | `PlaybackController.currentPlayingMusic` / `currentMusicLabels` | 已有 |
| 曲库总量、标签体系、Top 标签、艺术家分布 | `getMusicCount()` / `getLabelNamesByType()` / `getAllArtistsSummary()` | 已有 |
| 本地算法生成的队列 | `buildLocalFallback()` | 已有 |

| ~~最近播放记录~~ | `getRecentPlaybackHistoryGlobal()` 有，但与 C2「只做会话内」冲突 | **不使用** |

### 7.0.2 曲库视图：按预算自适应，不写死档位（D5）

曲库规模不可预知，因此**不设"多少首以上就怎样"的硬阈值**，改用一个 **token 预算** 连续降级：

```
B = 曲目列表的 token 预算；每首约 30 token → 可容纳 N = B / 30
```

| 策略 | 触发条件 | 做法 |
| --- | --- | --- |
| `FullLibrary` | 库 ≤ N | 全量注入 |
| `LabelFiltered` | 库 > N | 用本地标签粗过滤到 N 首（`getLabelNamesByType` + `getMusicIdListByType`） |
| `TwoPass` | 大到连标签过滤都筛不出有意义候选 | 第一轮只给库概况 → 模型定方向 → 本地按方向筛 → 第二轮挑 |

- **策略由代码按预算选，不由模型选** —— 筛选是本地算法的事，模型只看到"一份候选清单"。
- `LabelFiltered` 的过滤优先级：① 本地队列同标签 ② 种子命中的标签 ③ 高频标签 Top ④ 随机补齐保证多样性。
- **强制包含**：本地算法生成的 12 首 + 在播曲目 + 种子直接命中的曲目，无论过滤结果如何都必须在候选内
  —— 否则本地认为最好的那些可能被启发式筛掉。
- 提示模型时如实说明：「以下 N 首是从 M 首中按标签筛出的候选」，不说假话。

### 7.1 一次电台 = 一段对话（D1）…但关闭不等于立刻丢弃

**会话即对话**：点开电台 = 开一段 `messages`，模型在对话过程中记得住自己说过什么。

**关闭只是暂停**（§1 已改：不清播放列表），因此对话往往仍然有效 —— 队列没变、情境没变。
于是关闭时**不立刻丢弃**，而是把快照留在内存里，下次开电台时判断要不要续上。

**判断方向（2026-09-13 重设计）：复用是默认，重启才需要理由。**
时长是"情境可能变了"的劣质代理，而情境本身可观测 —— 所以不再用 30 分钟死窗口：

| 断裂信号（出现任一 → 新开一档） | 判断方式 | 理由 |
| --- | --- | --- |
| 无保留的对话 | 内存快照为空 | — |
| **情境换代**：时段（DayPart）或日期与开播时不同 | `WallClock`（快照记开播时段） | 昨晚的夜场节目，今早重开是另一场；"暂停去吃饭 40 分钟回来"则时段没变 → 仍续上 |
| **主题没换**（本次 seed 为空，或与快照记录的 seed 相同） | seed 比对 | 用户说"来点爵士"而上一档是摇滚 → 是新的一档 |
| 播放器当前曲目仍在当时那份队列里 | 快照问播放器 | 曲目被换成别的东西时，"续上"的对话跟眼前的音乐对不上 |
| **播放队列本身没被改动** | 队列指纹 —— **只比在播曲之后的尾巴** | 光看当前曲目不够：用户可能换了歌单，而新歌单里恰好也有那首歌。⚠️ 播放器队列是**稠密**的（`replaceQueueWith` 保留已播前缀），而电台镜像是压缩的 `[在播, ...后续]`，**整体比对会因前缀长度不同而永远不等** → 必须比尾巴（真机 2026-09-19 修复） |
| 兜底：距关闭超过 `REUSE_BACKSTOP_MS`（12 小时） | 单调时钟 | 时间只兜底，不再主判 |

即：**环境连续 → 默认续上；出现断裂证据 → 开新对话。**

**复用时省掉什么**：本地队列重建 + **曲库视图注入** + 模型定开播队列 —— 这一整段是流程里最贵的组装。
省掉它正是复用最大的收益：重开即续听，不用等模型。

**快照必须带"档案"，不只是 `messages`（2026-09-19 修订）**：
`messages` 只承载**原始对话历史**；而每轮 prompt 里的「节目档案（已执行 / 编排思路）」与
「本档收听台账」是**从会话状态重渲染**的。因此快照由两部分组成（`RadioConversation`）：

| 部分 | 内容 | 不带会怎样 |
| --- | --- | --- |
| `messages` | 原始对话历史（模型最近几轮的判定与理由） | 对话质感断层 |
| `archive`（`RadioSessionArchive`） | `executed` / `intents` / `settled` / `pauses` / `originMs` / 三个计数 | **`## 节目档案` 与台账空空如也 → 模型"失忆"**（真机 2026-09-19："继续对话上下文不保留"） |

`originMs` / `turnIndex` 也要一起恢复：台账里的「第 N 分钟」以**本档开播时刻**为原点、
TURN# 接着数 —— 重置会让跨档后的时间线看起来像新开的节目。

**边界**：快照**仅存于内存，从不落盘**，且超窗口即作废。
这是「延迟丢弃」而不是长期记忆，因此不违反 C2（只做会话内、不写长期偏好）。

> ⚠️ **「从不落盘」是已决边界，不是待补的缺口（2026-09-19 复核）**：
> 曾考虑"最小集落盘"以兜住进程被杀，**已裁定否决**（`agent-lifecycle.md` §5）。
> 关键理由：项目已有**唯一**的跨会话记忆载体 `UserMemory`（可审计、过闸门、写 `agent_audit_log`），
> 电台再落一份档案 = **第二条不可审计的记忆通路**；且电台状态多为**情境**（队列构成 / 在播曲 / 台账），
> 过期后反而污染推理。**跨会话的"用户是谁"该走 `UserMemory`，不该由电台自己记事。**
> 因此：**进程被杀 = 电台丢，属已接受行为**。

**会话即对话**：点开电台 = 开一段对话，关闭 = 整段对话丢弃（与 C2「只做会话内」一致）。
判断调用复用同一段 `messages`，模型在对话过程中记得住自己说过什么、做过什么。

承载方式（`LlmCallExecutor.call(messages: List<LlmMessage>, tools = null, temperature)`）：

```
messages = [system] + [轮次1 user / assistant] + [轮次2 …] + [本轮 user]
```

- **system**：主播人格 + 规约，常驻（见 §7.2）
- **user（第 1 轮 = 开播）**：完整情境（时刻 / 触发 / 用户原话 / 本地标签）+ **正在播曲目（电台起点，单独点名）** + 本地保底队列（不含在播首）+ 曲库视图。接播与从零起播两条路径统一渲染，在播锚点必须来自 `NowPlayingContext`，不得由本地队列第一首冒充（真机 22:57 事故：锚点认错 → reason 承接了一首不会响的歌）
- **user（第 N 轮）**：**全量收听台账（开播以来累计，★ 标本轮新增）** + 节目档案重渲染 + 曲库候选池 + 实时快照（§7.2）。事实一条一行成本可忽略，全量携带让模型拥有整档行为画像（连跳模式/听完的歌不因历史裁剪失忆）
- **assistant**：编排结果（三选一 JSON + reason），**留在历史里** —— 开播那轮不再用完即弃

**裁剪**：历史超过 K 轮只留最近 K 轮（K=4，台账每轮全量重发所以裁历史不失事实，
收窄窗口省下的是历史里重复的候选池块）；被裁掉的轮次，其意图由
**节目档案（ledger）** 承载（见 §7.2）。

### 7.2 上下文管理机制：一个主播主持一场节目（2026-09-13 重设计）

核心理念：**从「一次选曲调用 + 无状态判定内核」改为「一个主播从头到尾主持一场节目」**。
一段对话贯到底，开播是第 1 轮，不再是两段互不相识的对话。

**固定 system prompt（主播人格，一旦定稿基本不动）：**

```
你是这个音乐电台的主播。从听众点开电台那一刻起，这一场节目由你负责：
感知他的每一个操作和播放器里的动静，把播放列表编排出让他愿意一直听下去的样子。

你掌控的唯一资源：当前正在播放那首之后的队列。
你不可触碰的：正在播放的那首（必须放完）；播放器的播放/暂停不归你管。

你的动作只有三种：
- none    ：不动。主播的默认姿态——节目正在流动，没有充分理由不打断编排。
- append  ：往队列末尾续歌（节目按原方向走，只是加长）。
- replace ：整体替换当前曲之后的队列（承认这一段不对味，换个段落）。

分寸感（你自己的直播经验）：
- 刚起播就被切走是明确的负反馈；快听完才换是自然流动
- 连切好几首，说明你编排的这一段不对味——该换了，换就换彻底
- 暂停/继续是生活噪音，不是表态；别因为几次暂停就推翻编排
- 队列见底前主动续上，不让电台冷场

你不会跟听众说话，不生成任何面向用户的文案。只输出 JSON：
{"action":"none|append|replace","musicIds":[...],"count":0,"reason":"…","whys":["…","…"]}
whys 与 musicIds 一一对应：每首歌一句写给听众的主播按语（≤16 字），是电台卡片「按语」位的唯一来源。
reason 是写给节目档案的编排思路——你之后每一轮都会看到它，用它记住"我为什么这么排"；它是工作记忆，不上 UI。
```

**每轮 user 消息的四个块：**

| 块 | 内容 | 与旧版的关键差异 |
| --- | --- | --- |
| 收听台账 | 开播以来全量事实 + 暂停（★ 标本轮新增；瞬时暂停已被观测面去抖过滤） | 暂停不再带切歌过渡噪声（P3 修复） |
| **节目档案（ledger）** | 主题/种子 · 当前队列构成（id+标题）· 本档已执行动作 · 历次编排 reason —— **每轮重渲染** | 新增。对抗裁剪：历史只保对话质感，认知沉在档案里 |
| 曲库候选池 | 按主题/队列标签动态给 Top N 的 id+标题（token 预算内，复用 `buildLibraryView` 过滤） | 旧版 turn 不给任何 id 来源 → 幻觉 id（P1 根因消除） |
| 实时快照 | 在播曲目、队列剩余、后续几首标题（每轮 suspend 问播放器） | 同旧版，播放器是权威 |

**实现层面的三个落点：**

1. `selectOpeningQueue` 的 messages 与模型回复不再丢弃 → 直接作为 `RadioSession` 的起始历史
   （`resumeFrom` 已有入口）；turn 从第 2 轮开始
2. `reason` 写入档案（`noteExecuted` 旁边加 `noteIntent`），并上 RadioCard `lastAdjust`（§3.3 决议）
3. **每轮提问时快照 generation**（不再开播时快照一次）—— 只有"该轮在途期间被暂停/关闭"才丢结果（P0 修复）

### 7.3 触发（只有两条，D3）

| 触发 | 说明 |
| --- | --- |
| **`TrackSettled` 到达** | 一首歌一个结局，间隔几十秒，频率本就很低。留 **2-3 秒合并窗口** 捕获连跳 —— 这是"等一下看是不是连跳"，不是"攒够 N 条" |
| **队列见底（≤N 首）** | "何时值得看一眼"，不是判定。见 §7.5 |

已删除的发明：`batchMinOps`（攒够 N 条）、`quietMs`、`minIntervalMs`（给低频事件加低频限制）。
`Paused` / `Resumed` **不触发判断**（暂停不是表态），但记进上下文 —— S5 需要它区分「中途离开」与「不喜欢」。

### 7.4 输出（三选一，JSON）

```json
{"action": "none" | "append" | "replace", "params": {…}, "reason": "…"}
```

- `replace` 只作用于**当前播放曲之后**的队列（§3.1），在播那首必须放完
- `reason` = 主播写给节目档案的编排思路：进档案（每轮可见）、上 RadioCard `lastAdjust`（§3.3 2026-09-13 决议）
- 解析失败或字段非法 = 沉默，不重试

### 7.5 补歌路径：混合（D2，C4 的落实）

队列见底与判断路径**分开处理**，避免混为一谈：

- **有端点** → 走 judge（问模型补什么风格），失败则退回本地
- **无端点** → **直接本地按标签补歌**，跳过 judge，不发起注定失败的调用

这样 S4 在无端点时依然成立。

### 9.1 时间线长什么样（健康形态）

| 看什么 | 正常 | 异常与结论 |
| --- | --- | --- |

### A.1.2 断在哪：播放页完全绕过端口

```kotlin
// shared-ui/.../player/viewmodel/PlaybackViewModel.kt:23-27
fun playOrResume() = playbackController.playOrResume()   // ← 直连控制器
fun pauseMusic()   = playbackController.pauseMusic()     // ← 直连控制器
fun playNext()     = playbackController.playNext()       // ← 直连控制器
fun seekTo(p: Long) = playbackController.seekTo(p)       // ← 直连控制器
```

播放页是用户最可能操作的地方，却**完全不产生端口事件**，因此三个后果：

1. **用户点播放器「下一首」→ 不产生 `skipEvents`** → `MasterAgent.consecutiveSkipCount` 永不增长 → M6-T2「连跳 ≥2 触发重排」在真实使用中**不会触发**（只有对话里说「下一首」或工具调用才算）。
2. **自然播完 → 无信号** → DJ 收不到正反馈，无法区分「听完」和「跳过」。
3. **暂停 / 进度条 → 无信号** → 用户「接个电话」可能被误判为负反馈。

> **判据的价值**：这解释了「空有 Reroute/Refill 设计却全部悬空」不是回合设计的问题，
> 而是**输入端根本没有接线**。正文 §2「观测面不是从零埋点，而是把已有的结算结果接出一条事件流」
> 这个结论，正是从这里推出来的。
>
> **教训（对后续任何 agent 都适用）**：给一个 agent 设计能力之前，先核查**它的输入是否真的可达**。
> 设计文档里画得通的回合，可能一个信号都收不到。

### A.1.3 改造方向（已被正文 §2.2 吸收）

- 埋点**不复用端口的「命令驱动」模式**，而是下沉到控制器实现层（`MusicController` / `DesktopMusicController` / iOS 播放桥）。
- 端口层保留 `skipEvents` / `trackChangeEvents` 作为**兼容视图**（由统一流派生），避免一次性改动所有消费者。
- 收益：`PlaybackViewModel` 的直连调用**无需改造**即可被观测。
