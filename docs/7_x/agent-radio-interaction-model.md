# HMP W 阶段 · 电台用户操作模型 与 Agent 行为范式

> ⚠️ **过程稿**：本文的三层模型 / 八信号 / 阈值规则表已被 `agent-radio-spec.md` 取代 ——
> 定稿口径是「只记用户的播放操作事实，判断交给模型，默认沉默」，本文的判定规则表与信号清单仅作背景参考。

> **产出**：2026-09-13 | **分支**：`feature/agent-build`
> **定位**：本文件是 `agent-radio-persona.md`（人格与工作流 v2）的**前置模型层**。顺序是：先定义「用户在电台运行时的操作空间」，再由模型推导「DJ 该怎么反应」。
> **对回合集的检验作用**：`Start / Refill / Reroute / Segue / Wrap` 五回合是否**完备**，由本模型证明（每个信号必须被某个回合消化，见 §4.3）。

***

## 0. 结论先行

1. **用户操作 = 五维元组**：`(通道, 对象, 极性, 强度, 时效)`。用一个统一的分类维度描述，而不是逐个按钮写行为。
2. **观测层必须先统一，否则模型只是纸面** —— 当前**播放页操作绕过 agent 端口**，DJ 收不到任何真实用户操作反馈（§3.3 有逐条核查）。
3. **信号层是模型与 agent 的契约**：8 个规范化信号（`TrackCompleted` / `TrackSkipped` / …）取代"按钮级"描述，agent 只消费信号。
4. **行为范式 = 感知 → 判定 → 行动 三阶**，且 **「沉默是默认」**：绝大多数操作应该被静默吸收，只有跨过阈值才出声或换歌。

***

## 1. 为什么先建模型

| 不建模型的代价                       | 具体表现                                          |
| ----------------------------- | --------------------------------------------- |
| **回合集无法证明完备**                 | 出现"用户操作了，但没有任何回合负责"的空白（例如：用户拖进度条跳过副歌、用户手动播放别的歌单） |
| **阈值无依据**                     | "连跳 ≥2 就重排"是拍出来的 —— 跳 2 首可能只是不喜欢这两首，也可能是想换风格，二者该有不同响应 |
| **行为不可测**                     | 没有信号层就没法在单测里"注入一个操作 → 断言一个行为"，只能靠肉眼                        |
| **正反馈永远缺失**                   | 只知道"跳过"，不知道"听完" —— DJ 无法学习                        |

## 2. 用户操作模型

### 2.1 五维元组

| 维度           | 取值                                                        | 作用                        |
| ------------ | --------------------------------------------------------- | ------------------------- |
| **通道 Channel** | 控制面（播放器）/ 编排面（队列）/ 会话面（电台开关与主题）/ 环境面（系统事件）/ 语言面（对话与卡片） | 决定"谁观测得到"                  |
| **对象 Target** | 单曲 / 队列 / 会话 / 曲库数据                                        | 决定"影响范围"                  |
| **极性 Polarity** | 正反馈 / 负反馈 / 中性 / 新意图                                       | 决定"方向"                    |
| **强度 Strength** | 弱（1 次瞬时）/ 中（连续 2 次或明确语言）/ 强（连续 ≥3 或明确指令）                  | 决定"是否越过阈值"                |
| **时效 TTL**    | 瞬时（本回合）/ 会话级 / 长期（跨会话入库）                                  | 决定"记多久"                   |

### 2.2 操作分类矩阵

| 通道      | 具体操作                                    | 对象   | 极性  | 强度  | 时效  |
| ------- | --------------------------------------- | ---- | --- | --- | --- |
| **控制面** | 暂停 / 恢复播放                                | 单曲   | 中性  | 弱   | 瞬时  |
|         | 拖动进度条（小幅 <30%）                         | 单曲   | 中性  | 弱   | 瞬时  |
|         | **大幅前跳（≥70% 或跳到结尾）**                   | 单曲   | 负反馈 | 中   | 会话  |
|         | 音量 / 播放模式（随机、循环）                        | —    | 中性  | 弱   | 瞬时  |
| **编排面** | 下一首 / 上一首                               | 单曲   | 负反馈 | 弱→中 | 会话  |
|         | 连续跳过（≥2 / ≥3）                           | 队列   | 负反馈 | 中→强 | 会话  |
|         | 听完整首（自然播完）                              | 单曲   | **正反馈** | 中   | 会话  |
|         | 单曲循环 / 重复播放同一首                          | 单曲   | 正反馈 | 中   | 会话  |
|         | 手动调整队列（加入 / 移除 / 重排）                     | 队列   | 新意图 | 中   | 会话  |
| **会话面** | 停止电台（点收音机卡 / 说"停电台"）                    | 会话   | 中性→负 | 中   | 会话  |
|         | 暂停电台（PLAYING 态点卡）                       | 会话   | 中性  | 弱   | 瞬时  |
|         | 换种子重开（"来点爵士"）                           | 会话   | 新意图 | 强   | 会话  |
| **环境面** | 切后台 / 锁屏                                | 会话   | 中性  | 弱   | 瞬时  |
|         | 拔耳机 / 断连                                | 会话   | 中性  | 弱   | 瞬时  |
| **语言面** | "换点欢快的" / "别放这个歌手了"                     | 会话   | 新意图 | 强   | 会话  |
|         | "这首为什么推荐" / "再说说"                       | 会话   | 正反馈 | 中   | 瞬时  |
|         | 收藏 / 加入歌单                              | 曲库数据 | 正反馈 | 中   | **长期** |

### 2.3 三条建模公理

- **A1｜会话内的一切队列操作都是对 DJ 的反馈**：因为电台会话里的队列由 DJ 产生。但**强度不同**（自己手动加一首歌 ≠ 跳过 DJ 推的 3 首）。
- **A2｜反馈方向不由操作本身决定，而由"是否听完 + 是否重复"决定**：跳过 1 首是噪声，跳过 3 首是信号；听完 1 首是弱正反馈，重复听同一首是强正反馈。
- **A3｜用户主动播放非电台内容 = 会话自然终结信号**，不是"跳过"。当前实现里这让电台状态与真实播放脱节（队列被清空但电台仍显示 PLAYING）。

## 3. 信号层（模型 → agent 的契约）

### 3.1 八个规范化信号

| 信号                 | 含义                          | 极性  | 建议强度              |
| ------------------ | --------------------------- | --- | ----------------- |
| `TrackCompleted`   | 一首歌自然播完                     | 正反馈 | +1                |
| `TrackSkipped`     | 一首歌被跳过（含大幅前跳）               | 负反馈 | −1（连跳时累加）         |
| `TrackRepeated`    | 同一首被重复播放 / 单曲循环             | 正反馈 | +2                |
| `SeekedAway`       | 大幅前进但仍在同一首（视为准跳过）           | 负反馈 | −0.5              |
| `PlaybackPaused`   | 用户暂停（可能只是接电话）               | 中性  | 0（仅用于抑制误判）        |
| `QueueDepleted`    | 队列剩余 ≤ 阈值                   | 中性  | 触发补歌              |
| `ExplicitIntent`   | 语言面的明确意图（换风格 / 排除歌手 / 要更多类似） | 新意图 | 强（直接决定回合并写入偏好）    |
| `LeftRadioSession` | 主动播放非电台内容 / 停止电台 / 超时       | 终止  | 触发 Wrap           |

### 3.2 现有设施核查（逐条对代码）

| 信号                 | 现有来源                                                       | 状态    | 关键代码位置                                                                                                            |
| ------------------ | ---------------------------------------------------------- | ----- | ---------------------------------------------------------------------------------------------------------------- |
| `TrackSkipped`     | `PlaybackCommandPort.skipEvents`                           | **部分** | `ControllerPlaybackCommandPort:105` 要求 `source==USER && isSkipLikeCommand`，**且命令必须经端口下发**                       |
| （切歌通知）             | `PlaybackCommandPort.trackChangeEvents`                    | **部分** | `:112` 仅在 `pendingTrackChange`（NEXT/PREVIOUS/PLAY_BY_ID/SKIP_ALL **经端口**）后 emit                                  |
| `TrackCompleted`   | —                                                          | **缺失** | 自然播完无任何 emit 点（`trackChangeEvents` 的 KDoc 明确写"Agent 命令触发"）                                                        |
| `SeekedAway`       | `PlaybackCommand.SEEK_TO` 存在，但无信号                           | **缺失** | —                                                                                                                |
| `PlaybackPaused`   | `PlaybackCommand.PAUSE` 存在，但 UI 不走端口                       | **缺失** | —                                                                                                                |
| `QueueDepleted`    | `continueRadio()` 已实现但无调用点（G12）                            | **缺失** | 需要"队列剩余"观测能力                                                                                                     |
| `ExplicitIntent`   | `ChatAgentGateway` → `MasterAgent.handleUserMessage`        | **可用** | 但对话与电台会话无上下文关联（无法"针对当前这档节目"下指令）                                                                                  |
| `LeftRadioSession` | `RadioCard` → `stopRadio()`（有）；"播放了别的歌"（无）                 | **部分** | `MasterAgent.stopRadio()` 有；用户主动播放别的歌单无检测                                                                        |

### 3.3 ⚠️ 核心问题：观测层是断的

```kotlin
// shared-ui/.../player/viewmodel/PlaybackViewModel.kt:23-27
fun playOrResume() = playbackController.playOrResume()   // ← 直连控制器
fun pauseMusic()   = playbackController.pauseMusic()     // ← 直连控制器
fun playNext()     = playbackController.playNext()       // ← 直连控制器
fun seekTo(p: Long) = playbackController.seekTo(p)       // ← 直连控制器
```

播放页（用户最可能操作的地方）**完全绕过 `PlaybackCommandPort`**，因此：

1. **用户点播放器"下一首"→ 不产生 `skipEvents`** → `MasterAgent.consecutiveSkipCount` 永不增长 → **M6-T2「连跳 ≥2 触发重排」在真实使用中不会触发**（只有对话里说"下一首"或工具调用才会）。
2. **自然播完 → 无信号** → DJ 永远收不到正反馈，也就无法区分"听完"和"跳过"。
3. **暂停 / 进度条 → 无信号** → 用户"接个电话"可能被误判为负反馈（一旦补上信号，反过来需要这个中性信号来抑制误判）。

> 换句话说：**目前的电台 agent 是在对自己说话**。这解释了为什么空有 Reroute/Refill 设计却都悬空 —— 不是回合没设计好，是输入端根本没有线。

### 3.4 改造建议：统一播放信号流

- **不复用端口的"命令驱动"埋点，而是下沉到控制器实现层**（`MusicController` / `DesktopMusicController` / iOS 播放桥）——凡是"当前曲目变化 / 请求销毁"的地方统一产出信号，附带 `origin: USER | AGENT` 与 `reason: Completed | Skipped | SeekAway | UserSelected | QueueReplaced`。
- 端口层保留 `skipEvents` / `trackChangeEvents` 作为**兼容视图**（由统一流派生），避免一次性改动所有消费者。
- 这样 `PlaybackViewModel` 的直连调用**无需改造**即可被观测（埋点在控制器内）。

## 4. Agent 行为范式

### 4.1 三阶结构

```
感知 Perceive  ：信号 → 更新 RadioSession（negativeSignals / praiseSignals / pushedIds / turnSeq）
判定 Decide    ：按规则表决定「是否需要动作」——不动作也是合法结果
行动 Act       ：执行回合（Start / Refill / Reroute / Segue / Wrap），并回写状态 + 审计 + 解释
```

### 4.2 判定规则表

| 条件                                  | 动作                     | 参数                              |
| ----------------------------------- | ---------------------- | ------------------------------- |
| 负反馈累计 ≥3（连跳 3 首）                    | **Reroute**（换风格，非微调）   | 排除被跳标签/歌手；`proactiveness` 提高换风格幅度 |
| 负反馈累计 =2 且 `proactiveness ≥ 0.5`    | Reroute（轻量）            | 只换下一批，不换主题                      |
| 负反馈累计 =2 且 `proactiveness < 0.5`    | **静默吸收**（继续观察）         | —                               |
| 正反馈连续 ≥2（听完 2 首）                    | 静默吸收 + 加固主题（写偏好记忆）     | 不打扰                             |
| `QueueDepleted`（剩余 ≤3）              | **Refill**             | 延续当前主题，追加而非替换                   |
| 切歌且 `talkativeness ≥ 0.4`            | **Segue**              | 15-20 字衔接语                      |
| `ExplicitIntent` = 换风格              | **Reroute**（显式主题）      | 新主题入 `themeHistory`              |
| `ExplicitIntent` = 排除某歌手/标签         | 写 `negativeSignals` 并 Refill | 长期时效（跨会话）                       |
| `LeftRadioSession`                  | **Wrap**               | 归档"选了哪些、跳了哪些"                   |
| 其他（暂停、小幅 seek、音量、切后台）               | **静默吸收**               | 不改队列、不打扰                        |

### 4.3 完备性检验（8 信号 × 回合）

| 信号                 | 消化它的回合           | 结论        |
| ------------------ | ---------------- | --------- |
| `TrackCompleted`   | 静默吸收（+写记忆）       | ✅ 有归属     |
| `TrackSkipped`     | Reroute（阈值触发）+ Segue 抑制 | ✅ 有归属     |
| `TrackRepeated`    | 静默吸收（+强正反馈）      | ✅ 有归属     |
| `SeekedAway`       | 静默吸收（权重 −0.5）    | ✅ 有归属     |
| `PlaybackPaused`   | 静默吸收（抑制误判）       | ✅ 有归属     |
| `QueueDepleted`    | Refill           | ✅ 有归属     |
| `ExplicitIntent`   | Reroute / Refill | ✅ 有归属     |
| `LeftRadioSession` | Wrap             | ✅ 有归属     |

**检验结论**：五回合对当前信号集是**完备**的 —— 不需要新增第六个回合；缺的是**信号本身**（§3.2 的五个"缺失"）。这反过来验证了 `agent-radio-persona.md` 的回合划分。

### 4.4 边界（DJ 不该做什么）

- 不改用户数据：不加歌单、不删歌、不改标签（只写自己的会话记忆）。
- 不抢播放控制权：用户手动播放非电台内容时，不"抢回来"（A3 → Wrap）。
- 不在无信号时自我发挥：没有 `QueueDepleted` / 负反馈 / 明确指令，就不主动换歌（**沉默是默认**）。
- 不解释过度：衔接语 ≤20 字；说明只在 Reroute 时给一句。

## 6. 验收与测试

- **信号可注入**：统一信号流是 `Flow`，测试里可手工 emit 序列。
- **行为可断言**（用例清单）：
  1. 注入 3×`TrackSkipped` → 断言触发 Reroute 且排除被跳标签
  2. 注入 2×`TrackCompleted` → 断言**不**触发 Reroute（且写入正反馈）
  3. 注入 `PlaybackPaused` + 1×`TrackSkipped` → 断言不误判为连跳
  4. 注入 `QueueDepleted` → 断言 Refill 且主题不变、队列为追加
  5. 注入 `ExplicitIntent(排除歌手X)` → 断言 X 进负反馈且后续队列无 X
  6. 注入 `LeftRadioSession` → 断言 Wrap 归档
- **回归**：`:shared:desktopTest` + 三端编译；新信号流不得破坏现有 `skipEvents` 消费者。
