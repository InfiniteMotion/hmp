## 1. 定位与红线

**命题**：以播放器为身体的音乐伙伴——伴随你听歌，在你的音乐事务上帮助你；陪伴与视野不止于曲库。它一直是对话对象（话题不设限，音乐之外无本地记忆优势）；推荐可出曲库（伙伴的建议，用户如何获取是用户自己的事）。

**判定标准**：存在反馈闭环才叫伙伴——伙伴行动后，用户行为（听下去/跳过/收藏）改变它的下一次决策。没有闭环的只是带 AI 的功能。**它不是一次 AI 调用（旧每日推荐），也不是聊天界面（只是触发方式之一）。**

**产品红线（仅两条，其余由行为/工程级约束承托）**：

1. **伙伴只属于你**——记忆只存设备，无账号、无云同步（架构事实，也是它的忠诚）。
2. **隐私明示**——对话携带曲库摘要发往用户自填端点，必须让用户清楚知道。

**否决史（防止回流）**：不话多、只谈音乐、推荐限库内——三项均不立法（谈吐是人格滑杆维度；伙伴不应是只会谈音乐的机器人；推荐库外歌是表达自由）。**被否决的是「在线音乐服务闭环」（不内置流媒体/下载/账号），而非话语自由——推荐是话语，不是通道**：应用不为推荐提供一键播放/下载。

## 2. 本体——决策循环与认知

### 2.1 概念体系（七个）

| 概念 | 定义 | 关键纪律 |
|------|------|---------|
| 工具 | 确定性操作原语（读/算/写） | 本地工具即时响应；云端工具双方结果审计合并 |
| 模型调用 | 生成性原语，产出意图 | 永远不直接落地——输出必经解析、校验、写入或经人确认 |
| 任务 | 一次目标导向的循环 | 有预算（步数/token）、有结果、可失败；执行单位 |
| 触发器 | 任务如何开始（召唤/事件/定时） | 调度单位 |
| 策略 | 任务的约束包（白名单/许可分级/预算） | 安全单位；预算刻度由人格滑杆驱动，机制本身是防失控保险丝 |
| 记忆 | 分层数据、会话上下文、信任状态 | 记忆变更也是工具调用；记忆不占上下文（2.4） |
| 人格 | 用户感知单位 | 预置加自定义；一个伙伴，多个技能 |

### 2.2 认知：富化即认识

**旧定义废弃**（调 LLM 发预置提示词反序列化存字段）。**新定义**：富化是 Agent 认识每首歌并长期化记忆的过程。既有批处理管道（pause/resume/cancel 状态机、500ms 节流、逐首 LLM 调用——`GetDailyMusicRecommendationUseCase.autoProcessMissingExtraInfoWithCurrentProvider`）全部继承，五点改变：

1. **产出是长期记忆**——标签是索引面；`backgroundIntroduce`/`singerIntroduce`/`description` 等升为记忆正文（伙伴说「接着上礼拜你迷的那个乐队」引用的正是这些）；
2. **主语是伙伴**——预置提示词是它的感知习惯，管道是它的学习流程，第一次大规模认知=认识全曲库；
3. **导入即认识**——扫描入库自动进认识队列，如同 ID3 解析不是可延后的优化；未认识歌曲可播放可搜索，但不进标签驱动推荐（代码事实：无标签时 `getSimilarSongsByWeightedLabels` 直接返回空）；
4. **认识可演化**——用户修正（T1）覆盖模型认识（T2），云端新知更新旧认识，行为反馈调可信度；`MusicLabel` 的 `source/confidence` 是存储基础；
5. **`enrichSong` 是记忆写入工具**——会话中遇到不认识的歌，伙伴可主动发起认识。

**终生认知任务**（常驻 PersistentTask）：

```
新歌导入 → 增量认识（复用既有批处理状态机）
优先级队列：①正在听/刚收藏 ②高频播放未认识 ③按导入顺序
产物 → 长期记忆（带 source/confidence 溯源）· 额度耗尽暂停（非失败），恢复后断点续认识
```

产品化推论：认识进度=伙伴的阅历而非系统进度条——首启「我还在认识你的曲库，已认识 47 首」；曲库页徽标「已认识 2312/2500」；伙伴资料页展示阅历。

### 2.3 运作：双层机制与三轮协作

**原则：本地是响应保障，云端是决策权威。** 四条执行纪律：

| 纪律 | 内容 |
|------|------|
| 响应保障 | 本地层即时结果；判断质量以云端为准 |
| 留痕可撤销 | 云端修正已生效结果 → NOTIFY 级呈现 + 理由入审计日志 |
| 双向回流 | 用户行为同时修正本地参数（毫秒级零成本）与云端会话记忆 |
| 降级兜底 | 云端不可达或额度耗尽 → 本地层独立兜底，能力受限但永不失能 |

**三轮协作**（以种子推荐为贯穿示例，= 一个任务的两个 LLM 调用步 + 一次本地比对，步数预算内常规操作）：

1. **第 0 步 认识种子**——种子必须已被认识，否则当场 `enrichSong`（认识是推荐的第零步）；
2. **第 1 轮 本地响应**——相似度 + 行为先验产出保底队列 L，用户零等待开听；同时组装云端请求（种子画像/全库清单/语境）；
3. **第 2 轮 云端全量决策**——「歌名-歌手」清单（3000 首约 30k-60k tokens ≈ 0.1 元以内）交 LLM 全局视野选 30 首 → 队列 C；全量清单法能看到局部算法看不到的关联；
4. **第 3 轮 比对回传与云端仲裁**——diff(L,C)：共同命中直接保留；仅本地（行为先验证据）与仅云端（模型独有发现）差异集+双方理由回传裁决 → 终版队列落地（留痕、可撤销、NOTIFY）；第 3 轮只发差异集（几百 tokens，成本比第 2 轮低约两个数量级）；
5. **第 4 阶段 反馈修正**——播放列表是实验不是交付物：跳过降权、完播/收藏升可信度、列表级学习积累同语境先验。旧心动模式输出列表；新模式维护「它对你的认识」。

### 2.4 上下文组装：记忆 ≠ 上下文

长期记忆（Room）永不直接占用窗口，按分层配额组装：

| 上下文层 | 内容 | 配额策略 |
|---------|------|---------|
| 1. 会话与任务状态 | 当前任务进展 | 必在，占比小 |
| 2. 曲库概况 | 世界模型 | 两级切换（下） |
| 3. 工具结果 | 检索/计算产出 | 滚动淘汰，最旧先出 |

曲库概况两级打包：**清单法**（推荐/审计/仲裁任务允许时）= 全库「歌名-歌手」一行一条，3000 首约 30k-60k tokens；**概览法**（窗口吃紧/超大曲库/非清单任务）= 规模/语言分布/流派 top/年代/常听 50 首摘要，数百 tokens（纯本地 SQL 聚合，零成本零幻觉）。明细约定：清单既是世界模型又是选择空间（模型输出直接引用歌名歌手，本地解析回 ID）；单首深度认识经 `getMusicExtra` 按需进场一次一首。

### 2.5 人格：预置加自定义

出厂预置数款人格（「知音」健谈共情 /「DJ」热情高能 /「馆长」克制博学），每款 = persona 提示词 + 滑杆预设（健谈度/主动度/话题宽度）+ 称呼习惯。用户可自定义：调滑杆、设名字与代词（他/她/它）、高级用户直接改 persona 文本，存为个人款多套切换。

架构落点：人格 = `CompanionProfile`（滑杆/称呼）+ persona 提示词，存 DataStore；出厂预设为代码常量表。人格驱动三件事：模型 persona 注入、存在感预算刻度（健谈对应更宽预算，机制保留为防失控保险丝）、UI 呈现语气。

## 3. 认识论——知道什么、什么可信

### 3.1 三层可信度

| 层 | 内容 | 可信度 | 特性 |
|----|------|--------|------|
| T0 行为事实 | 播放/跳过/完播/收藏/时段/队列操作 | 绝对可信 | 用行为投票，零幻觉，持续更新；第一信源 |
| T1 用户手工 | 歌单策展/标签修正/ID3 编辑/隐藏文件夹 | 高可信 | 有意图的显式判断，最高优先级 ground truth；稀疏 |
| T2 模型认识 | 标签/富化正文/推荐解释 | 信任但可修正 | 本地算法地基；**被审计的资产**而非待怀疑的噪声——默认使用，可降权可覆盖，全程溯源 |

### 3.2 裁判规则

- **静态信任链 T1 > T0 > T2**——作用域**仅限同类证据冲突**（修正权排序，非重要性排序）；
- **异质证据（行为 vs 标签）不做优先级裁决，走融合仲裁**（3.3）；
- **动态修正三规则**：① T1 覆盖 T2（`source=USER` 永不被模型覆盖）② T0 确证/证伪 T2（行为与标签一致则 confidence 升，长期背离则降权，检索少用）③ T2 可被 T2 更新（云端新知更新旧认识，更新留痕，旧进历史不消失）。

### 3.3 两路证据的融合（废弃旧稿「行为优先，标签辅助」）

行为与标签是**两路平等证据**，融合裁决——三轮协作不是推荐专属机制，而是**一切语义检索的通用裁决模式**。两路盲区（缺一不可）：纯行为路=冷启动饿死、稀疏无法区分「不喜欢/没听过」、跳过可能只是「此刻不想听」；纯标签路=T2 可能错标、是导入时刻快照不随口味漂移。冷启动是融合最佳例证：新歌无行为 → 标签路独立支撑初始曝光 → 行为积累后两路汇合，权重随数据自然转移。**融合执行者是 agent**——怎么组合证据是规划自由，不是系统硬编码（「深夜歌单=先查行为再过滤标签」只是 agent 的一种做法）。

### 3.4 证据的三层供给

| 层 | 供给方式 | 内容 | 成本 |
|----|---------|------|------|
| 1. 系统供给 | 触发即随任务携带，无条件进上下文 | 语境包（时段/跳过模式/当前曲目）、曲库概况、种子画像 | 固定（任务底价） |
| 2. agent 自发获取 | 工具调用按需检索 | `searchLibrary`/`getListenStats`/`getRecentHistory`/`getMusicExtra`/`getSimilarSongs` | 边际（按需付费） |
| 3. 行为自发回写 | 用户行动无需召唤 | 听/跳/收藏持续进记忆层 | 零成本（T0 自动积累） |

分界必然性：全供给不可行（全库统计 = 几十万 tokens），全自取不可取（每次任务先烧两三轮调用）。**系统供通道，agent 定组合**——两次调用组合出的证据胜过十次盲调，工具调用次数 × 结果质量 = agent 效率指标。主动补证也可发生在云端仲裁中（tool loop 原生形态），底价供给与按需自取在任务中交织。

### 3.5 演化闭环与审计四问

```
建立：导入 → 认识（T2 初始记忆）   消费：检索（索引面）· 推荐（两路融合）· 对话引用（正文）
演化：用户修正（T1 覆盖）· 行为反馈（T0 调权）· 云端新知（T2 更新留痕）
审计：source/confidence 全程溯源
```

**审计四问**：任何一条认识（标签/正文/推荐理由）都能回答——来源？何时建立？被行为确证过吗？被谁修正？存储落点见 7.3（`source/confidence/created_at/updated_at` + audit_log 修正留痕）。

**隐私**：三层认识全存本地（Room/DataStore）；对外只发生在用户自填端点且明示——**云端知道的是请求内容，不是用户本人**（请求携带什么由 2.4 组装规则约束）。

## 4. 能力面——工具、场景、语音

### 4.1 既有 AI 功能归位（用户只应感知「伙伴本来就会这些」，UI 不出现「agent 化」表述）

| 既有功能 | 归位 |
|---------|------|
| 心动模式（本地相似度） | 伙伴的直觉——两路证据之一（3.3） |
| 富化管道 | 伙伴的认知过程（2.2） |
| 每日推荐 | 伙伴的每日问候——「为什么是这首今天给你」（定时任务+可解释） |
| AI 服务商配置 | 伙伴的身体素质——AI 页演进出「伙伴设置」：人格滑杆/信任状态/存在感预算/额度/实时语音端点 |

### 4.2 工具面 v1（十项）

描述按三段式：行为约束（结果上限 50 条）/ 成本提示 / 替代指引（优先零成本工具）。许可级语义见 5.3。

| 工具 | 类别 | 底层能力 | 许可级 |
|------|------|---------|--------|
| `searchLibrary` | 读 | `SearchMusicUseCase` + 标签过滤 | 静默 |
| `getListenStats` | 读 | `getUserUsageAnalytics` | 静默 |
| `getRecentHistory` | 读 | `getRecentPlaybackHistoryGlobal` | 静默 |
| `getNowPlayingContext` | 读 | `PlaybackCommandPort.events` | 静默 |
| `getSimilarSongs` | 算 | `getSimilarSongsByWeightedLabels` | 静默 |
| `getMusicExtra` | 读 | `getMusicExtraById` | 静默 |
| `enrichSong` | 记忆写 | 既有富化管道 | 通知 |
| `createPlaylist` | 写 | `ManagePlaylistUseCase` | 确认 |
| `addToPlaylist`/`reorderPlaylist` | 写 | 同上 | 确认 |
| `controlPlayback` | 写 | `PlaybackCommandPort.execute` | 确认→信任降级 |

远期候选（不进 v1）：`searchWeb`、`getArtistDiscography`。

**两级漏斗**（工具面运行纪律）：高频指令（暂停/下一首/音量/播某歌）走本地词表直映射——零 token、50ms 内；模糊意图（「换点安静的」）才升级为单轮 agent 任务。约八成流量被第一级拦下，FREE（无 Key）模式也用得起高频命令。

### 4.3 场景全景（四类十五个，优先级梯队）

```
一梯队：AI 电台(1) · DJ 衔接(4) · 曲库问答(6) · 歌单策划(7) · 一句话切换(3)
二梯队：跳过感知(2) · 标签修正闭环(9) · 可解释推荐(13)
三梯队：曲库医生(8) · 智能归档(10) · 遗忘唤醒(12) · 睡眠定时(5)
四梯队：听歌报告(11) · 艺术家深读(14) · 歌词注解(15) · Web 检索
```

陪伴态（听音乐时）：AI 电台、跳过感知重排、一句话切换、DJ 衔接、智能睡眠定时。工具态（管曲库时）：曲库问答、对话式歌单策划、曲库医生（标签缺失高频歌/30 天未播新歌/过气心头好）、标签修正闭环（T1 覆盖 UI 化）、智能归档。惊喜态：听歌报告（月/年度叙事）、遗忘唤醒、可解释推荐。学习态：艺术家/专辑深读、歌词翻译注解。逐场景交互流见第 6 章。

### 4.4 语音：二档制（能力探测驱动，无中间态）

```
填了实时语音端点（OpenAI Realtime / 豆包兼容 WebSocket）→ 语音对话：全双工·可打断·模型内端点检测·首响应 0.3-0.8s
没填 → 纯文字：锚点系统（第 5 章）+ 两级漏斗（指令 50ms 内）
```

**实时语音技术形态**：WebSocket 双向流（JSON 控制事件 + 二进制音频帧）；`RealtimeVoiceTransport` 单 port 纯 common 代码，**无 expect/actual**（已核验 `ktor-client-websockets` 3.1.1 具备 iosArm64/iossimulatorArm64 构件，三端齐全）。transcript 双向流（`input_audio_transcript.delta` / `response.audio_transcript.delta` 与语音块同步）→ **一套 UI 两种形态**：语音气泡 = 文字 + 内存内重放（音频不落库，不假装持久）；`agent_message` 存 transcript 文本；语音/文字同会话混排；工具调用与写确认全部有文字记录——**语音交互不产生无法审计的记忆**。会话模式与循环模式共享四层：工具（同一 ToolRegistry）/ 记忆（会话后增量回写）/ 嗓音（PresenceBus）/ 策略（PolicyGuard——语音里写操作降级为口头确认）。

**被砍掉的中间档**（否决史）：平台 STT（国行不可靠）、whisper.cpp（批处理错范式）、LLM 接口 STT（延迟 2-5s）、sherpa-onnx 本地流式（为不存在的能力需求背负三套 C 库桥接）。结论：**中间档的全部复杂度只服务「降级用户的语音」，而纯文字降级本身已完整可用**。v1=纯文字，v2=实时语音独立 feature。

### 4.5 行为级红线（四条，全部产品级）

1. 不做在线音乐服务闭环——不内置流媒体、下载、账号
2. 未经确认不写文件——ID3 修改必过确认，无例外
3. 不常驻后台——只在事件、召唤、定时时短时运行（电量红线）
4. 跨设备同步——伙伴记忆不云同步

## 5. 交互实施——锚点、对话、许可、呈现

### 5.1 骨架基线（交互设计只允许在下列真实骨架处生长）

| 骨架事实 | 代码位置 | 对伙伴的意义 |

### 5.3 对话：消息模型与三个厚度

**消息模型**：`agent_message(id, session_id, role, content, render_hint, created_at)` 是唯一事实，UI 只是读取它的三个姿势。`render_hint` 驱动渲染分级：

| render_hint | 气泡形态 | 承载 |
|------------|---------|------|
| `text` | 纯文本气泡 | 闲聊、问答、DJ 线、通知语 |
| `song` | 歌曲卡（封面+题名+艺人，点按=SongDetail，菜单=加歌单/分享） | 单曲推荐、每日问候 |
| `songlist` | 歌单卡：头部+`FixedMusicList`（`HeaderConfig.None`+`ItemVariant.Full`+序号，可增删，复用 HomeScreen 心动歌单区块配置）+尾部动作行（保存/调整/重选） | 歌单策划、电台备选、智能归档预览 |
| `explain` | 折叠卡：紧凑一句+「为什么」展开三轮轨迹（本地→云端→仲裁） | 可解释推荐、跳过重排说明 |
| `confirm` | 确认卡（5.4.2） | 批量写确认 |

气泡语法：用户侧 primary 右对齐；伙伴侧 surface 半透明+haze 左对齐、顶部小号伙伴名；语音气泡=文字+左下角小播放键（音频仅会话内存可重放——切页后不可重放，诚实呈现）。

**三厚度**（同一 session_id，无二等消息）：

1. **对话页**（独立 SubScreen 页）：问候区 + 正在听卡（封面+题名+播控，点按进播放页）+ 对话流（LazyColumn，新消息自动滚底，用户回看时暂停自动滚，流顶部翻页）+ 任务进行条（工具循环中「正在翻你的曲库…」三点脉动+取消，完成后原地替换为结果卡片）+ 常驻输入条（胶囊形输入框+发送+可选按住说话）。键盘：输入聚焦 `imePadding`，问候区随键盘收起。每日问候=一条 `song` 卡附 explain；门面上仍是卡片，同一数据两种呈现（门面管扫视、对话页管深聊）。
2. **轻量浮层**：底栏上方自底上滑单行条（无底栏页面贴屏底）。回复二分法——一句话气泡（浮层内直显）或卡片摘要（『建好了「深夜」歌单，12 首』+「查看」进对话页对应位置）；`songlist` 等重卡片不塞浮层（浮层管轻，对话页管重）。退出：发送后 2s 无输入 / 点浮层外 / Esc。
3. **搜索框条带**（SearchScreen 既有 TextField 不动）：两级漏斗第一级先行，未命中且含意图特征→结果顶部伙伴条带（「交给伙伴」=输入作首条消息进会话 / 「只是搜索」=收起且本次会话同类输入不再弹——拒绝纪律：不纠缠）；空结果页下方追加「问问伙伴？」轻条带——空结果是天然对话起点。

### 5.4 许可与呈现（判据：**用户不怕伙伴犯错，就怕错了回不去——撤销永远在场**）

**许可分级**：可逆·低可见=静默执行；可逆·可见=执行+通知侧条（『建好了「深夜」，12 首 ↩撤销』）；批量写=非模态确认卡片流；不可逆（删歌单/改 ID3）=传统强确认无例外。**信任阶梯**：每类写动作从「建议」起步，连续隐式接受逐级升「代劳→静默」——**自主权是挣来的**，全程可查可回拨（设置页每类动作当前档位）。语音会话 CONFIRM 降级为口头确认（「要建这个歌单吗？」——「好」）。**拒绝纪律**：被拒后可换方案、不可纠缠同一意图——「不」是完整回答不是谈判起点。

| 组件 | 形态 | 要点 |
|------|------|------|
| `AgentNoticeBar`（新建） | 底栏上方 haze 侧条，4s 自动退场 | 撤销点按=回滚（触觉 Confirm）；**撤销窗口过期≠不可逆**——入口转审计页；与 `MessageToast`（系统消息）两条通道不混用；同时刻至多一条 |
| `confirm` 确认卡（流内） | 非模态，不挡输入条 | 逐项勾选=执行范围，「照做」只执行选中项，「跳过全部」=本卡作废；执行后→NOTIFY 侧条+卡状态更新「已建 9 首，跳过 3 首」；语音=伙伴念关键项+口头答复 |
| STRONG_CONFIRM（复用 DialogHost） | 模态红字无撤销 | 删歌单/改 ID3；`EditMusicTagsScreen` 系统授权框（MediaStore/SAF）在前→**双确认链**：伙伴问意图→系统问权限，顺序不合并 |
| 审计日志页（新建 SubScreen） | `agent_audit_log` 驱动，时间倒序 | 每行=动作+「为什么」展开（→T0 行为证据：「你 23:00 后跳过了两首快歌…」）+可撤销动作的撤销钮；**撤销边界**：被用户后续修改过的动作（歌单被增删过）撤销降级为「删除」（STRONG_CONFIRM）；重排队列类始终可撤销 |

**存在感四形态**：通知侧条（NOTIFY 完成）、DJ 线（曲间预生成一句衔接：门面问候区轮换句不弹窗 + 对话页流内 `text` 沉淀可回看）、正在听卡（对话页顶部常驻）、胶囊徽标（未读/待确认/电台运行）。**唯一硬纪律：播放中不弹任何伙伴浮面——用户手势进行中永远闭嘴**（健谈如「知音」也遵守）。

**质量纪律**（适用于任何健谈度，代替废弃的「每天≤3 次」预算制）：不打断正在进行的操作；每次开口有信息增量（不说「接下来播放」这类零信息话）；解释按需（每个自主动作留一句紧凑理由，不主动展示，审计日志页承载全部「为什么」——信任来自随时可查，不是每次都说）；健谈度=人格滑杆。可解释性的尽头是 T0 行为证据——**伙伴从不说「我觉得你会喜欢」**。

**交互全景四层**：被动层（播放行为流→T0 记忆→影响一切决策）· 主动层（锚点一句话→两级漏斗→即时响应）· 对话层（对话页多轮/闲聊→富回复）· 呈现层（PresenceBus→自然窗口+信息增量+按需解释+永远可撤销）。

## 7. 工程——架构、选型、数据、实施序列

### 7.1 四平面架构（落在现有 KMP 代码库之上，零新增第三方依赖）

```
shared-ui（三端共享 Compose）——伙伴的脸：对话页 · 确认卡片流 · 审计日志页 · 伙伴设置页
:shared / domain/agent/
┌─────────────────────────────────────────────────────┐
│ 人格平面   CompanionProfile(滑杆+称呼+persona) × 预设常量表    │
│ 引擎平面   AgentOrchestrator(唯一循环, 步数预算 8)             │
│            Scheduler(触发+冷却) · PolicyGuard(四级许可)       │
│            TrustLedger(信任状态机) · ContextBudget · SessionStore│
│ 工具平面   ToolSpec DSL(手写 schema+校验) · ToolRegistry · 十项工具│
│ 端口平面   LlmTransport(手动 SSE) · RealtimeVoiceTransport(WebSocket) │
│            PlaybackCommandPort(播放指令/事件) · PresenceBus(唯一嗓音) │
└─────────────────────────────────────────────────────┘
data 层：Room v2（agent_task/agent_audit_log/agent_message 三表 + MusicLabel 加列）
          · DataStore（信任/预算/开关）         平台层：三端 PlaybackCommandPort 适配器
```

**双平面思想**：引擎平面拥有全部安全基建（预算、许可、审计），人格平面只做呈现——人格可以随便换，安全不随人格松动。**预算两层**：步数预算（单任务）与**云端调用频率/额度配额**（跨任务，防电台与高频对话的日成本累积）——额度耗尽触发本地兜底（2.3 降级兜底），能力受限但永不失能。

**双模式**：`AgentOrchestrator`（文本模式，客户端组装上下文+tool loop）与 `VoiceSessionController`（语音模式，会话建立时注入快照，服务端管上下文）并存，共享工具/记忆/呈现/策略四层；ContextBudget 前者每次调用裁剪、后者会话开启选快照+时长监护。

### 7.2 六项选型（全部零新增第三方依赖，含语音——WebSocket 是 Ktor 既有能力）

| # | 决策 | 理由 | 被排除项 |
|---|------|------|---------|
| 1 | 自研引擎（约 1500 行） | 循环本体 300 行，复杂度在护栏；量级=一次中等重构 | Koog（无 iOS target）、koaks、langchain4j/Spring AI（JVM-only） |
| 2 | 手动 SSE 解析（~80 行，ByteReadChannel） | 避开 Ktor 3.1.1→3.2 升级；兼容怪癖端点；Darwin 取消泄漏 3.2.x 才修 | Ktor SSE 插件 |
| 3 | 手写工具 schema（DSL 生成定义+校验器） | 与 kotlinx.serialization 协同；单测防漂移 | JSON Schema 生成器库 |
| 4 | 复用 Room/DataStore | 零新存储；v1→v2 只加表和列 | 新型存储、向量库 |

### 7.3 数据层：Room v1 → v2（AppDatabase 现 version=1，无历史迁移）

## 9. 附录：红线汇总与否决史

**红线六条**：

产品级：① 伙伴只属于你——记忆不出设备，无账号无云同步；② 隐私明示——对话/语音携带什么、发往哪里，用户始终清楚。
行为级：③ 不做在线音乐服务闭环；④ 未经确认不写文件——ID3 修改必过确认，无例外；⑤ 不常驻后台——只在事件、召唤、定时时短时运行。
工程级：⑥ 零新增第三方依赖——语音二档制后，实时语音也只是一个 Ktor WebSocket 实现。

**否决史总览**（原双文档各章审计轨迹合并；记录防回流，幸存的每个决策背后都有被否决的候选）：

| 被否决项 | 否决理由 |
|---------|---------|
| 不话多 / 只谈音乐 / 推荐限库内 | 人格维度不应由产品立法；话题域不设限（1 章） |
| 在线音乐服务闭环（流媒体/下载/账号） | 产品边界；推荐是话语不是通道（1 章） |
| 本地算法优先 | 双层机制以云端为决策权威（2 章） |
| 「行为优先，标签辅助」 | 两路证据应平等融合，与三轮协作统一（3 章） |
| 语音中间档四方案（平台 STT/whisper.cpp/LLM 接口 STT/sherpa-onnx） | 复杂度只服务「降级用户的语音」，纯文字降级已完整可用（4 章） |
| 存在感预算制（每天≤3 次） | 为寡言人格立法，与人格滑杆冲突；降格为出厂刻度（5 章） |
| Clippy 红线（需要用户回答问题的无感 agent） | 降为质量纪律「信息增量」的注释（5 章） |
| 上游三入口 B（长按播放键）/C（MiniPlayer 气泡） | 可发现性差；被三胶囊主锚点取代（5 章） |
| 门面对话流主体 | 门面承载多功能，对话降级为触发钮，主体回独立对话页（5 章） |
| 浮层悬浮卡片 / 侧条 4s 后撤销失效 / DJ 横幅 / 睡眠定时确认卡 / 标签修正确认卡 / 遗忘唤醒侧条推送 | 均可逆性、过度确认或「播放中不弹浮面」纪律的违规修正（5 章） |
| 曲库认识大进度条入门面 | 进度属设置域（体质信息）不属脸面（5 章） |
| 伙伴设置新路由 / 审计页并入设置二级 | 演进不推翻复用 `Routes.AI.AI`；审计是横向查询须独立路由（8 章） |

> 它始于一个会选歌的播放器，终于一个记得你们所有歌的伙伴。
