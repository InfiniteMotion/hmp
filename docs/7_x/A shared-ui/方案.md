# HMP 共享 UI 层提取方案

> 状态：已定稿（v4，三轮 review 修订版）
> 分支：`feature/shared-ui-extract`
> 基线：`master`（v6.13.1）
> 前置讨论结论：本方案**取代**已作废的 `docs/ui-rewrite` 重写路线；先提取（方案甲），后整理（向方案乙契约靠拢，作为第二阶段可选优化）。

---

## 1. 背景与决策回顾

### 1.1 为什么推倒重来

前一轮 `ui-rewrite` 路线采用「并行重写 + feature flag 双轨切换」：

- 新建 `shared-ui` / `shared-presentation` 纯数据驱动层，旧 UI 冻结为规格，逐页 flag 切换。
- 实践暴露的核心问题（已确认）：
  1. **双实现长期并存**：两套 UI、两套 ViewModel、两套资源，逐页对齐成本非线性上升。
  2. **资源契约被低估**：`IconKey` / `MessageKey` 到 Compose Resources 的完整映射在 P3 未一次做对，导致 A1 阶段边接线边补 key，出现「占位资源」「出错了」等反复返工。
  3. **方案乙式重写不适合本仓库规模**：边搬边改两个变量叠加，冲突面与回归风险失控。

**结论：推倒重来，改用「从 Android feature-ui 提取共享层」的迁移式路线（方案甲）。**

## 2. 现状盘点与关键前提

### 2.1 现有模块

| 模块 | 形态 | 对本方案的影响 |
|---|---|---|
| `shared` | KMP（desktop/android/ios），含 domain + data + DI，**无 Compose UI** | domain/data 已是好地基；共享 UI 不能塞入 shared |
| `android/feature-ui` | **AndroidX Compose** + Android Coil + navigation3 + lifecycle | 提取源；需先换 Compose Multiplatform 依赖 |
| `android/core-player` | Media3/ExoPlayer | 播放引擎实现（平台侧） |
| `desktop/feature-ui` | **已是 Compose Multiplatform** + koin-multiplatform + lifecycle-viewmodel-compose 2.8.4 | 形态正确，可作 CMP 依赖组合与平台隔离的参考 |
| `desktop/core-player` | FFmpeg + JNA | 播放引擎实现（平台侧） |
| `ios/HMP` | SwiftUI | 不在本轮范围 |

### 2.2 关键前提：Android feature-ui 的依赖替换

把 Android UI 抽到 commonMain 的**第一步实质动作**是依赖替换（不影响行为，但决定能否编译到 desktop target）：

| AndroidX 依赖（现状） | CMP/KMP 等价物（目标） |
|---|---|
| `androidx.compose.*`（ui/foundation/material3/animation） | `org.jetbrains.compose.*`（Compose Multiplatform） |
| `coil.compose`（`AsyncImage`） | `coil3` KMP（`coil3.compose.AsyncImage`） |
| `androidx.lifecycle.*` | `org.jetbrains.androidx.lifecycle:lifecycle-viewmodel-compose`（2.8+，desktop 已在用） |
| `androidx.navigation3` | **已适配 CMP**（`org.jetbrains.androidx.navigation3:*`，JetBrains 官方支持）→ 仅依赖替换，无需结构性改造 |
| `androidx.media3.common` | 从 UI 中剥离，收敛到 `PlaybackController` 接口 |
| `androidx.palette.ktx`（动态取色） | `expect/actual` 或移入平台实现 |

依赖替换是迁移的**第一道门槛**。**不以改行为为目标**（C17），但 Material3 版本、Coil1→Coil3、lifecycle→KMP、navigation3 的 AndroidX→CMP 切换会产生可预期的 API/视觉差异，需在替换步骤逐一确认。

**版本基准（C20）**：CMP 依赖组合与版本**以 `desktop:feature-ui` 已验证组合为基准**（含 lifecycle 2.8.4）；第 0 步需先验证 CMP 与当前 AGP 9.0 的兼容性（真实风险点）。

## 3. 目标态分层

```
commonMain（共享层，KMP）
├── ui/
│   ├── design/         设计系统（ColorTokens / TypographyTokens / AnimationTokens / Dimens）
│   ├── components/     通用组件 + 领域组件（MusicList 全家桶等）
│   ├── pages/          纯渲染页面（PageState → UI，纯参数化）
│   └── navigation/     路由契约（见 §5.2）
├── presentation/       ViewModel + 页面状态/事件（lifecycle KMP 版）
├── domain/             已存在（shared）
├── data/               已存在（shared）
└── platform/           平台能力接口（PlaybackController / PlatformServices / expect 声明）

androidMain / desktopMain（平台侧）
├── 装配壳（Application / MainActivity / 启动）
├── expect/actual 实现（播放 / 文件 / 分享 / 权限 / 触觉 / 悬浮窗 等）
└── 平台专属资源
```

> 注：`ui` / `presentation` / `platform` 是**一个 shared-ui 模块内的三个包**，不拆多模块（上一轮 shared-presentation 拆太碎的教训）。

**依赖方向**：UI → presentation → domain/data；UI/presentation 只依赖 `platform` 接口，不依赖平台实现。

## 4. 两阶段定义

### 4.1 阶段一：提取（保行为、保结构不保「美」）

- **目标**：feature-ui 的页面/组件/VM **原样迁入 commonMain**，Android 切换到共享层后行为与之前一致。
- **允许的「丑」**：保留旧命名、旧状态组织、旧封装耦合，不要求对齐理想契约。
- **唯一硬性要求**：只做「平台 API 剥离 + expect/actual 隔离 + 依赖替换」，不做结构性重构。
- **切换与旧代码（C9/C11/C19）**：切换前**先全量截图旧版 UI + 记录关键交互清单存档**（作为后续「对比旧行为」的唯一依据）。从第一步起把 Android 入口切到新共享层，旧 feature-ui **整体冷死**：**从编译图移除（settings.gradle 移除 include），代码文件保留在仓库**作为迁移对照物——不参与编译、不参与运行，无 flag / 跳转 / 衔接机制；提取期新层未覆盖的页面表现为空白/缺页，属可接受的开发中间态。旧层删除是**可选后续动作（C16）**，Android 新层成熟后再删，长期冷死保留亦可。
- **完成标志**：
  - Android Debug + Desktop 包都构建通过。
  - Android 真机跑通（以切换前截图基线为准的人工验收，非运行时对照）。
  - 旧 feature-ui / desktop-feature-ui 代码（可选）统一删除，最终单一实现。

### 4.2 阶段二：整理（向乙契约靠拢，纯内聚）

- **目标**：在共享层上收敛出清晰分层契约：统一 State/Event、组件原子化、资源键体系理顺。
- **性质**：单轨自进化重构，不是「两套对齐」，风险远低于原方案乙。
- **原则**：只借鉴乙的「分层清晰 / 状态与渲染分离 / 组件可复用」原则，**不复用**乙的具体类型与文件（那些是为双轨切换而设计的，单轨语境下未必成立）。
- **节奏**：按痛点排序，可渐进、可暂停，不影响「已共享」这一既得价值。

## 5. 平台差异隔离策略（重点）

### 5.1 三类差异的隔离机制

| 差异类型 | 机制 | 说明 |
|---|---|---|
| domain/data 层差异（播放/扫描/标签/存储） | `expect/actual`（沿用现有） | 已有好地基，不动 |
| UI 触碰的平台「能力」（分享/文件/权限/触觉/悬浮窗/媒体会话） | 接口抽象 + Koin 注入（`PlatformServices`） | 迁移阶段把散落 Context/Intent 调用都收进这层 |
| 渲染层差异（insets/窗口/图片） | CMP 标准 API + CompositionLocal | 图片统一 Coil3 KMP；insets 用 `WindowInsets` |

### 5.2 导航策略

- **navigation3 已适配 CMP**（`org.jetbrains.androidx.navigation3:*`，见 §2.2）：feature-ui 的 `NavBackStack<NavKey>` / `Routes` 等导航类型可**随页面原样进入 commonMain**，仅需依赖替换（androidx → org.jetbrains.androidx），无需结构性改造。
- **两端宿主分工**：Android 壳用 navigation3（CMP 版）作导航宿主；Desktop 壳沿用自研 NavController。
- **阶段一原则**：页面/VM 的导航调用方式**原样搬、不改抽象**（保结构）；「统一路由契约 + `AppNavigation` 抽象」属阶段二整理方向，不在阶段一做。

### 5.3 `PlaybackController` 接口（草案）

UI 只依赖此接口，Media3 / FFmpeg 实现不外泄类型到 commonMain：

```kotlin
interface PlaybackController {
    // 状态流
    val currentMusic: StateFlow<MusicInfo?>
    val isPlaying: StateFlow<Boolean>
    val positionMs: StateFlow<Long>
    val durationMs: StateFlow<Long>
    val playbackMode: StateFlow<PlaybackMode>       // SEQUENTIAL / SHUFFLE / REPEAT_ONE
    val queue: StateFlow<List<MusicInfo>>
    val currentIndex: StateFlow<Int>
    val likeStatus: StateFlow<Set<Long>>             // 收藏的 musicId 集合
    val timerRemainingMs: StateFlow<Long?>

    // 控制
    fun play(music: MusicInfo)                        // 指定单曲
    fun playAll(list: List<MusicInfo>, mode: PlaybackMode)
    fun playOrResume()
    fun pause()
    fun seekTo(positionMs: Long)
    fun next()
    fun previous()
    fun setPlaybackMode(mode: PlaybackMode)          // 循环切换三态
    fun setLike(musicId: Long, liked: Boolean)

    // 队列管理
    fun playAt(music: MusicInfo)
    fun moveToTop(music: MusicInfo)
    fun removeFromQueue(music: MusicInfo)
    fun clearQueue()
    fun playNextInQueue(music: MusicInfo)            // 插到下一首

    // 定时器
    fun startTimer(minutes: Int)
    fun cancelTimer()
}
```

> 注：这是初稿。**冻结前**（C15）须先盘点 feature-ui 全部真实调用点——尤其 `MusicController`/`PlaybackViewModel`/`PlaylistQueueViewModel` 的实际状态与方法——按盘点把接口一次补全（含 MiniPlayer 显隐、播放历史、心动模式/智能歌单生成、桌面托盘对应能力等遗漏项），**再冻结**，不留「迁移期临时增补」。`PlaybackMode` 用领域枚举（已在 domain 层存在则复用），不得引入 Media3 枚举。
>
> 实现落点（C12）：Android 实现放 `android:app`（适配 Media3 `MusicController`）；**Desktop 实现放 `desktop:app`**（适配 FFmpeg 引擎），对称处理。盘点产出物为「调用点 → 接口成员」映射表文档，随方案提交，冻结即冻结此表。

### 5.4 `PlatformServices` 接口分组（草案）

将现有可空大杂烩 `PlatformServices` **升格**为几个内聚、非空的接口：

```kotlin
interface ShareService        { fun shareAudio(request: ShareRequest); fun shareFile(path: String) }
interface FilePickerService   { fun pickImage(onResult: (String?) -> Unit); fun pickFile(...); fun pickDirectory(...) }
interface PermissionService   { suspend fun requestAudio(); suspend fun requestNotification() }
interface HapticService       { fun perform(effect: HapticEffect) }
interface FloatingLyricsService { fun start(); fun stop() }
interface AppLifecycleService { fun minimize(); fun close() }
```

其中 `PlaybackController` 与 `MediaSessionController`（锁屏/通知控制）职责相邻但不合并：
- `PlaybackController`：UI 驱动播放。
- `MediaSessionController`：系统媒体会话/锁屏/通知的桥接（Android 强相关），**并入 `PlatformServices`**，用「接口 + Koin 注入」实现（Desktop 给空实现）。与主流 KMP 做法一致：有状态、有生命周期的平台服务用接口 + 注入，expect/actual 只留给无状态纯逻辑。

## 6. 资源迁移清单

> 这是上一轮踩坑点。本次选 **A：资源文件整体搬迁**（C13），分两个独立动作：

| 动作 | 时机 | 内容 |
|---|---|---|
| **A1 资源文件整体搬** | 地基期，一次性 | feature-ui 的 `res/` 整体迁入 shared-ui `composeResources/`，**剔除/转换 Android 专属项**（`style.xml` 主题、`@color`/attr、密度目录）；产出「资源 → CMP 路径」映射表供 A2 查用 |
| **A2 引用点重写** | 随页面/组件提取，逐页推进 | 每迁一个组件/页面，把该处 `R.string.*`/`R.drawable.*` 改为 `Res.string.*`/`painterResource(Res.drawable.*)`；迁完即删旧 feature-ui 对应资源本体（避免长期双份） |

| 资源 | 迁移方式 |
|---|---|
| 字符串 | `values/strings*.xml` → CMP `composeResources/values*/strings.xml` |
| 图标/drawable | vector 直接迁；Android 专属（`@color`/attr/style）留平台侧 |
| 颜色/主题 | 抽成 commonMain `ColorTokens`（纯数据）；动态取色走 expect/actual 或平台实现 |
| 字体 | `res/font` → CMP `composeResources/font` |
| 尺寸 | → commonMain `Dimens` 对象 |

**原则**：选 A 省的是「决定哪些资源该进」的脑力，不省「引用点重写」的体力——A2 天然随页面推进。资源键体系在阶段一锁定，CMP Resources 生成式访问（`Res.*`）是首选，不复用上一轮「IconKey/MessageKey 语义 key 拼 drawable」的隐患路径。

## 7. 提取顺序（定稿）

原则：**按可运行闭环推进**（C14），不是纯概念分层。搬家顺序由「谁先被用到 / 什么能让 Android 尽早可跑可验证」决定，而不是「概念上谁更底层」。

```
第 0 步 地基（一次性做完，不留尾巴）
   - 旧 UI 全量截图 + 交互清单存档（验收基线，C11）← 最前，须在依赖替换前拍"真旧版"
   - 依赖替换为 CMP（android:feature-ui 内完成，先跑通旧 Android；navigation3/Coil/lifecycle 一并换）
   - 依赖替换后**就地 KMP 化**（C18）：feature-ui 原地转成 KMP 模块（commonMain + androidMain），再重组为 shared-ui，避免"新起模块拷文件"的大搬家
   - 资源 A1 整体搬迁 + 映射表（§6）
   - 盘点 feature-ui 全部播放/平台调用点 → 冻结 PlaybackController / PlatformServices 接口（C15）

第 1 步 让「空的能跑」
   - 迁「设计系统 + 主题」进 shared-ui
   - **改** android:app 的 MainActivity（入口指向新层，属"改"非"迁"）
   - 建**空 NavHost**（无页面；旧 MainScreen/TabsHost 不搬，仍在冷死的 feature-ui 里）
   - 切入口 → 旧 feature-ui 从编译图移除、冷死（C9/C16/C19）
   - 真机看：Android 启动出空壳（白底 + Tab 占位，白屏可接受）

第 2a 步 让「壳与首页骨架能跑」
   - 迁「底部 Tab 壳 + 首页骨架（推荐卡片/入口）」
   - 真机看：能点开 Tab、看到首页骨架

第 2b 步 让「第一条列表主路径能跑」
   - 迁「列表页 + MusicList 全家桶」（最重，单独一步）
   - MiniPlayer 容器一并迁入，但**仅空渲染占位**（播放状态接线留第 3 步）
   - 列表项「点击播放」同样**占位空实现**（PlaybackController 真实现第 3 步才有）
   - 真机看：看到列表、能滚动

第 3 步 让「播放闭环能跑」
   - 迁「Player 页 + PlaybackController 真实接线（app 端适配 Media3）+ 队列 + MiniPlayer 接真实状态」
   - 真机看：从列表点一首歌，放出声

第 4 步 横向铺满
   - 剩余 library / playlist / settings 页面按旧依赖顺序逐个迁，每迁一个真机看一眼
   - 每页迁完即删旧 feature-ui 对应资源本体（A2）

第 5 步 Desktop 适配
   - 参考旧 CMP feature-ui，补 desktop 实现与验证

第 6 步 收尾（可选，C16）
   - 全量真机回归（对照截图基线）→ 旧 feature-ui / desktop-feature-ui 统一删除
```

> 与上一轮/原 v1 的**根本区别**：
> 1. **壳在第 1 步就迁**（而非最后），否则解2「第一步就切」无从落地。
> 2. 用「主路径（列表→播放）」代替「纯按域平铺」，让 App 尽快拥有一个完整可用闭环，而非先迁满 library 再轮到 player。
> 3. 地基（资源 + 接口）**完整做完 + 截图基线**先于任何页面，避免「占位资源」「出错了」式返工；接口冻结前先盘点全量调用点（C15）。
> 4. 每个可运行节点都有明确的「真机看什么」，不是切片，但每步都可验证。

## 8. 验证标准

- **切换前**：产出全量截图 + 关键交互清单基线（唯一"旧行为"依据）。
- **阶段一每步**：Android Debug 构建绿 + 该步骤涉及的可运行节点真机验收（对照截图基线）；旧层保持冷死、不参与运行。
- **阶段一完成**：双平台（Android + Desktop）构建绿 + Android 全量真机走查（对照截图基线）。
- **旧层删除（可选，C16）**：先完成全量真机回归，确认新层成熟后才删。
- **阶段二每步**：共享单测绿 + Desktop 渲染冒烟 + Android 真机回归。
- **全程**：不破坏 shared（domain/data）与播放引擎；不引入平台 source set 写 UI。
- **测试处置（冷死期间）**：旧 feature-ui 模块自移除编译图起，其单测/instrumented 测试**一并停跑**（不保留红测试）；随页面搬迁，对应 VM/纯逻辑测试**成对迁入 shared-ui 的 commonTest**；迁移完成后的既有失败测试（如旧 DeepLinkHandlerTest 的 Uri not mocked 问题）不迁移、随旧层删除。

## 9. 第一步落地任务（方案批准后执行）

1. **截图基线**：在 master 上全量截图旧 UI + 记录关键交互清单，存档（C11）——**最前，须在依赖替换前拍"真旧版"**。
2. **依赖替换实验**：在 `android/feature-ui` 内把 `androidx.compose.*` → `org.jetbrains.compose.*`（含 Coil→Coil3、lifecycle→KMP、navigation3→org.jetbrains.androidx），确认 Android 构建 + 运行仍可（C17，逐项确认库差异）。
3. **就地 KMP 化**：feature-ui 原地转为 KMP 模块（commonMain + androidMain），重组为 shared-ui（C18）。
4. **播放/平台调用点盘点**：盘点 feature-ui 全部 `MusicController`/`PlaybackViewModel`/`PlaylistQueueViewModel` 及散落 Context/Intent 调用，据此补全并冻结 `PlaybackController` + `PlatformServices`（C15）。
5. **资源 A1 整体搬迁** + 产出资源映射表（§6）。
6. **迁壳 + 切入口**：App 入口切到新层，旧 feature-ui 变冷死；真机看空壳可启动（第 1 步）。
