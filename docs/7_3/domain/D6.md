## 二、目标状态

做完之后 D6 应是：

- **四 Agent 编排（Master/Radio/Enrich/Hello）+ 工具注册/执行 + 确认闸门 + 策略权限 + Token 计量 + 审计/撤销 + 每日推荐刷新** 在 Android / Desktop 上行为一致、可观测、可回归；iOS 至少有一次真机/模拟器端到端核验。
- 所有"破坏性操作"（删歌单、清库、改标签、播放控制等）的**权限裁决与执行结果**双双入审计；审计屏可查、可过滤、可清空。
- 排序/分页等字符串化参数（如 `getAllMusicInfoAsList` 的 orderBy）改用**类型安全枚举**，从编译期消除"拼错键"整类问题。
- 运行时协程生命周期在 `close()`/`shutdown()` 下**全部收敛**（无泄漏、无悬空 continuation），并发集合有锁。
- `token_ledger` 有保留窗口 + 索引，监控页打开不再全表扫。
- 每日推荐触发时机明确文档化，且依赖的 Hello 副驾驶有保活兜底。

## 三、本轮发现

> 每条四项：现状（符号 + file:line）→ 影响 → 动作 → 判据。标注「亲验 / 待验」。

### D6-01 · RadioSubAgent 排序键 `"play_count"` 三端静默错误排序【亲验】
- **现状**：`RadioSubAgent.kt:955`、`RadioSubAgent.kt:1252`、`RadioSubAgent.kt:1595` 调 `musicRepository.getAllMusicInfoAsList("play_count", "desc")`。三端实现均只识别 `title/artist/album/duration/playCount`，未知键落入 `else` 分支按 `music.id` 排序：`MusicRepositoryImpl.desktop.kt:253`/`:259`、`MusicRepositoryImpl.android.kt:110`、`MusicRepositoryImpl.ios.kt:244`/`:250`。而仓库其余调用统一用 `"playCount"`（`MusicRepositoryBase.kt:129`/`:138`/`:474`；DB 列名 `Music.kt:53`）。
- **影响**：电台的 fresh/种子/兜底列表实际按 `music.id` 而非播放量排序——推荐质量受损且**无任何报错**，属静默错误行为（非崩溃）。
- **动作**：三处改为 `"playCount"`；更优方案是把 orderBy 改为类型安全 `MusicSortKey` 枚举（与 D2 同源），编译期消除拼错类问题。
- **判据**：`:shared:commonTest`（或 `:shared:desktopTest`）新增回归——先用 `getAllMusicInfoAsList("play_count","desc")` 断言返回 id 序（即复现当前错误，红），再改为 `playCount` 后断言首位为 `playCount` 最大者。落点：`commonTest`/`desktopTest`。

### D6-02 · MasterAgent.close()/shutdown() 不取消 `scope`，转发/监听协程泄漏【亲验】
- **现状**：主作用域 `MasterAgent.kt:158` `scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)`。`close():559` 与 `shutdown():543` 仅 cancel `lifecycleScope`（`:410`）与已登记的 `*RunLoopJob`，**从不 cancel `scope`**。7 个转发/监听协程全为 `scope.launch`：`radioStateForwarderJob:814`、`radioCardStateForwarderJob:820`、`radioPlaylistForwarderJob:828`、`recommendListForwarderJob:1040`、`radioSettledListenerJob:1136`、`radioPauseListenerJob:1144`、`radioTrackChangeListenerJob:1152`；它们只在 `stopRadioLocked:876-881`/`stopRadioInternal:905-910`/`stopHelloLocked:1070-1071` 中被 cancel。
- **影响**：若"App 终止/关电台"路径未先 `stopRadio`/`stopHello`（如平台 terminate 直接调 `close()`），这些协程在 `scope` 下继续存活——后台持续观察 StateFlow、占 CPU/电池，移动端可能阻止进程退出。
- **动作**：`close()`/`shutdown()` 末尾补 `scope.coroutineContext[Job]?.cancel()`（或把这些 job 收进一个统一 supervisor 一并 cancel）。
- **判据**：`:shared:commonTest`（同族 `F11LifecycleTest.kt` 已存在）新增——构造 MasterAgent、`startRadio()`、`close()` 后断言 `radioStateForwarderJob?.isCancelled == true`（需暴露该 job 或断言无残留活动协程）。落点：`commonTest`。

### D6-03 · pauseRadio/resumeRadio 不持 radio 生命周期锁，与 stopRadioLocked 竞态【亲验】
- **现状**：`pauseRadio():922`、`resumeRadio():935` 直接 `_subAgents["radio"] as? RadioSubAgent` 取引用后调用，**未进入 `radioLifecycleMutex`**；而 `stopRadioLocked():874` 持同锁并 `remove("radio")` + `shutdown()`。
- **影响**：并发 `pause` 与 `stop`（或 `resume` 与 `stop`）时，`pauseRadio` 拿到的局部 `radio` 可能是正在 shutdown 的实例，向其发 PAUSE/PLAY 命令落在半销毁状态。
- **动作**：`pause`/`resume` 也包进 `radioLifecycleMutex.withLock`，或先取引用并判 `state()` 再操作。
- **判据**：`:shared:commonTest`（同族 `MasterAgentRadioTest.kt` 已存在）新增并发用例——`pauseRadio` 与 `stopRadio` 交错运行后断言无异常、最终状态一致。落点：`commonTest`。

### D6-04 · 共享可变集合 `_subAgents` 无全局锁，跨 Agent 并发写/清空竞态【亲验】
- **现状**：`MasterAgent.kt:381` `private val _subAgents = mutableMapOf<...>()`；各 `start*` 用**各自** mutex（`enrichLifecycleMutex`/`helloLifecycleMutex`/`radioLifecycleMutex`）但写入同一 map（`:662`/`:793`/`:1022`）；`close():562`/`shutdown():548` 调 `_subAgents.clear()`。读侧 `subAgents` getter `:382` 用 `.toMap()` 但仍与写并发。
- **影响**：同时 `start` 两个不同 Agent（各自 mutex 不互斥）→ 对 HashMap 并发 `put` 不同 key 仍属结构并发修改；或 `start` 与 `clear()` 并发 → 丢失写 / `ConcurrentModificationException`。
- **动作**：对 map 的写/读/清空加一个全局 `Mutex`，或改用并发安全容器/原子替换。
- **判据**：`:shared:commonTest` 新增——并发 `startEnrich`+`startRadio` 同时 `close()`，断言 `_subAgents` 结构完整（无 CME、无丢失）。落点：`commonTest`。

### D6-05 · token_ledger 无保留/清理窗口，监控全表扫描【亲验】
- **现状**：计量只增——`TokenMeter.kt:91` `ledgerDao.insert(entry)`，无 delete 路径。DAO `TokenLedger.kt:152` `sumTotal()` 全表 `SUM(...)`；`:153` `deleteAll()`、`:84` `count()` 在生产代码**零调用方**（grep 口径：`TokenLedgerDao.deleteAll/sumTotal/count` 仅在 `F12TokenMeteringTest.kt` 被测试调用，生产调用方为空）。监控页 `AgentMonitorScreen.kt:206` `ledgerDao.sumTotal()` 每次打开全表扫。
- **影响**：表无界增长（与 R23 同判）；库大时打开监控页卡顿。
- **动作**：加保留窗口（仅保留近 N 天）并在写入/打开时清理；给 `created_at` 加索引并接上已有的 `sumByDay/sumByHour`（`:124`/`:135`，当前零调用方）。属 schema 增量 → **需并入 v10 或另开 v11**（参照 `v10-migration.md` §七）。
- **判据**：纯单测难断言"无界"；改判据为 `:shared:desktopTest` 新增——插入大量行后 `sumTotal` 耗时基线 + 调用 prune 后行数下降；并断言 `sumByDay(sinceMs)` 被 monitor 实际调用。落点：`desktopTest`；实机见 §5。

### D6-06 · 每日推荐触发时机：启动一次性 + 跨天 minuteTick，强依赖 Hello 常驻【亲验】
- **现状**：`HelloSubAgent.kt:330` `dailyRefreshLoop` 启动一次性检查；`:458` `minuteTickLoop` 检测日期变化触发 `dailyRefreshOnce()`；`:356` 今日已生成则跳过。Hello 由 `MasterAgent.initialize()` 自动 `startHello()` 常驻。
- **影响**：逻辑正确，但刷新**强依赖 Hello 副驾驶常驻**；若 Hello 被 stop 且无 UI 长期重启入口，则不再每日刷新。粒度为"日期变化"无随机时段扰动（符合预期，但需文档化）。
- **动作**：确认为预期并文档化；或补保活兜底防止 Hello 被回收后静默停更。
- **判据**：`:shared:commonTest`（同族 `UserMemoryIntegrationTest.kt`）新增——注入 `TimeProvider` 前进 1 天，断言 `dailyRecommendList` 重新生成。落点：`commonTest`。

### D6-07 · 工具执行错误不吞、PolicyGuard 判定可观测（正面确认，回应两假设）【亲验】
- **现状**：`ToolCallExecutor.kt:178-189` `catch (e: Exception)` 写 `AuditEntry(outcome="failed")` 并 `appendToolResult("（执行失败，已跳过）")`——异常被记录并回传工具结果，ReAct 循环继续（不挂起、不静默丢失）；`CancellationException` 正确上抛（`:178`）。`PolicyGuard.kt:49`/`:59`/`:81` 每次决策（Phase0/1/2）均 `auditLog.record(AuditEntry(...))`。且 `SharedModules.kt:136` 已传 `chatAuditLog = get()`，故工具执行结果**确实入审计**（非 null）。
- **影响**：假设"ToolCallExecutor 错误被吞掉""PolicyGuard 判定不可观测"均**不成立**——破坏性操作的结果与裁决均可经 `agent_audit_log` 追溯。
- **动作**：保持；仅建议在 `ToolCallExecutorTest.kt` 已有用例基础上补一条"异常路径写 audit + 不抛"的断言固化。
- **判据**：已有 `:shared:commonTest` `ToolCallExecutorTest.kt` 可承载该断言。落点：`commonTest`。

### D6-08 · 确认闸门 DialogManager 用毫秒时间戳当 key，同毫秒两次确认互相覆盖【亲验】
- **现状**：`shared-ui/.../ui/common/dialogs/controller/DialogManager.kt:59` `val id = nowEpochMillis()` 作 `pendingConfirms`（`mutableMapOf<Long, PendingConfirm>`，`:46`）的 key；`:67` `pendingConfirms[id] = pending`。同毫秒两次 `requestConfirm` 得相同 id，后写覆盖前写，前一次的 `continuation`（`:63`）永不 `resume` → 对应工具调用永久挂起。`DialogConfirmGateAdapter.kt:38` 经 `requestConfirm` 接入确认链。
- **影响**：极低频但后果严重——一旦同毫秒并发两条确认链（如主对话确认 + 电台仲裁确认），其中一条 continuation 永不 resume，工具调用挂死。
- **动作**：key 改用单调 `AtomicLong` 计数器（而非时钟），消除碰撞。
- **判据**：`:shared-ui:testAndroidHostTest` 新增——构造两条并发 `requestConfirm`，断言各自 continuation 均被 resume 且 id 互异（改后用计数器即满足）。落点：`testAndroidHostTest`。

## 四、四项横查

### 4.1 数据正确性
- `play_count` 排序键错误（D6-01）是**唯一**确认的数据正确性缺陷：静默错序、无报错。其余 agent 表（`agent_task`/`agent_audit_log`/`agent_message`/`hello_card_cache`/`hello_report_narrative`/`forgotten_delivery`/`token_ledger`，schema 见 `9.json:493-1009`）结构存在、字段完整。
- `token_ledger` 只增不清（D6-05）→ 长期数据正确性无碍，但体积/查询正确性需保留窗口兜底。
- 审计链路数据正确：`PolicyGuard` + `ToolCallExecutor` 双写入 `agent_audit_log`，且 `chatAuditLog` 已接线（`SharedModules.kt:136`）。

### 4.2 并发与生命周期
- 三处隐患：**`scope` 不取消致协程泄漏**（D6-02）、**`_subAgents` 无全局锁**（D6-04）、**pause/resume 不持 radio 锁**（D6-03）。三者均为 commonMain 逻辑缺陷，三端同受影响，非平台差异。
- `ReActLoop` 的 `stepBudget`、各 SubAgent 的 `runLoop` 自带 `while(isActive)` 退出机制，单 Agent 内部生命周期正常；问题集中在 **MasterAgent 顶层 teardown 与共享集合**。
- F11 保活：`AgentKeepAlivePort` 仅 Android 实现，Desktop/iOS `getOrNull()→null` 静默跳过（`SharedModules.kt:141`）→ 后台生命周期在两端无保障。

### 4.3 可观测性
- **判定可观测**：`PolicyGuard` 每次决策写 `AuditEntry`（reason 含 phase/level/trust），`ToolCallExecutor` 执行结果写 audit，均经 `RoomAuditLogAdapter` 落 `agent_audit_log`（Android/Desktop/Ios Modules 均注册）。
- **审计被消费**：`AuditLogScreen.kt` 经 `AuditLogViewModel` 展示并支持 radio/reorder 过滤；`AgentMonitorScreen.kt:206` 读 token ledger。→ "是否有人消费"= **是**。
- **但消费侧 DI 未注册**：`AuditLogViewModel` 不在任何 Koin module（AGENTS §三），靠 `remember { ... }` 构造。属横切/依赖注入问题，留横切线；本域仅记录其**表现后果**——在 iOS 上因"DI 无图校验、纯懒加载"（AGENTS §八.4），进审计页才可能因缺失依赖崩（待验）。
- **计量可观测缺口**：`token_ledger` 的 `measured` 真假值 UI 不区分（ROADMAP:255）；看板仅"按 Agent + 累计"两格，端点/模型/分时明细零调用方。

### 4.4 测试覆盖
- **已有** agent 运行时测试（grep 口径：`shared/src/commonTest` + `shared/src/desktopTest` 下 `agent/**Test.kt` 约 7 个文件）：`F11LifecycleTest`、`MasterAgentRadioTest`、`ReActLoopTest`、`ToolCallExecutorTest`、`EngineGuardTest`、`F12TokenMeteringTest`、`UserMemoryIntegrationTest`。覆盖了编排、生命周期、策略、计量、ReAct、工具执行。
- **缺口（纯逻辑但未被测）**：D6-01 排序键、D6-02/03/04 的并发/teardown、D6-06 跨天刷新、D6-08 确认 key 碰撞——均无对应断言。
- **iOS 零机器反馈**：D6 运行时全在 `shared` commonMain，经 `shared-ios` 聚合；本机不编 iOS（AGENTS §二），上述行为在 iOS 上**无任何自动验证**，全部待验（见 §5）。
