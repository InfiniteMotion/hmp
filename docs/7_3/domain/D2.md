## 二、目标状态

做完之后，本域应满足：

1. **一条扫描流水线，三份数据源。** `commonMain` 定义 `ScanSource`（返回 `List<ScannedMusicFile>`）与统一的落库器（事务 + upsert + 软删除保留）；三个平台只实现"从哪儿拿到文件"。Android 不再有"两条扫描实现"（D2-10），桌面/移动不再各自重抄一遍 `performMusicScan`。
2. **软删除只由用户决定。** 任何扫描路径都是 upsert 语义：`isDeleted` 的唯一成因是"用户在 UI 上隐藏了它"，扫描结果既不置位也不清位；全库重建必须是单事务。
3. **扫描永不损号。** 收藏、播放次数、歌词、AI 富化文案（`musicExtra` + `userInfo`）属于用户资产，全量重建不得触碰 —— 验收口径是"重扫一次之后，用户的喜好没有归零"。
4. **格式与元数据的单一真源。** 格式白名单在 `commonMain` 一处常量；`MusicMetadata` 的字段契约在三端同样成立（含 iOS 的 year/genre/track），达不到的端要么补齐要么显式标注"本端不提供"，不留静默的空值。
5. **排序键是类型不是字符串。** `enum class MusicSortKey { TITLE, ARTIST, ALBUM, DURATION, DATE_ADDED, PLAY_COUNT }` + 方向枚举，非法/未知组合在编译期或入口处拒绝，不留 `else` 兜底。
6. **查询有护航。** `music` 表在 `isDeleted`、`title`、`artist`、`album`、`duration` 上有索引，`musicLabel` 在 `label`/`type`/`source` 上有索引；`getAllArtistsSummary` / `getAllAlbumsSummary` / `getSimilarSongsByWeightedLabels` 走 SQL 聚合，不再全库载入。
7. **搜索语义与 UI 承诺一致。** 覆盖 title/artist/album，用户输入 `_` `%` 走字面匹配。
8. **每端能力自陈。** iOS 标签写入现阶段做不到，就由平台的 `MusicTagEditService` 自陈能力并向 UI 降级（禁用/隐藏保存），而不是提供必然失败的路径。

### D2-01 · 全量扫描是「三张表 deleteAll + 分批 insert」，无事务，且会带走用户资产

**[亲验]**

- 现状：`loadMusicFromDevice()` 在三端同构 —— Android `MusicRepositoryImpl.android.kt:150-152` 调 `musicDao.deleteAll()` / `musicExtraDao.deleteAll()` / `userInfoDao.deleteAll()`，随后 `:154-164` 分 50 条一批 `insertAll`；Desktop `MusicRepositoryImpl.desktop.kt:83-95`；iOS `MusicRepositoryImpl.ios.kt:78-90`。三处均无 `@Transaction`（全仓 `withTransaction` / `inTransaction` 0 命中口径见 `AGENTS.md` §八.5）。被删的三张表不只是索引：`musicExtra` 承载 `lyrics` + 富化文案 6 列（`Music.kt:26-45`），`userInfo` 承载 `liked` / `playCount` / `lastPlayed`（`Music.kt:47-58`）。
- 影响：进程被杀 / IO 异常在 delete 与 insert 之间发生时，库停在"半成品"状态且对外表现为**空曲库**（UI 只显示 0 首，无异常态 ——`LibraryViewModel.fullRescan:218-237` 的 `.onFailure` 只在抛异常时才进 `UiState.Error`）。即使成功，`playCount` / 收藏 / 已富化文案也被清零，Enrich 管道会重新把所有歌判为未富化（`MusicExtra.isGetExtraInfo` 默认值 false，`Music.kt:37`）。
- 动作：
  1. `AppDatabase` 暴露一个事务上下文（Room 的 `withTransaction`），把「清空 + 写回」包进单事务；
  2. 语义从"清空重灌"改为 **upsert**：缺失的才 mark deleted，新增的才 insert，`musicExtra` / `userInfo` 的既有行**保留**（只补缺列，不整行覆盖）。
- 判据：`:shared:desktopTest`（`MusicDaoTest` / 新增 `MusicScanPersistTest`，用 `createTestDatabase()` 装配，`shared/src/desktopTest/kotlin/com/hmp/test/db/TestDatabaseProvider.kt`）。断言：① 预置 3 首 + `userInfo.playCount=7` + `musicExtra.lyrics="x"`，跑一次全量重建 mock 场景，结果的 `playCount` 仍为 7、`lyrics` 仍为 "x"；② 在第 2 批写入前抛 `CancellationException`，事后 `musicDao.getMusicCount().first()` 等于重建前的数量（不出现半空库）。

### D2-02 · 全量重建会抹掉软删除标记，「隐藏的歌」在下次重扫后全部复活

**[亲验]**

- 现状：`performMusicScan()` 构造实体时不带 `isDeleted`（默认 false）——Desktop `MusicRepositoryImpl.desktop.kt:194-204`、Android `MusicRepositoryImpl.android.kt:435-445`、iOS `MusicRepositoryImpl.ios.kt:184-192`。而 `loadMusicFromDevice()` 先 `deleteAll()`（已删除的行也一并消失），`getDeletedMusicIdsGroupedByFolder()` 依赖 `WHERE isDeleted = 1`（`Music.kt:113`）取回隐藏集合。二者叠加：**隐藏标记的唯一载体被抹除**。
- 影响：用户隐藏整个文件夹 → 任意一次「全量重建」（`LibrarySettingsScreen.kt:436-444` 的 destructive 卡，以及 D2-03 里被静默触发的那些路径）后，该文件夹的歌全部回到曲库与歌单（`playlist_item` JOIN 只看 `music.isDeleted`，`PlaylistItem.kt:45`）。「隐藏」这一用户意图没有任何跨扫描的持久化手段。
- 动作：把"用户隐藏"与"文件不存在"两种 `isDeleted` 成因分开 —— 落库时 `isDeleted` 不被扫描结果覆盖；因文件缺失而软删除的行保留一份可分辨的记录（哪怕是 `UserInfo`-侧的标记列，随 v10 迁移一起做，见 `domain-baseline.md` §三·批一）。
- 判据：依赖 D2-01 的动作把扫描器变成可注入的 `ScanSource`；随后在 `:shared:desktopTest` 断言：预置 `music(id=1, path="/a/1.mp3", isDeleted=true)` → 以 `ScanSource` 返回同一条 `/a/1.mp3` 跑一次全量落库 → `musicDao.getDeletedMusicIdAndPath()` 仍含 id=1。

### D2-03 · 改动扫描目录 / 屏蔽目录会静默触发一次破坏性全量重扫

**[亲验]**

- 现状：`LibraryViewModel.updateScanDirectoryConfig:162-173` —— `addScanDirectory` / `removeScanDirectory` / `addBlockedDirectory` / `removeBlockedDirectory`（`:144-160`）四条都收敛到这里，末尾无条件调用 `fullRescan()`（`:171`），而 `fullRescan():218-237` 走的正是 D2-01 那条 destructive 路径。UI 侧：「全量重建」卡片**单独有**二次确认弹窗（`LibrarySettingsScreen.kt:436-444,468-491`），但目录增删**没有任何确认**（`:629-631,720-727` 的「移除」直接回调 `onRemove`）。
- 影响：用户只是"屏蔽一个铃声文件夹"，结果收藏数、播放次数、歌词、已富化文案全部被清。这条把 D2-01 从"用户点了 destructive 按钮才可能发生"升级为"日常设置操作就会发生"。
- 动作：目录变更改走 `syncMusicFromDeviceIncremental()`，并对"因新目录规则被排除的曲目"显式 mark deleted；在真正需要全量重建的场景保留确认弹窗。
- 判据：`:shared-ui:testAndroidHostTest`。前置动作：`LibraryViewModel` 的第 8 个构造参数是具体类 `MasterAgent`（`LibraryViewModel.kt:65`），测试不可构造，**先把 `masterAgent.onLibraryMutated()` 这一处收窄成一个单方法端口**（其余依赖不变，仍由 Koin 注入真实实现）。随后在测试里注入假 use case + 假端口，断言 `addScanDirectory("/x")` 之后：`loadMusicFromDeviceUseCase` 调用次数 == 0，`syncMusicFromDeviceIncrementalUseCase` 调用次数 == 1。

### D2-04 · 领域模型不承载 `isDeleted`，Mapper 往返会把已删除的曲静默复活（潜伏）

**[亲验]**

- 现状：数据层三张实体都有 `isDeleted`（`Music.kt:23`、`Music.kt:44`、`Music.kt:57`），领域模型**一个都没有**（`MusicModels.kt:6-14`、`MusicModels.kt:16-35`、`MusicModels.kt:92-101`），`MusicMapper` 的六个方向也都不搬运它（`MusicMapper.kt:21-29,31-39,41-58,60-77,79-88,90-99`）。因此 `Music.toEntity()` 出来的实体 `isDeleted` 恒为默认 `false`。
- 影响：**当前无真实调用点，属潜伏风险而非当班故障** —— grep 口径 `\.toEntity\(\)`（限定 `shared/src/commonMain`），被生产代码真正调用的只有 `MusicLabel.toEntity`（`MusicRepositoryBase.kt:196,216`）与 `PlaybackHistory.toEntity`（`MusicRepositoryBase.kt:432`）；`Music` / `MusicExtra` / `UserInfo` / `MusicInfo` 四个 `toEntity` 零生产调用。风险在于它是一枚已经上膛的雷：任何人按 README 的直觉写一条"取 domain → 改字段 → 落 entity"的路径，就会把删除的行复活。`MusicMapperTest` 里命名为 `*_roundTrip_preservesData` 的两个用例（`MusicMapperTest.kt:69-82`、`MusicMapperTest.kt:152-161`）**起点是 domain 对象**，天然覆盖不到这处丢失。
- 动作：二选一 ——（推荐）删掉这 4 个零调用的 `toEntity`（保持"落库只经由扫描器与各 update 语句"的现状），或在本域决定"领域模型应当知道自己在不在曲库里"时给三个模型补 `isDeleted` 并同步 mapper。无论选哪条，都要把结论写进模型的 KDoc。
- 判据：`:shared:desktopTest`（若选"删除死码"，判据是编译期：commonTest 中 `MusicMapperTest` 剩余用例全绿且 `Music.toEntity` 在生产源集无引用；若选"模型承载"，判据是新加用例断言 `entity(isDeleted=true).toDomain().toEntity().isDeleted == true`）。本条不入施工队列，除非有人开始写 domain→entity 回写路径。

### D2-15 · `getSimilarSongsByWeightedLabels` / `getAllArtistsSummary` / `getAllAlbumsSummary` 全库载入后逐行查（N+1 与 O(N) 内存聚合）

**[亲验]**

- 现状：

### D2-16 · 封面文件名规则在 Kotlin 与 Swift 各写一份，且符号处理不一致

**[亲验]（源码级；是否实际错位**待验**）**

- 现状：同一条"路径 → 封面文件名"的规则有两份跨语言实现：
  - Kotlin（`DeviceMusicScanner.desktop.kt:112-119` 与 `DeviceMusicScanner.ios.kt:108-115`，两份逐字相同的 FNV-1a 64 位），返回 `hash.toLong()` ——**可能为负数**，文件名 `cover_$id.jpg`（`desktop.kt:102`）。
  - Swift（`ArtworkExtractor.swift:240-249` 的 `stableHash`，同样 FNV-1a），但在计算文件名时用 `abs(musicFilePath.stableHash)`（`ArtworkExtractor.swift:26,192,216`）—— **恒为非负**。
- 影响：**当前不会真的错位**，因为两端各自只写自己沙盒/家目录下的 `covers/`，且 `albumArtUri` 各自由自己那一侧产生。但这条规则的重复实现 + 符号分歧，会让任何"用 Kotlin 侧算出的 id 去拼 iOS 封面路径"的动作立刻错位 —— 例如将来做封面缓存清理、或在备份恢复里迁移封面文件：hash 为负的那部分路径会得到 `cover_-123.jpg` 与 `cover_123.jpg` 两种名字。
- 动作：把封面落盘抽成一个 `CoverArtStore`（`store(path, bytes) -> uri`），命名规则只有一处实现；Swift 侧继续只负责"从文件里抽出字节"，文件名由 Kotlin 侧给出。
  > 附注（不作为本条结论）：`ArtworkExtractor.swift:50-66` 的 `extractAsync` 是否有 Swift 侧调用点，本轮未核到，不把它判为死码。
- 判据：**[待验] 需 macOS + iOS 模拟器/真机**（命令同 D2-11）。验完看什么：在 Documents 放同一首带封面的 mp3，分别由 Kotlin 扫描管道与 Swift `savedCoverPath(for:)` 算出文件名并打日志，断言两者字符串**逐字相同**（重点是能取到负 hash 的路径 —— 用一条 FNV 值为负的路径样本，例如先把 `abs` 分支验证掉再去掉 `abs` 复跑一次）。

### D2-17 · 封面缓存"存在即跳过"，换过封面的文件永远显示旧图

**[亲验]**

- 现状：Desktop `DeviceMusicScanner.desktop.kt:98-110` —— `if (!coverFile.exists()) { coverFile.writeBytes(data) }`（`:103-105`），而文件名由**路径的 hash** 决定（`:101` 的 `generateStableId(filePath)`），与文件内容无关。iOS 同构：`ArtworkExtractor.extractAndSave:36-38` 若 `fileExists` 就直接 return。Android 不落盘（走 `content://media/external/audio/albumart`，`MusicRepositoryImpl.android.kt:396-399`），但那意味着它依赖 MediaStore 的索引 —— 而 `MusicTagEditor.desktop.kt:43` 的 `AudioFileIO.write(audioFile)` 之后，全仓**没有任何触发 MediaStore 重新索引的通知路径**（grep 口径 `MediaScannerConnection\|scanFile\|sendBroadcast(.*MEDIA_SCANNER`，0 命中）。

### D2-18 · SearchScreen 每次按键触发**两次** `searchMusic`，无防抖，存在旧结果覆盖新结果的风险

## 四、四项横查

### 1. 数据正确性

- **软删除不变量只存在于数据层。** 四张相关表都有 `isDeleted`，领域模型一个都没有（`MusicModels.kt:6-14,16-35,92-101`），Mapper 六向全丢（D2-04）。当前零调用点让它暂时安全，但它同时意味着：**没有人可以在 domain 层表达"这首歌还在不在曲库里"**，`RemoveFromLibraryUseCase` / `RestoreToLibraryUseCase`（两个只有 16 行的转发壳）也无法做前置校验。
- **隐藏状态不跨扫描存活**（D2-02）。这是本域最贴近用户数据丢失的一条：用户意图（"别给我看这个文件夹"）的唯一载体是一条 `UPDATE` 语句的结果，而该结果会被下一次全量重建抹掉，而触发全量重建的路径里有一条正是 D2-03 那样的日常设置操作。
- **全量重扫不带事务也不保护用户资产**（D2-01）。`musicExtra.lyrics` + 富化文案 6 列 + `userInfo.playCount/liked/lastPlayed` 都是用户侧长期积累，被 `deleteAll()` 一并带走没有确认。
- **搜索语义与 UI 承诺不一致**（D2-05），且这条不一致被一条"替身更强"的测试挡住了（D2-06）。
- **元数据完整度按平台分叉**：`year/genre/track` 三端 KMP 侧的 `MusicMetadata`（`MusicTagParser.kt:8-21`）承诺了这三个字段，iOS 侧恒 nil（D2-11）；更彻底的是它们**根本没进数据库**（`musicExtra` 表无 year/genre/track 列，`Music.kt:26-45`），所以即便三端都读得到，也无法用它们排序/筛选 —— 这直接导致专辑详情页只能按标题拼音排（`MusicRepositoryBase.getMusicListByAlbum:121-126`），按音轨号排专辑曲目这条路**当前不存在**。

### 2. 并发与生命周期

- **扫描的重入没有保护。** 三端的 `isScanning` 是普通 `MutableStateFlow`（`MusicRepositoryImpl.android.kt:131`、`desktop.kt:72`、`ios.kt:67`），写值为 true 之前没有任何 CAS；且 `DeviceMusicScanner.{desktop,ios}` 各持有**另一份** `_isScanning`（`DeviceMusicScanner.desktop.kt:9`、`ios.kt:15`），两处状态互不相干。同时点「增量扫描」和「全量重建」会得到两个并发写事务 —— 叠加 D2-01 的无事务 `deleteAll`，结果可以是任意交错。
- **扫描器的可变静态状态。** `DeviceMusicScanner.desktop.kt:12-13` 的 `scanDirectories` / `blockedDirectories` 是 `object` 上的可变集合，由 `MusicRepositoryImpl.desktop.performMusicScan:181-185` 在每次扫描前 `clear()` + `addAll()`。同一进程内若两个扫描并发（见上一条），目录配置会互相踩踏；且这份状态对 ViewModel 完全不可见。
- **iOS 桥的可变注册点。** `MetadataParserBridge.registered`（`MusicTagParser.ios.kt:38`）与 `ArtworkBridge.registered`（`DeviceMusicScanner.ios.kt:123`）都是非 `@Volatile` 的 `var`，在 `AppDelegate.swift:21-22` 启动时写、在工作线程（`DeviceMusicScanner.ios.kt:19` 的 `Dispatchers.Default`）读。K/N 内存模型下没有 happens-before 保证（仓库里有 `platform/Volatile.kt` 这个基础设施可以用而这里没用）。是否会在真机上读出旧值取决于时序，标 **[待验]**。
- **Android 的 `MediaMetadataRetriever` 与扫描并行度。** `MusicRepositoryImpl.android.kt:420-428` 用 `Semaphore(4)` 并发解析，这一步是好的；但 `retriever` 实例在 `:303` 那次 fallback 里每首歌 new 一个并在 finally 里 release，若在并行块里被触达会有 4 个 retriever 同时活动 —— 尚可接受，仅记录。
- **`LibraryViewModel._allMusic` 是拉模型，不是流。** `getAllMusic()` / `refreshMusicList()` / `fullRescan()` 手动往 `MutableStateFlow` 里赋值（`LibraryViewModel.kt:80-90,197-237`），而 DAO 侧本来就提供了流式的 `getAllMusicInfoSortedByTitle` / `getAllMusicInfoSortedById`（`Music.kt:322,327`）—— 这两个查询全仓零消费（grep 口径 `getAllMusicInfoSortedBy`，命中仅 `Music.kt:323,327` 两处声明）。结果是：**标签编辑成功写库后，曲库列表不会自动刷新**（`updateMusicTags` 只改 DB，`MusicRepositoryBase.kt:304`），导致用户退回 Gallery 看到的仍是旧标题。

### 3. 可观测性

- **扫描侧有日志。** `loadMusicFromDevice` / `syncMusicFromDeviceIncremental` 三端都有 `HmpLog.i/e`（`MusicRepositoryImpl.desktop.kt:81,97,100,172`；Android `:168,243`；iOS `:76,92,95,167`），Android 还对"目录过滤生效"打了 debug（`MusicRepositoryImpl.android.kt:367-371`），`LogTag.DataMusicRepo` / `LogTag.libraryMetadata` / `LogTag.libraryArtwork` 三者分工明确。这一项做得对。
- **缺"为什么是空的"的可观测性。** Android 若 `contentResolver.query` 返回 null（`MusicRepositoryImpl.android.kt:377` 的 `?.use {}` 静默跳过），或 Desktop/iOS 的扫描根一个都不存在（`DeviceMusicScanner.desktop.kt:53-59` 的 `filter { it.exists() }`），最终表现在 UI 上是"0 首"，中间不产生任何一条日志。UI 侧已有权限提示条（`LibrarySettingsScreen.kt:127-129`）覆盖了"无权限"这一个原因，其余原因（目录不存在、权限给了但 MediaStore 还没索引）没有对应信号。
- **Agent → 曲库调用缺乏耗时信号。** D2-15 里那两条全库载入方法没有日志也没有耗时打点，卡片生成慢时无法归因到 DB 层。

## 六、刻意不做（带改判条件）

1. **不碰 `musicLabel` 的主键设计**（`(musicId, label)`，`MusicLabel.kt:13-16`，缺 `type`）。它意味着同一首歌的同一个标签名只占一个槽位，不能同时挂两个不同 Category —— 这是一个有意的建模选择（"同一事实只有一个槽位"），现有 agent 溯源规则建立在其上（`MusicRepositoryBase.kt:189-207` 的所有日志都在按槽位说话）。**改判条件**：出现真实需求要在同一曲目上挂同一 LabelName 的两个 Category。
2. **不补 FTS / 拼音列。** 当前搜索在叠加 D2-07 的索引之后，对本地几千首的量级已经足够；引入 SQLite FTS5 会带来 Room KMP 三端构建差异 + 迁移负担。**改判条件**：有用户报告库大于约 2 万首且搜索有可感延迟，或出现"搜索要支持拼音首字母"这类需求（`MusicListConfig.kt:227` 的 `indexJumpConfigForOrderBy` 目前是按内存分组实现的，并未依赖 FTS）。
3. **不做(a) 曲目级 array of `year/genre/track` 入库。** 这一项的问题是现实且清晰的（`EditMusicTagsViewModel` 每次都从文件重读这三个字段，`:104-111`），但它需要一次 v10 schema 变更。**改判条件**：与 `domain-baseline.md` §三 批一的其他 schema 需求一起评审 —— 若 v10 已经因为别的原因开了，就顺带带上；不为它单独开一次迁移。
4. **不删 `"play_count"` 之外的历史排序键。** `PlaylistAlgorithms.kt:50,156,187` 传的是 `"id","asc"`（大小写混合），`RadioSubAgent` 传 `"play_count","desc"`，`GetAllMusicUseCaseTest` 传 `"artist","DESC"` —— 这些在 D2-08 改成枚举后会被编译器一次性找出来。现在不逐个修补，等枚举到位。
5. **不为 `DeviceMusicScanner.android.kt` 写测试后再删。** D2-10 的结论是"删"，给它写测试等于给将死的代码付双倍成本。**改判条件**：如果选择了另一条动作（给它注入 Context 并把内联逻辑搬回去），那它必须同时获得至少一条 `:shared:androidMain` 侧的测试 —— 但 `shared/src` 下不存在 `androidHostTest` 源集（`AGENTS.md` §八.12），届时需要先解决源集问题，这本身就得单独立项。
6. **不评估 `ArtworkExtractor.extractAsync` 是否死码。** grep 未核到它的调用点，但也未核到"无调用"的确定证据（跨 Swift 侧引用关系未在本次范围内穷尽）。挂在这里，等有人动 iPhone 封面路径时顺手核。
