## 二、目标状态

做完之后，D5 应该是：

1. **一个时间口径**。「小时」「天」「最近 N 天」在本域内只有一套定义，且这套定义同时被 SQL 与 Kotlin 侧遵守：`playedAt` 的分桶统一走**本地时区**，Kotlin 侧不再出现 `epochMs / 3_600_000 % 24` 这类自算 UTC 小时。
2. **窗口参数被方法体真正使用**。任何签名里带 `days` / `windowDays` 的聚合方法，该参数既参与窗口下界计算、也（在除法语义里）参与除数；`-1`（全部）在三端所有维度上落到同一个下界（`daysToCutoffMs`），不再被 `coerceAtLeast(1)` 悄悄夹成 1 天。
3. **三端 `playDuration` 同义**。三端在「自然播完」与「中途切走」两种结局下写入的 `playDuration` 是同一个量（累计实听毫秒），且暂停—恢复不中断累计。统计页的完播率 / 跳过率 / 总时长在三端可比。
4. **退出不丢尾部数据**。Desktop 退出路径上所有落库调用在进入 `exitApplication()` 前被结构化地等待完成（或显式 flush + join），尾部 0~30 秒与最后一条会话结算不丢。
5. **热力图名实相符**。要么把图做成真实日历网格（缺失日期补零、按真实星期对齐列），要么把文案从「全年热力图」改成实际口径；当前「35 个有听歌的天 + 假的星期表头」两头不靠。
6. **表有索引、有边界**。`PlaybackHistory` 对 `playedAt`（窗口扫描）与 `musicId`（按歌聚合）建索引；证据表有保留窗口或清理入口，批量写入走单个事务。
7. **失败可观测**。窗口聚合失败必须留一条 `HmpLog.w`，与「窗口内确实没数据」在日志里可区分；UI 空态不再同时表示这两种情况。
8. **每个数都有判据**。上表 18 项里标注「部分 / 空壳」的每一格，都有一条能在本机跑的断言钉住口径。

## 三、本轮发现

### D5-01 「小时」指标两套时区：SQL 走 localtime，Kotlin 侧自算 UTC

- **现状（亲验）**：
  - SQL 侧用 `strftime(..., 'localtime')` 取本地小时 / 本地月日：
    `shared/src/commonMain/kotlin/com/hmp/data/database/PlaybackHistory.kt:113`
    （`CAST(strftime('%H', playedAt / 1000, 'unixepoch', 'localtime') AS INTEGER) AS hour`）
    `shared/src/commonMain/kotlin/com/hmp/data/database/PlaybackHistory.kt:101`
    （`strftime('%m-%d', playedAt / 1000, 'unixepoch', 'localtime') = :mmdd`）
  - Kotlin 侧用整除自算，**结果是 UTC**：
    `shared/src/commonMain/kotlin/com/hmp/data/repository/MusicRepositoryBase.kt:1221`
    `private fun hourOf(epochMs: Long): Int = ((epochMs / 3_600_000L) % 24).toInt()...`
    `shared/src/commonMain/kotlin/com/hmp/data/repository/MusicRepositoryBase.kt:1223`
    `private fun dayKey(epochMs: Long): Long = epochMs / (24L * 3600 * 1000)`
  - 两条路径都被真实消费：`hourOf` 喂 `getBehaviorSnapshot` 的 `hourHistogram`（`MusicRepositoryBase.kt:1092`），`dayKey` 喂 `activeDays`（同文件 `:1093`）；DAO 的 localtime 版喂 `getHourlyDistribution`（`:1005-1010`）与 `getMusicIdsPlayedOn`（`:967-970`）。
  - 同型第三处（不属本域但同源，供交叉参考）：`shared-ui/.../ui/agent/chat/ChatAgentGateway.kt:256` 也写 `((currentTimeMillis() / 3_600_000L) % 24).toInt()`，而仓库里已有本地时区的 `expect fun currentHour()`（`shared/src/commonMain/kotlin/com/hmp/data/util/DateFormats.kt:15`，三份 actual 都在）。
- **影响**：同一台设备、同一份 `PlaybackHistory`，「时段分布」页给用户看的峰值小时（本地）与写进画像行为快照的 `hourHistogram`（UTC）相差一个时区偏移；在 UTC+8 上差 8 小时，足以让「夜猫子」判定整段错位。同理「今日播放过的歌」按本地月日匹配，而 `activeDays` 按 UTC 日界切分，跨零点的一小时会被算进相邻两天。
- **动作**：本域统一到**本地时区**。把 `hourOf` / `dayKey` 改为走平台本地时区（复用 `DateFormats` 已有的 `currentHour()` 那套 expect/actual 思路，补 `hourOfDay(epochMs)` / `localDayKey(epochMs)`），或反过来把 DAO 的 `strftime` 去掉 `'localtime'` 并让 UI 明示「UTC 口径」——二选一，不许并存。同时确认 `strftime(..., 'localtime')` 在三端 SQLite 驱动上的取值与 `todayDateString()` 一致（见 §五 验证缺口）。
- **判据**：`:shared:desktopTest` 新增 `HourBucketParityTest`：插一条 `playedAt` 落在本地时区 23:30、UTC 15:30 的记录，断言 `PlaybackHistoryDao.getHourlyDistribution(since).single().hour` 与 `MusicRepositoryBase` 暴露出的小时桶函数返回**同一个值**；再插一条跨 UTC 日界但同本地日的记录，断言 `getMusicIdsPlayedOn(todayDateString())` 与本地 `dayKey` 口径一致。
  Desktop 生产与测试同为 `BundledSQLiteDriver`（`shared/src/desktopMain/kotlin/com/hmp/data/database/DatabaseBuilder.desktop.kt:34`），故该用例能代表 Desktop 生产。

### D5-02 「全部」时段在时段维度被夹成 1 天，与其余四个维度不一致

- **现状（亲验）**：
  - `NarrativeTimeRange.ALL.toDays() = -1`：`shared/src/commonMain/kotlin/com/hmp/domain/agent/card/SlideModels.kt:40-46`。
  - 其余四个维度走 `daysToCutoffMs(days)`，`-1` 映射到 10 年前：`SlideModels.kt:49-52`；调用点 `MusicRepositoryBase.kt:1144 / 1161 / 1170 / 1176 / 1188`。
  - 时段维度**不走** `daysToCutoffMs`，而是自己算并 `coerceAtLeast(1)`：
    `shared/src/commonMain/kotlin/com/hmp/data/repository/MusicRepositoryBase.kt:1006`
    `val sinceMs = currentTimeMillis() - windowDays.coerceAtLeast(1) * 86_400_000L`
    → `windowDays = -1` 时 `sinceMs = now - 1 天`。
  - 调用链闭合：`UserUsageDataViewModel.kt:97`（`val days = range.toDays()`）→ `:116`（`repo.getHourlyDistribution(days)`）。
  - 同型：`getBehaviorSnapshot` 的 `sinceMs`（`MusicRepositoryBase.kt:1088`）也用 `days = windowDays.coerceAtLeast(1)`。当前唯一调用方传的是 `ProfileConfig.BEHAVIOR_WINDOW_DAYS = 90`（`ProfileModels.kt:79`），尚未踩到，但同一处写法随时可被 `-1` 触发。
- **影响**：用户在使用数据页把时段切到「全部」，概览 / 口味 / 排行 / 最近四个维度都给 10 年口径，唯独时段柱图只画最近 24 小时，且页面顶部的时间标签（`:142` `时段分布（${timeRange.zhName()}）`）仍写着「全部」。UI 宣称的时间范围与数据真实范围矛盾。
- **动作**：`getHourlyDistribution` 改用 `daysToCutoffMs(windowDays)`；把 `coerceAtLeast(1)` 这种静默夹取从窗口计算里去掉（真正需要防御的是 `days <= 0 && days != -1`）。`getBehaviorSnapshot` 同步处理。
- **判据**：`commonTest` 新增纯函数用例：`NarrativeTimeRange.ALL.toDays() == -1` 且 `daysToCutoffMs(-1) < daysToCutoffMs(365)`；`:shared:desktopTest` 在 `WindowedAnalyticsDaoTest` 旁补一条：用 `days = -1` 调 `getHourlyDistribution` 与 `getWindowedAnalytics`，断言两者返回的行集合覆盖**同一批**种子记录（种子里放一条 3 天前、一条 2 年前的记录，两者都必须出现）。

### D5-03 `getAvgDailyListeningMinutes(days)` 的 `days` 只当除数，不是窗口

- **现状（亲验）**：`shared/src/commonMain/kotlin/com/hmp/data/repository/MusicRepositoryBase.kt:992-997`
  ```
  val all = listeningDurationDao.getAllDurations()      // 全表
  if (all.isEmpty()) return 0f
  val totalMs = all.sumOf { it.duration }               // 全表求和，无任何 cutoff
  return (totalMs / 60_000f) / days.coerceAtLeast(1)    // days 只出现在除数位置
  ```
  调用方：`shared/src/commonMain/kotlin/com/hmp/domain/agent/runtime/sub/hello/HelloSubAgent.kt:1112`，`windowDays` 来自 `rangeToDays()`（同文件 `:1143-1149`，DAY=1 / WEEK=7 / MONTH=30 / YEAR=365 / ALL=3650）。
- **影响**：「最近 N 天日均听歌时长」实际是「**有史以来**总时长 ÷ N」。用户听了一年、切到「今日」时得到的是全年总量（分钟），恒 > 120 → `adaptiveFrequency`（`HelloSubAgent.kt:1167-1171`）恒判为日更；切到「全部」时除以 3650 → 恒 ≤ 30 → 判为周更。频率决策与真实活跃度脱钩。
- **动作**：按 `date` 列做窗口过滤（`ListeningDuration.date` 是 `yyyy-MM-dd` 文本，可用 `WHERE date >= :fromDate`），只对窗口内的天求和并除以窗口内的**实际天数**（不是 `days`），或至少除以「有记录的天数」——两者语义不同，需写明并一致；同时把 `rangeToDays`（`HelloSubAgent.kt:1143`）与 `NarrativeTimeRange.toDays()`（`SlideModels.kt:40`）这两份**已经分叉**（ALL 分别为 3650 与 -1）的映射收敛成一份。
- **判据**：`:shared:desktopTest`：seed 3 条 `listeningDuration`（2 天前各 60 分钟、400 天前 60000 分钟），断言 `getAvgDailyListeningMinutes(7)` 只统计窗口内那 2 天（≈60.0f），且不等于全表总量 ÷ 7。
  另加一条 `commonTest` 断言两份 `NarrativeTimeRange → days` 映射对 5 个枚举值返回同一组数（`rangeToDays` 需先提升可见性）。

### D5-04 `playDuration` 三端三种口径：Android 写整曲时长，Desktop 写播放位置，iOS 写 30 秒残值

- **现状（亲验）**：
  - Android 自然播完 → 写**曲目总时长**，中途结束 → 写**会话累计**：
    `android/core-player/.../MusicController.kt:680`（`completePlaybackSession(historyId, musicId, totalDuration)`）与 `:683`（`skipPlaybackSession(historyId, musicId, duration, true)`，`duration` 来自 `:653` 的 `totalPlayedDurationInSession`）。
  - Desktop 两种结局都写**引擎当前播放位置**：
    `desktop/core-player/.../DesktopMusicController.kt:420`（`completePlaybackSession(historyId, music.music.id, currentPos)`）与 `:422`（`skipPlaybackSession(..., currentPos, isSkip)`），`currentPos` 即 `_currentPosition.value`。
  - iOS 写 `listeningDurationAccumulator`：
    `ios/HMP/HMP/Features/Player/MusicPlayerController.swift:410`（`let duration = listeningDurationAccumulator`），而该累加器每 30 秒被清零一次（`:462-463` `let duration = listeningDurationAccumulator; listeningDurationAccumulator = 0`），且**结算前不会把 `playbackStartTime` 到现在的残值补进累加器**（补值只在 `pauseListeningDurationTracking()` `:449-454` 里做，而它只由 `pauseMusic()` `:169` 调用）。
  - 三个量最终都落到 `PlaybackHistory.playDuration`，被 `getTotalDurationSince`（`PlaybackHistory.kt:124-129`）、`getWindowedPlaybackCount`（`:132-140`）、`getPlayRowsSince`（`:84-92`，算跳过点）消费。
- **影响**：总收听时长、完播率、跳过率、Top 歌曲在三个平台上不是同一个量。iOS 上一首听满 4 分钟的歌，落库的 `playDuration` 通常只有「上次 tick 之后的几秒」——完播率仍标记为 true，但时长统计与 `skipBucketOf`（`MusicRepositoryBase.kt:1211`）拿到的比例接近 0，会被判成 `SKIP_INTRO`。
- **动作**：定义 `playDuration` 的单一语义（建议：**本次会话累计实听毫秒**，不含 seek 空档，与 `listeningDuration` 的日累计同口径），三端结算点统一：自然播完也写累计实听（不是元数据时长），iOS 在 `endCurrentPlaybackSession` 开头先执行一次 `pauseListeningDurationTracking()` 把残值并入累加器。
- **判据**：三端各一条、至少先落地两条：
  - `:shared:desktopTest`：`DesktopMusicController` 已有 `desktopTest` 用例（`desktop/core-player/src/desktopTest/...`，`PlaybackHistoryUseCase` 已在 `DesktopPlaybackQueueTest.kt:58` 注入），补一条：播完一首 200 秒的歌后断言 `updatePlaybackRecord` 收到的 `duration` 等于**累计实听**而非引擎最后位置；
  - Android：`android/core-player/src/test/.../MusicControllerTest.kt:45` 已有 `mockk(relaxed = true)` 的 `playbackHistoryUseCase`，补一条 `verify` 断言完播时传入的 `duration` 来自累计值而非 `music.duration`；
  - iOS：**待验**（见 §五），真机上连续播放 > 90 秒后查 `PlaybackHistory.playDuration` 是否 ≈ 实听毫秒。

### D5-05 iOS 暂停后再恢复，听歌时长计时永久停摆

- **现状（亲验）**：`ios/HMP/HMP/Features/Player/MusicPlayerController.swift`
  - `pauseListeningDurationTracking()`（`:449-454`）在把残值并入累加器后把 `playbackStartTime` 置为 `nil`；
  - `playOrResume()`（`:158-165`）只调 `engine.resume()`，**没有重置 `playbackStartTime`**；
  - 全文件对 `playbackStartTime` 的赋值只有 3 处（`:391` 新建会话、`:452` 暂停置 nil、`:459` tick 内续期），resume 路径不在其中；
  - 于是 tick 回调里的 `if let start = playbackStartTime`（`:457`）恒为 false → 累加器不再增长 → `recordListeningDuration`（`:467`）不再被调用。
- **影响**：iOS 用户只要暂停过一次，当天剩余播放时间**不再计入** `listeningDuration`，热力图出现「听了但显示为空」的空洞；直到切下一首（`:389` 新建会话）才恢复。
- **动作**：`playOrResume()` 在 `engine.resume()` 成功后 `playbackStartTime = Date()`；更好的是把「开始 / 暂停 / 恢复 / 结算」收口成一处状态迁移，避免 `playbackStartTime == nil` 这个隐含状态。
- **判据**：**待验**（iOS 无单测源集，`shared/src` 下只有 `commonTest` 与 `desktopTest`）。真机上：播放 40 秒 → 暂停 → 恢复 → 再播 40 秒 → 切歌，查 `listeningDuration` 当日 `duration` 是否 ≥ 80 秒；修复前预期只有第一个 40 秒入账。
  若后续为 iOS 计时逻辑抽出平台无关的状态机，则降级为 `commonTest` 纯函数用例。

### D5-06 播放来源分布：iOS 恒空壳

- **现状（亲验）**：
  - iOS 建会话恒传 nil：`ios/HMP/HMP/Features/Player/MusicPlayerController.swift:396`
    （`startPlaybackSession(musicId: musicId, source: nil)`）
  - Android / Desktop 都传了值：`MusicController.kt:633`（`startPlaybackSession(track.music.id, source)`）、`DesktopMusicController.kt:399`（`startPlaybackSession(musicId, source)`，`:270` 传 `"direct"`）。
  - 来源分布 SQL 直接排除 NULL：`shared/src/commonMain/kotlin/com/hmp/data/database/PlaybackHistory.kt:169-175`（`WHERE playedAt >= :cutoff AND source IS NOT NULL`）。
  - UI 侧 `windowed.sourceBreakdown.isNotEmpty()` 为假时整块不渲染：`shared-ui/.../settings/pages/UserUsageDataScreen.kt:267`。

### 4.2 并发与生命周期

- **写入并发**：三端播放历史写入都在各自控制器的 `scope.launch` 里 fire-and-forget（`DesktopMusicController.kt:409`、`:383`、`:226`；`MusicController.kt:633`、`:678`；iOS 用 `Task {}`），**无一处等待完成**；Android 的注释自己点明了这个风险（`MusicController.kt:657-658`：「那个 id 是 scope.launch 异步赋值的，连跳时很可能还没写回来」），但只在**观测面**绕开，**写库路径仍依赖这个可能还没赋值的 id**（`:674` `currentPlaybackHistoryId ?: run { ... return }` → 连跳时静默丢历史行）。
- **退出时序**：Desktop 三个退出入口都是「release() 后立刻 `exitApplication()`」（`Main.kt:188 / 269 / 331`），且 `DisposableEffect.onDispose`（`:246`）会二次 `release()`；见 D5-07。
- **批量写无事务**：`upsertEvidence` 循环 + `recomputePortraits` 逐条 upsert（`UserMemory.kt:114/160/487`）、`restoreListeningStats`（`MusicRepositoryBase.kt:767/778`）均无事务；见 D5-12 / D5-13。
- **去重闸门**：行为刷新有 20 小时日内去重（`UserMemory.kt:140-146`，阈值 `ProfileModels.kt:86`），是本域唯一一处节流，实现正确。

### 4.3 可观测性

- **好的一面（亲验）**：`UserMemory` 的日志纪律做得扎实 —— 每个刷新面都有 `HmpLog.i` 记条数、每条失败都有 `HmpLog.w`（`UserMemory.kt:117-127 / 162-168 / 250 / 314 / 321 / 332 / 346 / 396`），且类注释第 2 条明确「日志只记条数，不记内容」（`:33-34`）；审计只记工具名与条数（`:497-501`）。
- **差的一面（亲验）**：
  - `UserUsageDataViewModel` 六处 `runCatching` 全部静默（`:102-125`），见 D5-14；
  - `PlaybackHistoryUseCase`（全文件 52 行）与 `MusicRepositoryBase` 的统计方法（`recordListeningDuration` `:438`、`getWindowedAnalytics` `:1143` 等）**零日志**：时长写库失败、窗口查询失败都无从发现；
  - 三端播放控制器对历史写入用裸 `try {} catch (_: Exception) {}` 吞掉（`DesktopMusicController.kt:401 / 427`、`MusicController.kt:372`），Desktop 侧连 `HmpLog` 都不记。
- **结论**：本域的「日志纪律」在画像侧是正面样板，在统计侧完全没有建立。
