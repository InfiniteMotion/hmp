## 二、目标状态

D4 做完后应呈现：

1. **单一歌词存储源**：歌词文本统一来自 `musicExtra.lyrics`（内嵌标签经三端元数据通道写入）；**不存在**侧车 `.lrc` 查找（除非后续需求明确，见"刻意不做"）。
2. **设置单一真源**：播放页（内联 `PlayerScreen` + 独立 `LyricsScreen`）与悬浮歌词都从 `LyricsSettingsUseCase.getComponentConfig(LyricsComponent.*)` 经 `LyricsConfigResolver` 解析读取；设置页 `LyricsSettingsPage` 写入同一 per-component 模型。legacy 扁平键（`@Deprecated`）彻底下线，无"改了字号不生效"。
3. **三端对齐的悬浮歌词**：Android 已有；Desktop / iOS 要么有原生浮窗，要么 UI 明确标注"本端不支持"而非静默空实现。
4. **LRC 解析完整**：支持标准重复时间行 `[t1][t2]text`、增强逐字 `<…>`、双语启发式可关可配；解析错误有日志与降级。
5. **可观测**：歌词加载/解析/高亮行切换有 `HmpLog` 埋点；缺失/失败时用户可见降级。

### D4-01　歌词设置双存储：设置页写新模型、播放页读 legacy，导致"改了不生效" 　【亲验】

  - 读取侧（播放页）：`PlayerScreen.kt:93-99` 经 `LyricsSettingsViewModel.lyricsOriginalTextSize` 等（`LyricsSettingsViewModel.kt:22-45`）→ `LyricsSettingsUseCase` 中全部标 `@Deprecated("Use getComponentConfig(...)")` 的 legacy 扁平流（`LyricsSettingsUseCase.kt:85-125`）。`LyricsScreen.kt:104-110` 同路。

### D4-02　`LrcParser` 不支持标准 LRC 重复时间行 `[t1][t2]text` 　【亲验】

- **现状**：
  - `LrcParser.parse()` 每行仅取**首个** `[mm:ss.xx]` 时间戳（`LrcParser.kt:37-48`：`timeRegex.find(line)` 只匹配一次，第二时间戳留在 `content`）。
  - 残留的 `[mm:ss.xx]`（第二时间戳）被 `parseTimedContent` 的 `tokenize` 当作行内逐字标记处理（`LrcParser.kt:175-192`：遇到 `[` 且 `timeRegex` 命中即加 marker）。
  - 结果：如 `[00:12.00][00:40.00]hello` 被解析成"12s 处一条、带一个从 40s 开始的错乱 charTiming"，且 40s 处的重复句**整体丢失**。
- **影响**：合唱等重复句在第二段时间点不显示，且首段逐字时序错乱（开启卡拉 OK 时尤为明显）。
- **动作**：在 `parse` 阶段将多时间戳前缀行展开为多条同文本条目（识别行首连续的 `[mm:ss.xx]` 段），再交给普通/增强分支；逐字 `<…>` 仍走现有 `parseTimedContent`。
- **判据**：落 `:shared:desktopTest` / `commonTest`（`LrcParserTest`）。新增用例 `["[00:12.00][00:40.00]hello"]` 期望解析出两条 `LyricLineData`，`timestamp` 分别为 `12000` 与 `40000`，文本均为 `"hello"`，且 `charTimings` 为空（非错乱）。

- **施工结果（2026-10-28，二-1）**：
  - `parse` 先吃**行首连续时间戳**（`leadingTimestamps`，只吃从行首开始、紧邻无空隙的那一段），逐个展开成条目，再交给原来的普通/增强分支；正文里出现的 `[..]` 仍归 `parseTimedContent` 处理。
  - **判据 3 例**：12s/40s 展开成两条、近似时间戳（12.34/12.78）同样按"重复"处理、展开后正文里的 `<mm:ss.xx>` 逐字标记仍生效。
  - ⚠️ **一处行为变化要记住**：旧用例 `parse_enhancedDoubleTimestamp_buildsCharTimings` 把 `[t1][t2]text` 当"逐字结束标记"（第二条 12.78 作为首字结束）。这与本条的动作直接冲突，已按本条改为"重复时间戳"语义；逐字请用 `<mm:ss.xx>`。这不是迁就实现改测试 —— 标准 LRC 的重复行远比 A2 自造的双时间戳前缀常见，且后者的"结束时间"语义在规范里没有依据。
  - **探针**：把 `leadingTimestamps(line)` 改成 `.take(1)`（退回只取首个）→ **精确红 3 例**，其余 LRC 用例（含单时间戳增强三例）全绿。

### D4-03　`AdvancedLyrics` 自动滚动未居中，与注释意图不符 　【亲验】

- **现状**：`AdvancedLyrics.kt:125-132` 用 `scrollState.animateScrollToItem(index = currentIndex, scrollOffset = 0)`，`contentPadding` 垂直 = `containerHeightPx/2`（`:138`）。`scrollOffset=0` 仅把当前行**置顶**；配合 `contentPadding` 仅当滚到 `item 0` 时该行才居中，任意 `currentIndex>0` 时高亮行贴在顶部而非视口中线。行内注释 `:124` 写"居中显示"。
- **影响**：播放时高亮歌词贴顶，观感与"旗舰辉光居中"设计不符；长歌词滚动易丢焦点。
- **动作**：以 `scrollOffset = -(containerHeightPx/2) + 当前行高/2`（或 `animateScrollToItem` 后补 `scrollBy`）实现真正居中；可用 `LazyListLayoutInfo` 取当前行高。
- **判据**：落 `:shared-ui:testAndroidHostTest`（UI 宿主测试）。断言播放中高亮行 `bounds` 纵向中心落在视口 `[height/2 ± 容差]` 内；若无法像素断言，明确"macOS 实机打开 `LyricsScreen` 播放，肉眼确认高亮行位于屏幕纵向中线附近"。

  **2026-11-03 决议**：本条**暂不修**，已记入 `docs/ideas.md`「歌词自动滚动只顶不居中」；
  与歌词专项（逐字、翻译、对齐）一起排期。`plan.md` 二-2a 随之暂缓。

### D4-05　双语拆分 `DualLanguageAnalyzer` 为字符比例启发式，存在误判风险 　【亲验，待验】

- **现状**：`DualLanguageAnalyzer`（`LrcParser.kt:201-297`）以中/英/日/韩/西里尔字符计数比例判定主次语言并拆分原文/译文（`splitByBoundaries`/`extractByScript`）。当一行中两种语言字符数相近或含标点/数字时，阈值 `0.6`（`detectDominantLanguage` `:289-294`）可能把原文/译文判反或错拆。
- **影响**：部分双语歌词被错误拆分为"原文=英文部分、译文=中文部分"（或反之），显示错位。
- **动作**：增加时戳增强 LRC 中显式双语标记优先；或提供"手动指定语言顺序"开关；保留启发式作兜底。
- **判据**：落 `:shared:desktopTest` / `commonTest`。新增 `DualLanguageAnalyzer` 用例覆盖"中英语各半混排""带数字/标点的双语行"，断言拆分结果与预期一致。

- **施工结果（2026-10-28，二-1）**：
  - `splitByBoundaries` 与 `extractByScript`（两份"按字符过滤重组"）删成一份 `splitTwoScriptSegments`：**只有两种文字各占一段、且恰好一次切换才拆**；交错混排一律不拆。
  - 旧实现的两个实际伤害：① 过滤会**丢字** —— `"Hello, world! 你好，世界 2026"` 拆出来只剩 `("Hello", "world", "你好，世界")` 一类的东西，数字与标点静默消失；② 交错行（`"今天 weather 很好"`）被按字符重排成两半，语序彻底丢。现在按**原串切片**，两侧文本原样保留。
  - **判据 3 例**：数字+标点保留、交错混排不拆、中文在前时仍把英文作为原文（保持既有 `analyzeDualLines` 的约定）。
  - **探针**：换回旧的字符过滤实现 → **3 例全红**（含"中文在前"那条，因为标点被丢后文本不相等）；换回后其他双语用例照绿。
  - **残余**：`detectDominantLanguage` 的 0.6 阈值未动 —— 它在 `analyzeDualLines`（两行式）里只用于判断"这是两种语言"，且现在只影响"谁是原文"，不再影响切分；真要判原文/译文方向，得靠标签或用户开关（动作里的"手动指定语言顺序"未做，属产品口径）。

## 四、四项横查

**数据正确性**
- 歌词文本仅来自 `musicExtra.lyrics`（DB），与 D2 同表，无独立持久化需求（见"刻意不做"）。`LrcParser` 解析为该域唯一文本入口，存在 D4-02 重复时间行缺陷与 D4-05 双语误判。
- 双存储（D4-01）是最高优先数据正确性缺陷：设置写入与播放读取走两套 keys，数值永不汇合。
- iOS 内嵌歌词已填 `lyrics`（含 FLAC Vorbis 兜底，`MusicMetadataParserBridge.swift:64-67`），与 D2 的 `year/genre/track = nil`（`MusicMetadataParserBridge.swift:102-104`）**不同源**——iOS 漏的是年/流派/音轨，歌词本身已实现，不阻塞 D4。

**并发与生命周期**
- `FloatingLyricsOverlay` 在 `LaunchedEffect(Unit)` 中**一次性** `resolveConfig(FLOATING)`（`:71-73`），浮窗存活期间改设置不实时刷新（需重开浮窗）。
- Android `MusicController.getMusicLyrics` 解析后写入 `parsedLyrics` 可变列表（`MusicController.kt:223,847`），属单线程回调，未见明显竞态；三端 `getMusicLyrics` 均走 `CurrentPlaybackUseCase` → DB 读，IO 切换至 `Dispatchers.Default`（`MusicRepositoryImpl.ios.kt:174` 等）。
- `FloatingLyricsService` 为 Android `Service` 生命周期，退出由 `saveFloatingLyricsEnabled(false)` 收尾（`:83`）。

**可观测性**
- `LrcParser` / `AdvancedLyrics` 解析与渲染**无 `HmpLog` 埋点**：解析为空、逐字时序异常、找不到当前行均无日志，排障只能靠 UI 表现。
- 歌词加载失败的唯一直观信号是 `EmptyLyricsView`；无 metrics/计数区分"无歌词文件"与"解析失败"。

**测试覆盖**
- 已有（commonTest / desktopTest）：`LrcParserTest`、`LyricsConfigResolverTest`、`LyricsComponentConfigTest`、`LyricsPresentationParamsTest`、`LyricsSettingsUseCaseTest`、`CurrentPlaybackUseCaseTest`（getMusicLyrics）、`SettingsRepositoryImplTest`（含 `floatingLyricsEnabled`）。
- 缺口：① 双存储隔离的端到端断言（D4-01）；② 重复时间行解析（D4-02）；③ 双语启发式边界（D4-05）；④ UI 滚动居中（D4-03）；⑤ 悬浮跨端（D4-04）。上述①②④⑤均缺对应测试源集用例。

## 六、刻意不做（带改判条件）

1. **侧车 `.lrc` 文件查找（F2）**：本轮不做。当前数据模型仅 `musicExtra.lyrics`（DB 文本），全仓无 `.lrc` 路径查找。改判条件：若确认需求为"从音频同级目录加载 `*.lrc`"，需并入 v10 或另开 v11，新增文件查找 + 编码探测（注意**不在 `version=9` 上偷加字段/表**，依 `v10-migration.md` §七）。
2. **歌词搜索/跳转（D4-06）**：本轮不做（影响小、非核心）。改判条件：用户反馈长歌词难定位，或播放页/独立页明确排入期。
3. **Desktop/iOS 原生悬浮歌词**：本轮不做（平台原生工作量，且本机无法编 iOS 验）。改判条件：Android 之外用户明确需要；届时 D4-04 动作 (a) 落地并补 iOS 桥钩 `floatingLyricsStart/Stop`。
4. **legacy 扁平键下线**：不在本轮直接删除（D4-01 动作含迁移），待播放页全部切到 per-component 读路径、且 `:shared-ui:testAndroidHostTest` 端到端判据通过后，再移除 `@Deprecated` 字段，避免回归。

> 本域**不引入新的 Room 持久化字段/表**：歌词配置已落在 DataStore 的 per-component JSON（与 legacy 并存），修复为"读路径 wiring"而非 schema 变更，故无需并入 v10/v11。
