## 二、目标状态

做完之后：

1. **密钥**：Android 走 AndroidKeyStore + AES-GCM；Desktop 走 OS 凭据容器（macOS Keychain / Windows DPAPI / Linux libsecret）——三端都是"真加密 + 平台保护的密钥材料"。iOS 关键一步是**密钥不再落 `Documents`**：Keychain 或至少 `Application Support` + `NSFileProtectionComplete` + `NSURLIsExcludedFromBackupKey`。
2. **密钥不可解时降级而非崩溃**：任何一次 `decrypt` 失败都返回空串并触发一次"请重新填写"的用户可见提示；`getCustomAiConfig()` / `customAiConfig` Flow 与 `getAgentEndpointConfig()` 三处行为一致。
3. **备份恢复是一条事务**：导入前自动留一份 pre-restore 安全副本；4 个仓库的 restore 全成功才提交，任一步失败整链回滚，UI 拿到的是"已回滚 + 安全副本路径"而不是"失败但库已被改写"。
4. **路径有边界**：`BackupFileRepository` 的 `loadBackup` / `deleteBackup` 只接受规范化后位于本端备份目录内的路径，越界返回 failure。
5. **快照有版本闸门**：导出写真实 schema 版本；导入对高于本端可解析版本的快照返回明确的"备份版本过新"failure，不静默丢字段。
6. **迁移链有门禁**：`AppDatabase` 暴露单一 `ALL_MIGRATIONS` 常量，三端 `addMigrations` 都引用它（结构上不可能漏端）；`1→9` 每一环都有 `runMigrationsAndValidate`；新增 v10 忘了写迁移 = 测试红。
7. **降级有出口**：`user_version > 9` 时不静默失败、不崩溃——记录一条 `HmpLog.e(LogTag.Data*)` 并给用户一条"库版本高于本版本，请升级或恢复备份"的可见路径。
8. **死链要么删要么接**：`backupSettings` / `restoreSettings` / `cleanOldBackups` 三法要么从接口与三端一起删掉，要么接上 UI 并补往返测试；不允许继续以"存在但没人调"的形态挂着。
9. **可观测**：`LogTag.DataBackup` 在导出 / 导入 / 删除 / 列表四条的成败路径上三端都埋点，失败带异常与路径（路径本身不敏感，密钥不落日志）。
10. **三端一份语义**：`SettingsRepository` 三端 `*Impl` 只保留平台差异（DataStore 构造、文件路径），业务语义与默认值由 commonMain 的契约测试统一约束。

### D7-01 Android 云备份 / 设备迁移恢复后，API Key 解密必然失败且无降级 → 打开 AI 页崩溃

- **现状**【亲验】：
  - `AndroidManifest.xml:18-20` `android:allowBackup="true"` + `dataExtractionRules=@xml/data_extraction_rules` + `fullBackupContent=@xml/backup_rules`；
    `res/xml/backup_rules.xml:9` include `datastore/player_preferences.preferences_pb`，`:15` include `backups/`；
    `res/xml/data_extraction_rules.xml:9`（cloud-backup）与 `:21`（device-transfer）同样 include DataStore 与 `backups/`。
  - 该 DataStore 文件里存着 `custom_ai_api_key`（`SettingsRepositoryImpl.android.kt:303`）与每个 Agent 的 `agent_apikey_<role>`（`:340`），都是 `SecureStorageHelper.encrypt()` 的密文。
  - Android 的加密密钥是 **AndroidKeyStore 不可导出密钥**（`SecureStorageHelper.android.kt:17-38`，`KEY_ALIAS="my_secure_key"`，`KeyGenParameterSpec` 无 `setUserAuthenticationRequired` 但密钥本身不随 `allowBackup` 迁移）。
  - 换机 / 设备迁移恢复后，prefs 回来了、Keystore 密钥没有 → `decrypt` 必抛。
  - 消费侧**没有降级**：`SettingsRepositoryImpl.android.kt:290`（`getCustomAiConfig`）与 `:276`（`customAiConfig` Flow）都是裸 `SecureStorageHelper.decrypt(it)`，无 `runCatching`；
    而同文件 `:321`（`getAgentEndpointConfig`）用了 `runCatching { ... }.getOrDefault("")` —— 同一份代码里两种写法，说明作者知道会失败，另两处漏了。
  - `AiSettingsViewModel.kt:44-48` 在 `viewModelScope.launch` 里裸调 `getCustomAiConfig()`，无 try/catch；`AIScreen.kt:178` collect 其结果。
- **影响**：换机 / 云备份恢复后的用户，第一次打开 AI 设置页即抛异常 → `viewModelScope` 未捕获 → Android 运行时崩溃。用户无法自行恢复（只能清 app 数据）。Desktop（`:216`/`:224`）与 iOS（`:219`/`:227`）写法相同，风险同源。
- **动作**：① 三端 `decrypt` 统一改为 `runCatching { decrypt(it) }.getOrDefault("")`，并对"有密文但解不开"这种情况额外打一条 `HmpLog.w` + 返回一个"需重填"标记；② 把密钥的解密能力抽成可注入的门面（当前 `expect object SecureStorageHelper` 是 object，无法在测试中替换）；③ 决策：要么从 Android 备份规则里排除 DataStore 中的密钥键，要么接受"迁移后需重填"并把它做成用户可见提示（推荐后者，因为前者要动 `backup_rules` 的粒度，DataStore 是单文件无法按键排除）。
- **判据**：
  - **自动化（`:shared:desktopTest`）**：在 `SettingsRepositoryImplTest` 加一条用例——注入一个 `decrypt` 恒抛的门面（依赖动作②），断言 `repo.getCustomAiConfig().apiKey == ""`、`repo.customAiConfig.first().apiKey == ""` 且两者都不抛。Desktop 侧的等价场景（删掉 `~/.hmp/keystore.p12` 后用旧密文读）也可作为第二条用例。
  - **实机（Android）**：由 Android 端负责人在真机或 API 33+ 模拟器上执行 `adb shell bmgr backupnow com.hearablemusic.player` → 卸载 → 重装并触发恢复 → 打开「AI」页。验完看：页面不崩（Logcat 无 `FATAL EXCEPTION` / `AEADBadTagException` / `KeyStoreException`），密钥输入框为空并出现"请重新填写 API Key"提示。
  - **实机（iOS）**：同一人在 iOS 真机上做 iCloud / 快速开始迁移后打开 AI 页，看同样的两点。

### D7-02 导入恢复无事务、无安全副本：中途失败留下已被 `deleteAll()` 清空的库

- **现状**【亲验】：
  - `ImportUserDataBackupUseCase.kt:23-26` 串行调 4 个仓库的 restore（settings → musicUserState → listeningStats → playlists），`:29-30` `catch (Exception) → Result.failure`。无事务、无回滚、无导入前副本。
  - 第 4 步内部先清后写：`PlaylistRepositoryImpl.android.kt:142-143` `playlistDao.deleteAll()` + `playlistItemDao.deleteAll()` 再 `insertAll`；`PlaylistRepositoryImpl.desktop.kt:129-130`、`PlaylistRepositoryImpl.ios.kt:129-130` 同构。
  - 全仓无事务包装：`grep "withTransaction|inTransaction"` 在 `shared/src` 下 0 命中（口径：排除 `*/build/**`）。
- **影响**：第 2/3 步成功、第 4 步在 `deleteAll()` 之后抛异常（磁盘满、约束冲突、反序列化出的脏数据）→ 用户的歌单已被清空、曲目用户态已被改写，UI 只弹一句"恢复失败"，没有任何回退路径，也没有可供手工找回的副本。
- **动作**：① 把 4 个 restore 包进单一写入事务（Room 2.8.3 的事务 API，落地前先按符号名确认可用重载；若不可用则退化为在导入前手工 `BEGIN`/`COMMIT` 包裹，或把 4 个 restore 合并到一次 DAO 批量写入）；② 导入开始前先 `ExportUserDataBackupUseCase` 生成一份 `pre-restore-<ts>.json` 安全副本，并在 UI 的失败文案里带上它的路径。
- **判据**（`:shared:commonTest`，与 `BackupUseCaseTest.kt` 同包）：
  - 用例 A：注入一个在第 3 步（playlists）抛异常的 Fake 仓库，断言 ① `importUseCase(path).isFailure`；② 前 3 个仓库的状态与导入前**逐字段相等**（Fake 记录写前快照，断言回滚后一致）。
  - 用例 B：任意一次导入（成功或失败）后，`getBackups()` 的结果里存在且仅存在一份文件名前缀为 `pre-restore-` 的新备份。
  - 现有 `BackupUseCaseTest` 里的 `exportAndImport_roundTrip` 必须继续绿（它用全空 Fake，是" happy path 不回归"的下限）。

### D7-03 iOS 密钥是 XOR 伪加密，密钥明文落 `Documents/.keys`，且工程开着文件共享

- **现状**【亲验】：
  - `SecureStorageHelper.ios.kt:57-65` `simpleEncrypt` 实为逐字节 `xor keyBytes[i % keyBytes.size]`；`:67-73` `simpleDecrypt` 同构；`:58-59` 生成了 12 字节 IV，但加解密都**不使用它**——同一明文恒产出同一密文（已知明文即可推出整个密钥流）。
  - `:45-55` `generateAndStoreKey()` 用 `Random.nextBytes`（`kotlin.random.Random`，非 CSPRNG）生成 32 字节，Base64 明文写盘。
  - `:17-26` `keysDir = NSDocumentDirectory + "/.keys"`，密钥文件 `:29` `.aes_key`（名字叫 aes，算法不是 AES）；**与密文（DataStore 在 Documents）同目录**。
  - `ios/HMP/project.yml:43` `UIFileSharingEnabled: true`、`:44` `LSSupportsOpeningDocumentsInPlace: true`（Info.plist 由 XcodeGen 从本文件生成）。
  - 数据库同样在 Documents：`DatabaseBuilder.ios.kt:13` `documentDirectory() + "/music_database.db"`；`:43-52` 取的就是 `NSDocumentDirectory`。
  - 全仓（`ios/**`）无 `NSURLIsExcludedFromBackupKey`、无 `NSFileProtection*` 设置；`createDirectoryAtPath(dir, true, null, null)`（`:30`）与 `createFileAtPath(path, nsData, null)`（`:52`）的 attributes 均为 null。
  - `ROADMAP.md:440` 自陈「安全存储现为 XOR 伪加密，待升级 AES-GCM + Keychain」——与本轮实读一致（互证）。
  - Android / Desktop 对照：`SecureStorageHelper.android.kt:40-65` 是真 AES-GCM + AndroidKeyStore；`SecureStorageHelper.desktop.kt:48-64` 是真 AES-GCM，但 `:14-15` `KEYSTORE_PASSWORD="hmp_ks_pass"` / `KEY_PASSWORD="hmp_key_pass"` 硬编码，keystore 落 `~/.hmp/keystore.p12`（`:17-21`）。三端密文互不可解（这是既成事实，跨端迁移备份本来也不带走密钥，见 §六刻意不做第 3 条）。
- **影响**：iOS 用户可以用 macOS Finder 或系统「文件」App 直接把 `.aes_key` 与数据库一起拷出来，密钥与密文同获 === 明文；且 Documents 默认进 iCloud/整机备份，等于把密钥推上了用户没预期的地方。
- **动作**：① 密钥材料改由 `SecRandomCopyBytes` 生成并存入 Keychain（`SecItemAdd`），或最低限度迁到 `Application Support` + `NSFileProtectionComplete` + `NSURLIsExcludedFromBackupKey`；② 算法换成 AES-GCM（`CryptoKit` 或平台 `CommonCrypto`），IV 真正参与运算；③ 保留 `decryptOldFormat`（`:97-102`）的读取路径做一次性迁移，老用户升级后密钥自动搬家、不丢配置；④ `project.yml` 的 `UIFileSharingEnabled` 只在"用户要导出备份"这一件事上需要，改密钥位置后与 D2/D9 一起评估是否保留。
- **判据**：
  - **源码级（可 grep 复验）**：`SecureStorageHelper.ios.kt` 内不再出现 `xor` 与用 `Random.nextBytes` 生成密钥材料；`keysDir` 不再指向 `NSDocumentDirectory`。
  - **实机（iOS）**：由 iOS 端负责人在 Xcode 26.x + iOS 26.3+ 真机上验三步，验完看：① 打开系统「文件」App → 「我的 iPhone」→ HMP，目录里**看不到** `.keys`，macOS Finder 的 HMP 容器里也看不到；② 在 AI 设置页填一次 API Key → 杀进程重启 → 仍能读回（往返成功，说明迁移/新路径都通）；③ 用 `grep` 扫一遍 iTunes/Finder 的未加密整机备份解包目录，确认无 `.aes_key` 与明文密钥串。

### D7-04 API Key 用 `rememberSaveable` 持有 → 明文写进系统 Bundle

- **现状**【亲验】：`shared-ui/src/commonMain/.../agent/config/AIScreen.kt:573` `var apiKeyValue by rememberSaveable { mutableStateOf("") }`；`:637-643` 该值由用户在 `TextField` 里直接输入（`visualTransformation` 只是遮罩，不改变状态值）。
  同一函数的 `:572`（endpoint）与 `:574`（model）也用 `rememberSaveable`，但只有 `apiKeyValue` 是密钥。
  `rememberSaveable` 的语义就是把值写进 `SavedStateHandle`/Bundle 以跨进程死亡恢复 → Android 上密钥明文落系统保存态（可被 `dumpsys` 读到、随系统保存态持久化）。
- **影响**：直接抵消 `SecureStorageHelper` 的整套设计——密文存得好好的，明文另有一份在系统侧，且生命周期比进程更长。
- **动作**：`apiKeyValue` 退回 `remember { mutableStateOf("") }`（endpoint/model 保持 `rememberSaveable` 无妨）；同时确认保存路径上没有把 `apiKeyValue` 再写进任何日志或别的持久化点。
- **判据**：

- **现状**【亲验】：`BackupFileRepositoryImpl.android.kt` 四个方法（`saveBackup:25`、`loadBackup:40`、`getBackups:58`、`deleteBackup:69`）**都没有 `withContext`**，直接在调用方线程上做 `File.writeText` / `readText` / `listFiles` / `delete`。
  对照：`BackupFileRepositoryImpl.desktop.kt:23,38,53,67` 全包在 `withContext(Dispatchers.IO)`；`BackupFileRepositoryImpl.ios.kt:36,54,72,90` 全包在 `withContext(Dispatchers.Default)`。
  调用方线程是 Main：`BackupViewModel.kt:59-86` 的两个方法都在 `viewModelScope.launch {}`（默认 `Dispatchers.Main.immediate`）里调 UseCase，`ExportUserDataBackupUseCase.kt:16` 直接串行调 4 个 export 再 `saveBackup`。
- **影响**：导出时要在主线程上序列化并写出整份快照（歌单 + 曲目用户态 + 听歌统计，随曲库规模增长），导入时同理——大曲库下会掉帧，`StrictMode` 打开时还会报磁盘读写违规。这是三端唯一的调度分叉。
- **动作**：Android 端四个方法补 `withContext(Dispatchers.IO)`，与 Desktop 对齐（iOS 的 `Dispatchers.Default` 也建议一并统一为 IO 语义；KMP 上 `Dispatchers.IO` 可用）。
- **判据**：
  - **源码级（grep 复验）**：`BackupFileRepositoryImpl.android.kt` 的四个 `override suspend fun` 体内都出现 `withContext(Dispatchers.IO)`。
  - **实机（Android）**：Android 端负责人在真机上（曲库 ≥ 数千首，或构造等价规模）点「生成备份」。验完看：Android Studio Profiler / Logcat 里无 `Choreographer: Skipped N frames` 的连续跳帧，开启 `StrictMode` 的 debug 构建无 `StrictModeDiskReadViolation` / `DiskWriteViolation`。

### D7-12 备份快照覆盖面窄、`version` 恒为 1 且导入不校验，`@Contextual` 非空路径零覆盖

- **现状**【亲验】：
  - `UserBackupSnapshot.kt:22-38` `AppSettingsSnapshot` 只有 14 个字段（用户名 / 头像 / 主题 / 背景风格 / 毛玻璃 5 项 / autoBatchProcess / aiAccessMode / 自定义端点 / 自定义模型）。
    **不在**快照里的：API Key（三端密文）、扫描目录配置、三段歌词配置 + 卡拉OK + 悬浮开关、音效 5 项、曲库排序、推荐算法配置、per-Agent 端点/密钥/policy/global、免费额度、播放态。
  - `UserBackupSnapshot.kt:14` `val version: Int = 1`，`ExportUserDataBackupUseCase.kt:23-29` 从不传别的版本；`ImportUserDataBackupUseCase.kt:21` 解析后**不校验 `snapshot.version`**。
  - `PlaylistsSnapshot`（`:83-89`）与 `ListeningStatsSnapshot`（`:91-97`）里 4 个类型用 `@Contextual` 标注（`Playlist` / `PlaylistItem` / `ListeningDuration` / `PlaybackHistory`），而注入给 `BackupFileRepositoryImpl` 的 `Json` 来自 `SharedModules.kt:64` `single { createJson() }` → `HttpClient.android.kt:28-34` / `desktop.kt:23-29` / `ios.kt:23-29`：`ignoreUnknownKeys = true; isLenient = true; encodeDefaults = true`，**没有 `serializersModule`、没有为这 4 个类型注册 contextual**。
  - 现有测试全部走空集合：`UserBackupSnapshotTest.kt:82-83` 显式传 `PlaylistsSnapshot()` 与 `ListeningStatsSnapshot()`（空）；`BackupUseCaseTest` 全用 Fake，`FakePlaylistRepository.kt:155-156` 返回空。**"有歌单 + 有听歌记录"的编码/解码路径从没被执行过。**
- **影响**：
  - 覆盖面窄 + 无版本闸门：用户以为"备份了设置"，恢复后发现 AI Key、歌词字号、扫描目录、音效全没了，且没有任何提示；将来快照加字段时，旧版本 app 会静默忽略（`ignoreUnknownKeys = true`）而不是拒绝。
  - `@Contextual` 的运行时行为本轮**未能确证**（本机未找到 kotlinx-serialization 的源码/jar 可核对 `ContextualSerializer` 在无 `serializersModule` 注册时是否回退到 `@Serializable` 生成的实现）。因此这一条只立"覆盖缺口"，不立"必然崩溃"：
    - 若能回退 → 现状可用，但这 4 个 `@Contextual` 标注毫无意义且把线上格式绑到了回退行为上；
    - 若不能回退 → 任何有歌单或有听歌记录的用户导出/导入备份都会抛 `SerializationException`。
- **动作**：① 把 4 处 `@Contextual` 去掉（这 4 个类本身都带 `@Serializable`，见 `PlaylistModels.kt:177` / `:192`，标注是多余的），让快照格式由自身 schema 钉死；② `ImportUserDataBackupUseCase` 加版本闸门：`snapshot.version > CURRENT_BACKUP_VERSION` → `Result.failure` 并给出"备份版本过新，请升级应用"；③ 决策：要么把丢失的那些设置补进 `AppSettingsSnapshot`（同时升 `version = 2`），要么在导出/导入的 UI 文案里明确列出"备份包含什么、不包含什么"（推荐先做③的文案，补字段随 v10 一起定）。
- **判据**（`:shared:commonTest`，新增 `BackupSnapshotRoundTripTest`）：
  - 用例 A：用与 `createJson()` 同配置的 `Json { ignoreUnknownKeys = true; isLenient = true; encodeDefaults = true }`，对一份含 **1 个歌单 + 2 个歌单项 + 1 条 `ListeningDuration` + 1 条 `PlaybackHistory`** 的 `UserBackupSnapshot` 做 encode → decode，断言解码结果与入参相等。**这条用例在当前代码下第一次跑就能回答上面那个未确证的问题**——跑通说明能回退，跑挂说明生产上必崩，两种情况都要继续做完①。
  - 用例 B：`version = 99` 的快照喂给 `ImportUserDataBackupUseCase`，断言 `isFailure`（当前必红）。

## 四、四项横查

### 4.1 数据正确性

- **导入不是原子的**（D7-02）：4 个 restore 串行、`deleteAll()` 先于写入、失败只 catch。这是本域唯一会造成"数据被改写且不可恢复"的路径。
- **设置恢复的键覆盖不完整**（D7-08）：Android 版 `prefs.clear()` + 14 键白名单，其余静默丢弃仍返回 success；三端都用手写 JSON + 正则解析，含 `,`/`}`/`"` 的值必损坏。
- **备份快照覆盖面窄**（D7-12）：14/40+ 项设置进快照，恢复后其余归默认，UI 不提示。
- **`@Contextual` 非空路径零覆盖**（D7-12）：歌单与听歌统计是备份的主要内容，恰恰是最没被测到的部分。
- 正面结论（亲验）：三份 `SettingsRepositoryImpl` 的默认值常量与 Flow 默认值**逐项一致**（`DEFAULT_HAZE_*` = 20f/0.15f/0.22f、`hazeIntensity` 0.6f、免费额度 100、`equalizerPreset` 0、`galleryOrderBy` "title"、音效与歌词默认值均相同），镜像复制目前没有漂移；迁移链 1→9 在三端都完整注册（D7-09）。

### 4.2 并发与生命周期

- **导入/导出无互斥、无进行中状态**：`BackupSettingsScreen.kt:117-135` 三个 section 各自独立，`BackupViewModel.kt` 只有 `backupResult: StateFlow<String?>` 一个结果槽，没有 `isRunning`。用户可以在"导出"还没返回时再点"导入"，两条链会同时改同一批表。
- **Android 端主线程做文件 IO**（D7-11）。
- **Android 导入固定落 `cacheDir/restore_temp.json`**（`AndroidPlatformServices.kt:167`）：同名覆盖，连续两次导入会互相踩；系统清缓存后文件消失（但那时导入已结束，无害）。
- **`BackupViewModel` 是 `koinViewModel()`、`SettingsViewModel` 是 `activityViewModel()`**（`BackupSettingsScreen.kt:72` / `ProfileSettingsScreen.kt:71`）：前者随页面、后者随 Activity——`ProfileSettingsScreen` 里 `SettingsViewModel.init` 只加载一次头像（`:137-139`），`saveAvatarUri` 后 `_avatarUri` 不刷新（`:56-60`），靠页面本地的 `uriImg` 状态遮盖（`ProfileSettingsScreen.kt:154`）。属"看起来对、其实没回流"，当前不显形。
- **iOS `KoinHelper` 的 4 个备份入口**（`:198-210`）是 Swift 侧可直达的 suspend 函数，无并发保护、无路径校验（D7-05）。

### 4.3 可观测性

- **备份链日志只存在于 Android 一处**：`BackupFileRepositoryImpl.android.kt:32,35,53` 共 3 条 `HmpLog`（tag `LogTag.DataBackup`，定义在 `LogTag.kt:50`）。Desktop 与 iOS 的 `BackupFileRepositoryImpl` **零日志**（亲验：两个文件全文无 `HmpLog`）。
- **两个 UseCase 零日志**：`ExportUserDataBackupUseCase.kt` / `ImportUserDataBackupUseCase.kt` 全文无 `HmpLog`——导入失败时没有任何"失败在第几步、哪个仓库"的记录，只有 UI 上 `e.message`。
- **降级场景零日志**（D7-10）。
- 正面结论（亲验）：`LogTag.DataBackup` 这个 tag 已经存在且在用，补埋点不需要新建 tag 体系。

## 六、刻意不做（带改判条件）

1. **不做在线/云同步、不引入账号**（`AGENTS.md` §一.2 产品边界）。改判条件：产品边界书面变更。
2. **不挂 `fallbackToDestructiveMigration` 兜底**。当前行为是"宁可打不开也不静默清库"，这是对的。改判条件：出现"版本降级必须可用"的产品需求——且必须先做完 D7-10（显式守卫 + 用户确认）与 D7-02（导入前安全副本），否则不开这个口子。
3. **不把 API Key 放进备份快照**。跨设备迁移密文而密钥不可迁移，只会制造 D7-01 那种"有密文解不开"的坑。改判条件：三端都用上了可随设备迁移的平台密钥容器（Android Keystore 的可迁移变体 / iOS Keychain 的 `kSecAttrSynchronizable`），且用户显式勾选"同步我的密钥"。
4. **不做自动/定时备份与备份轮转**（`cleanOldBackups` 目前连调用者都没有）。改判条件：有明确产品需求 + 存储配额与保留策略的方案。
5. **不为 `androidMain` / `iosMain` 新建测试源集**。本域判据落在 `:shared:desktopTest` / `:shared:commonTest` 与 §五 的实机清单上。改判条件：横切线决定新增平台测试源集（届时 D7-01/03/05/06/11 的判据应回迁为自动化）。
6. **不动 Desktop keystore 的存放位置**（`~/.hmp/keystore.p12`）。硬编码口令是问题，但搬家会让已有安装解不开旧密文。改判条件：先给出"旧 keystore → 新凭据容器"的一次性迁移路径，再动位置；口令本身可以在迁移路径里一并换掉。
7. **不给备份快照加密**。快照里现在没有密钥、没有凭据，明文便于用户自救。改判条件：若将来把 API Key、画像原文或完整对话记录纳入备份内容，则必须同时引入口令派生加密。
8. **不为了对齐而把 Android 的 `restore_temp.json` 机制拆掉**（D7-05 里它是唯一的正面结论）。改判条件：若路径白名单实现后证明 cacheDir 副本成为例外负担，再改为统一落到 `backups/`。
