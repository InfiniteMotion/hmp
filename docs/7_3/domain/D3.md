## 二、目标状态

做完之后这个域应该满足以下 7 条。它们是收敛条件，不是愿望清单。

1. **排序是持久化的、可恢复的**。`itemOrder` 是歌单内容的一部分：DOMAIN 模型的 `PlaylistItem` 带上它，备份快照带上它，`restoreFromSnapshot` 原样还原。任何"导出—导入"往返后，`getPlaylistById` 返回的 id 序列与导出前**逐项相等**。
2. **写操作要么全成要么全不成**。新增/删除/重排/批量添加/整表重置，每一项都在一个业务事务里完成；`itemOrder` 在同一歌单内不出现重复值（并发下也不出现）。
3. **歌单名唯一，且唯一性由数据库保证**，不是靠 UI 弹窗的一次 `validatePlaylistName`。所有按名删除的调用点（含自愈路径）改为按 id 删除。
4. **派生字段（`songCount` / `totalDurationMs` / `coverUri`）有单一真源**：要么每次都在同一事务里重算，要么改为查询时算；自定义封面不被自动重算覆盖。
5. **三端只有一份歌单仓库实现**。`PlaylistRepositoryImpl` 的可共享逻辑提到 `commonMain`（`MusicRepositoryBase.kt` 已是先例），平台源集只剩 DAO 的组装。改歌单语义只改一处。
6. **系统歌单（默认 / 心动 / 最近播放）的自愈只有一份实现**，三端共用；心动与最近播放的写入发生在 `shared` 的播放用例里，而不是各端控制器里各写一遍（iOS 因此漏了两条）。
7. **智能歌单是一个真歌单**：生成结果落 `playlist` + `playlist_item`（或显式标记为一次性队列），用户保存的算法类型 / 权重模板 / 扩展配置真正参与生成，而不是存进去就没人读。

### D3-01 · iOS 的 `currentTimeMillis()` 用的是 2001 参考纪元，不是 Unix epoch

**亲验**
- `shared/src/iosMain/kotlin/com/hmp/data/database/PlatformTime.ios.kt:8`：`return (NSDate().timeIntervalSinceReferenceDate * 1000).toLong()` —— `timeIntervalSinceReferenceDate` 是"自 2001-01-01 起的秒"。
- 对照 `shared/src/androidMain/.../PlatformTime.android.kt:4` 与 `shared/src/desktopMain/.../PlatformTime.desktop.kt:3`：均为 `System.currentTimeMillis()`（Unix epoch）。
- `shared-ui/src/iosMain/kotlin/com/hearablemusic/player/ui/platform/PlatformTime.ios.kt:8` 是同一处错误的第二份拷贝。
- 消费点：`PlaylistRepositoryImpl.ios.kt:28/35/57/61/65/69` 的 `createdAt` / `updatedAt`；`PlaylistViewModel.kt:274` 的 `nowEpochMillis()`（写 `lastPlayedAt`）走 shared-ui 那份。

**影响**：iOS 上所有歌单时间戳比真实时间少约 978307200000 ms（≈31 年），落在 1995 年前后。后果：① `PlayList.kt:74-79` 的 `getAnniversaryPlaylists` 用 `strftime('%m-%d', createdAt/1000,'unixepoch')`，iOS 上算出的月-日与创建日期无关，歌单纪念日候选永不命中；② 跨端备份恢复后，Android 写入的 Unix 时间戳与 iOS 写入的参考纪元时间戳混在同一列，`ORDER BY updatedAt DESC` 把新数据排到最末；③ `lastPlayedAt` 与 D5 的播放历史时间戳不同源，跨端不可比。

**动作**：两处 `PlatformTime.ios.kt` 改为 `NSDate().timeIntervalSince1970`。存量数据的修正在 v10 迁移里按平台判别处理（iOS 库可判 `createdAt < 1_000_000_000_000L` 加回偏移），或明确声明"v7.3 起新建的才正确"。

**判据**：`iosMain` / `iosTest` 无测试源集（`shared/src` 下只有 `commonTest` 与 `desktopTest`），落不进自动化测试。**由维护者在本机 iOS 模拟器上验**：① `./gradlew :shared-ui:compileKotlinIosSimulatorArm64` 通过；② 模拟器里新建一个歌单，取 `~/.hmp` 同路径的 `music_database.db`（iOS 用 App 容器内的库），执行 `SELECT name, datetime(createdAt/1000,'unixepoch') FROM playlist ORDER BY createdAt DESC LIMIT 5;`，**看第一行是否等于此刻（±1 分钟）**；③ 同一库里再执行 `SELECT strftime('%m-%d', createdAt/1000,'unixepoch','localtime') FROM playlist;`，**看是否等于建单当天月-日**。

- **施工结果（2026-10-09，一-3 C3）**：`PlatformTime.ios.kt` 改用 `NSDate().timeIntervalSince1970 * 1000`；**存量数据不修正** —— 用户 2026-10-09 决策「iOS 侧可以破坏性改动，并未上线」，因此不写偏移修正迁移、不做双读兼容，装上新包即从当天起算（旧库里的 1995 年时间戳随 iOS 首版发布前的数据一起作废）。
  同时消掉了这条点名的**第二份拷贝**：`shared-ui` 自己另有一套 `PlatformTime.{common,android,desktop,ios}.kt`，四个文件已删，三个消费点（`ChatAgentGateway` / `ChatKoinModule` / `ChatViewModel`）统一指向 `com.hmp.data.database.currentTimeMillis`。"同一处错误的两份拷贝"这件事是结构性没了，不是抄对了。
  判据的边界要如实写：`:shared:desktopTest` 与 `:shared-ui` 两端都只跑 JVM，`iosMain` 的 actual 在本机（Windows）**连编译器都覆盖不到**（记入 `plan.md` §六）。所以①②③三条模拟器断言仍是实机签收项；本机可核对的只有「不再有第二份实现可错」。


### D3-02 · 备份 / 恢复丢失歌单内排序（顺序在导出时被丢，在恢复时被重排）

**亲验**
- 领域模型 `shared/src/commonMain/.../domain/playlist/PlaylistModels.kt:192-197`：`data class PlaylistItem(songUrl, songId, playlistId)` —— **没有 `itemOrder`**。
- `PlaylistMapper.kt:36-47`：`toDomain()` 丢掉 `itemOrder`，`toEntity(itemOrder = 0)` 默认填 0。
- 快照容器 `domain/backup/UserBackupSnapshot.kt:84-89`：`PlaylistsSnapshot(playlists, playlistItems)`，`playlistItems` 用的正是上面那个无 `itemOrder` 的领域模型。
- 导出 `PlaylistRepositoryImpl.desktop.kt:120-126`（ios:120-125，android:126-139 同）→ `playlistItemDao.getAllPlaylistItems()`，而 `PlaylistItem.kt:85-86` 的 SQL 是 `SELECT * FROM playlist_item`，**无 ORDER BY**。
- 恢复 `PlaylistRepositoryImpl.desktop.kt:128-140`：`groupBy { it.playlistId }` 后 `mapIndexed { index, it -> ... itemOrder = index }` —— 按导出时的任意行序重新编号。

**影响**：歌单内顺序（置顶、上移下移的结果）在"设置 → 备份 → 恢复"后被打回插入顺序，且无提示。用户手动排过的长歌单是本次操作唯一的不可再生数据。

**动作**：① 领域 `PlaylistItem` 增加 `itemOrder` 字段并在 mapper 双向带上；② `getAllPlaylistItems()` 加 `ORDER BY playlistId ASC, itemOrder ASC`；③ `restoreFromSnapshot` 原样写入 `itemOrder`，不再 `mapIndexed` 重排；④ 快照加版本字段，读旧快照（无 `itemOrder`）时按"保持导出顺序"降级处理。

**判据**：`:shared:desktopTest` 新增用例（可扩 `PlaylistRepositoryImplTest`，现有 `:121-129` 的 `exportAndRestore_roundTrip` 只有 1 首歌，测不出）：建歌单 → 依次加入 song 1/2/3 → `reorderPlaylistItems(pid, listOf(3,1,2))` → `exportPlaylistsSnapshot()` → `removePlaylistById(pid)` → `restoreFromSnapshot(snap)` → 断言 `getPlaylistById(pid).map { it.music.id } == listOf(3L, 1L, 2L)`。

### D3-03 · 批量写与排序写都不在业务事务里；`itemOrder` 无唯一约束

**亲验**
- 全仓 grep `withTransaction|inTransaction`（口径：`*.kt`，排除 `build/` 与 KSP 产物）**0 命中**；`@Transaction` 共 21 处命中，全部落在 `shared/src/commonMain/.../data/database/{Music,PlaylistItem}.kt` 的 DAO 注解上 —— 没有一处是业务层事务。
- `PlaylistItemDao.resetPlaylistItems`（`PlaylistItem.kt:71-83`）带 `@Transaction`，是本域唯一真正原子的批量写。
- 其余批量写都不在事务里：
  - `addToPlaylist`（三端 Impl，例 `desktop.kt:80-85`）：`getMaxOrder` → `insert` → `refreshPlaylistStats`，三步各自独立；
  - `reorderPlaylistItems`（`desktop.kt:97-102`，ios/android 同）：`forEachIndexed { playlistItemDao.updateItemOrder(...) }`，N 条 UPDATE 无事务；
  - `PlaylistViewModel.addItemsToPlaylist`（`PlaylistViewModel.kt:229-244`）：对每一首串行跑一遍完整的 `addToPlaylist`（即 3N 次往返 + N 次统计重算）；
  - `restoreFromSnapshot`（`desktop.kt:128-140`）：`deleteAll()` ×2 → `insertAll` → `insertPlaylist`，四步无事务。
- 约束：`9.json` 中 `playlist_item` 只有 `PRIMARY KEY(songId, playlistId)` 与 `index_playlist_item_playlistId`，**没有 `(playlistId, itemOrder)` 的唯一索引**。

**影响**：① 并发两个 `addToPlaylist` 会读到同一个 `maxOrder`，写出两条相同 `itemOrder` 的行，`ORDER BY itemOrder ASC` 的相对顺序退化为 SQLite 自选，重排结果不可预期；② 中途失败（异常 / 进程被杀）留下半截状态：删了旧项没插新项、改了一半顺序；③ 批量加 N 首是 O(N) 往返 + O(N) 次全量统计重算，大歌单明显卡顿。

**动作**：DAO 增加 `@Transaction suspend fun replaceAll(playlistId, items)` 与 `@Transaction suspend fun reorder(playlistId, orderedIds)`；仓库层改调它们，`refreshPlaylistStats` 移进同一事务；`addItemsToPlaylist` 改走一次性批量插入。v10 迁移补 `CREATE UNIQUE INDEX index_playlist_item_playlistId_itemOrder ON playlist_item(playlistId, itemOrder)`（先跑一次去重再建，否则存量库迁移会失败）。

**判据**：`:shared:desktopTest` 两条 —— ① 并发用例：`coroutineScope { launch { repo.addToPlaylist(pid, 1, "/1") }; launch { repo.addToPlaylist(pid, 2, "/2") } }`，断言 `playlistItemDao.getAllPlaylistItems().map { it.itemOrder }.toSet().size == 2`；② 原子性用例：让第二次 `updateItemOrder` 抛异常（DAO 层注入失败或用 `orderedMusicIds` 含非法 songId），断言异常抛出后 `getPlaylistById(pid)` 的顺序仍是重排前的完整顺序。


- **施工结果（2026-10-08，一-1）**：`UNIQUE(playlistId,itemOrder)` 已建，存量按决策 1 在每个歌单内按 `(itemOrder, songId)` 重编为连续 `0..n-1`（单条目歌单的 `itemOrder=7` 也会被压成 0 —— 空洞同样填，否则末值会一直悬着）。
  **本条预警的"索引建了但写入仍撞号"当场兑现了**：`reorderPlaylistItems` 的逐条 `updateItemOrder` 一建索引就 `SQLITE_CONSTRAINT`（`置顶`是活的 UI 路径），所以重排侧必须与本迁移同批改 ——
  新增 `PlaylistItemDao.reorderAndRefresh`（`@Transaction` 两阶段：先 `itemOrder = -(itemOrder+1)` 整体取负，再落终值，未列出的条目按原相对顺序接在后面），三端 Impl 统一改调它；
  `PlaylistDaoTest.item_updateItemOrder` 现在同时钉住"裸 UPDATE 必撞"与"reorderAndRefresh 可完成同一互换"。
  **一-1 当时仍未收口**：`addToPlaylist` 的 `getMaxOrder → insert` 三步无事务，并发添加从"静默同序号"变成**撞索引抛错**（比原来更响，但仍是崩溃）—— 由下面的 A 批收口。

- **施工结果（2026-10-08，一-2 A 批）**：本条 ①② 两条判据都已收口，且 `refreshPlaylistStats` 从三份逐字镜像的 Kotlin 实现收成 DAO 里一条 SQL。
  - **写路径收口方式**：仓库只持有 DAO、拿不到数据库句柄，所以事务只能建在 DAO 侧。`PlaylistItemDao` 新增 `@Transaction` 写族
    （`addSongAndRefresh` / `removeSongAndRefresh` / `replaceItemsAndRefresh` / `reorderAndRefresh`，每个都是"改条目 + `refreshStats` + 首曲封面回填"同事务），
    `getMaxOrder` 已从 DAO 删除，取号改在一条语句里完成：`insertWithNextOrder` 用 `INSERT ... SELECT COALESCE(MAX(itemOrder),-1)+1`；
    三端 Impl 的对应方法各自缩成一次 DAO 调用，私有 `refreshPlaylistStats` 三份全删（D3-14 的镜像复制少一处）。
  - **判据 ①（并发添加）**：`PlaylistDaoTest.addSongAndRefresh_concurrentAddsGetDistinctOrders` —— 两次并发 `addSongAndRefresh` 都落库、序号集合大小为 2、派生计数收敛到最后一次写入。
    重复添加同一首仍是"移到末尾"（`INSERT OR REPLACE`），与原语义一致，`item_insertWithNextOrder_isSequentialAndMovesDuplicateToLast` 钉住。
  - **判据 ②（原子性）**：`BackupRestoreTransactionTest.daoTransaction_insideOuterRollback_leavesNoTrace`（外层事务里调 DAO 的 `@Transaction`，外层失败后顺序复原）。

- 歌单域**没有一条自己的日志**。grep `HmpLog`（口径：逐个文件 `grep -c`）在 `PlaylistRepository.kt` / `ManagePlaylistUseCase.kt` / `GeneratePlaylistUseCase.kt` / `PlaylistTools.kt` / `PlaylistViewModel.kt` / `PlaylistRepositoryImpl.desktop.kt` 上**全部为 0**；唯一相关日志在 `DefaultPlaylistGuard.kt:72/74`（自愈事件）与三端控制器的队列持久化失败。

## 六、刻意不做（带改判条件）

1. **不做歌单的云同步 / 分享链接 / 协作歌单。** 改判条件：产品边界（`AGENTS.md` §一.2「纯本地，不做在线/云同步、不引入账号、不做社交」）被明确修改。
2. **不做 m3u / pls / xspf 等外部歌单格式的导入导出。** 当前只有随全量备份的快照一条路径（D3-02 已报"备份路径内顺序丢失"这一缺陷，但"新增格式支持"不在本轮）。改判条件：用户明确提出跨平台换播放器 / 迁移需求。
3. **不设计"歌单条目上限"。** DB 无上限、UI 无上限、Agent 的 `maxItems=200` 只是给模型的 schema 提示（D3-12）。改判条件：出现真实的性能或内存问题报告（届时统一在三处设同一个上限，而不是只在 Agent 侧）。
4. **不把 `songCount` / `totalDurationMs` 改成查询时聚合。** 这是 D3-08 的"长期方案"，本轮只要求补齐刷新时机。改判条件：v10 迁移里顺带做（若届时已决定动 `playlist` 表结构），或软删与统计不一致的报障累计超过 2 次。
5. **不实现真正的长按拖拽排序。** D3-13 给的是"接上已有上移/下移回调"这一最小动作。改判条件：拖拽被排进 ROADMAP 的某个版本（届时它同时是 D8 的交互工作量）。
6. **不把 `DefaultPlaylistGuard` 之外的 iOS 播放控制器逻辑合并进 shared。** D3-09 / D3-10 只要求把"系统歌单自愈"与"心动/最近播放写入"这两件事下沉，其余 iOS 播放编排（`MusicPlayerController.swift`）保持现状。改判条件：D1 域另有结论要求统一播放控制器。
7. **不动 `playlist` / `playlist_item` 的主键与外键结构**（除 D3-03 的唯一索引、D3-05 的名字唯一索引、D3-15 的删列外）。改判条件：v10 迁移窗口内由批一（D2/D3/D5/D7）统一决定。
