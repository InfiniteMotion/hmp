## 1. 阶段定位

**三天连续三刀，把整个 Agent 体系重做一遍。**

S 补齐工具层（10 → 27），T 把架构从「Tool + 单个 chatbot」重塑为「Master + SubAgent 两层」，U 把全项目日志基础设施统一。三者是同一轮"体系级重塑"的递进：**T 需要 S 的完整工具面**（Master 要能派活给子 Agent，工具不够就无处可派），**T/U 都改 `runtime/` 与 `sub/` 同一批文件**，U 又直接取代了 T 留下的三套自封 Log。合并为一族。

## 3. T Agent 体系终局（插叙）

### 3.1 阶段诊断

> **当前诊断（2026-08-31）**：agent 是"植物人"——**闭箱、失忆、被动**。27 原子工具 + 引擎循环 + 确认护栏都齐全，但：
> - 跑一轮对话 = 醒一次，醒来就失忆（跨会话零积累）
> - 闭箱运行：agent 调 `playback_play_at` 让你听一首歌，但你手动跳过 → agent 不知道
> - 完全被动：只有你发消息才运行，不会主动排下一首
> - 学习闭环断裂：跳过了 agent 推的歌 = 无事发生，永远第一次见面
> - LLM 是单故障点，额度耗尽 = agent 死

> **根因**：当前架构只有 Tool + 单个对话 Agent 两层。这个 Agent 就是 chatbot——一次性 `run()`、被动响应、无自主行为。缺的是：独立的长期运行时（Sub Agent）、跨 Agent 共享的感知/记忆/配额管理。

> **本阶段定位**：重塑 Agent 体系的**基础设施层 + Master 内核 + Enrich 端到端**，Radio SubAgent 留 M6 填实现（T 只预留基类）。**不推倒重来**——现有 chatbot（`AgentOrchestrator`）、27 原子工具、`ToolRegistry` 全部复用，T 是「在现有 chatbot 上焊一层 Master 管理逻辑 + 加一个 Enrich 执行器」。

### 3.2 架构定案

**设计铁则 F1–F6**（完整论述与两层结构图见 `../design/agent-architecture.md`）：

| 编号 | 铁则 | 反对什么 |
|------|------|----------|
| F1 | **Master 是唯一大脑**：派发任务、验收结果、决定子 Agent 生命周期，全部收口 Master；子 Agent 只有执行权，无决策权 | 子 Agent 自毁、自己找活干、自己判断完成 |
| F2 | **每个 Agent = 独立 LLM 实例 + 独立 `AgentContextBudget`** | 全局一份 ContextBudget 分账、串行调用 |
| F3 | **全局唯一 `AgentScheduler`**：纯规则、零 LLM，只管「Agent 能不能跑」 | ContextBudget 兼管运行仲裁 |
| F4 | **Master 的派活/验收循环是轻量规则协程**，不用 LLM | Master 用 LLM 判断富化是否完成 |
| F5 | **Enrich 的 system prompt 由 Master 生成并注入** | Enrich 自改 prompt、自调整策略 |
| F6 | **SubAgent 是纯无状态执行器**（除自己的 history），不知道"任务是否完成"、不知道"当前是不是 WiFi" | 子 Agent 持有全局状态感知 |

**双层结构**：第一层 = Agent 内部（Master 128K 窗口 / Enrich 32K 窗口 / 各自独立 LlmTransport，物理并行）；第二层 = 全局共享纯规则（`AgentScheduler` + `GlobalTokenCounter` + `ToolRegistryView` + `PresenceBus` + `AgentMemory` + `AuditLogPort`）。

**关键澄清**：`AgentContextBudget`（每 Agent 独立，管上下文窗口）与 `AgentScheduler`（全局唯一，管能不能跑）是**两件不同的事**——此前混淆为一体。

## 4. U Kermit 日志体系统一治理（插叙）

> **问题**：全项目零统一日志基础设施。Agent 体系自封了三套几乎一模一样的 `object AgentLog` / `AgentRuntimeLog` / `AgentSubAgentLog`（底层全是 println + 不同 TAG 前缀），加上其余 40+ 处裸 println 散落各模块。println 在 Android 上输出到 `System.out`（Logcat 里混在系统输出中无法按 TAG 过滤），iOS 上仅进 App 沙箱 stdout（Xcode Console 看不到）。根因是项目从未引入过 KMP 日志库。

> **方案**：引入 [Touchlab Kermit 2.1.0](https://github.com/touchlab/Kermit)——KMP 社区事实标准，Apache 2.0，三端原生桥接（Android → `android.util.Log` 进 Logcat、iOS → `OSLog` 进系统日志、Desktop → stdout + ANSI 颜色）。纯 Kotlin 库零外部依赖代价，立即获得 Logcat TAG 过滤、iOS 系统日志可见、Release 级别裁剪、per-tag 覆盖、测试捕获能力。

| 项 | 内容 | 结果 |
|----|------|------|
| U-T1 依赖引入 | `libs.versions.toml` 加 `kermit = "2.1.0"` + library alias（`co.touchlab:kermit`）；shared + shared-ui 的 commonMain 加依赖 | ✅ 类路径可见，`compileKotlinDesktop` 通过 |
| U-T2 三端初始化 | Android `MusicApplication.onCreate()`、Desktop `HmpDesktopApplication` main、iOS `AppDelegate` 各自设 `Logger.setMinSeverity`；统一走 `platformLogWriter()` | ✅ 三端原生桥接生效 |
| U-T3 三套 Log 合并 | 删除 `AgentLog.kt` / `AgentRuntimeLog` / `AgentSubAgentLog`；~40 处 Agent 日志调用改 Kermit；Tag 层级 `Agent.Master` / `Agent.Scheduler` / `Agent.Enrich` / `Agent.Tool` / `Agent.ReActLoop` / `Agent.LlmCall` | ✅ `grep AgentLog\|AgentRuntimeLog\|AgentSubAgentLog` 零结果 |
| U-T4 裸 println 迁移 | 扫描 66 处 `println(`，迁移 Repository + DailyRecommendation 域（Desktop/FFmpeg 平台特定实现延后）；Release 构建 BuildConfig 注入 `Severity.Warn` | ⚠️ 部分迁移，Desktop/FFmpeg 待续 |

**退出核验**：`compileAndroidMain` / `compileKotlinDesktop` / `desktopTest` 全绿；三端原生桥接生效。

**刻意纪律**：

- 不在本阶段引入 `kermit-io`（文件日志轮转）、`kermit-crashlytics`（崩溃上报）等扩展——本地播放器 + 单人开发，console 足够
- 不做 `withTag` 作用域工厂、Coroutine 上下文传播等高级特性——保持 API 极简（静态调用 + TAG 字符串）
- `truncate()` 辅助方法不复用 Kermit API，在消息字符串模板中内联处理——避免自定义 wrapper 增加间接层

## 5. 经验与踩坑

- **"植物人"诊断的启示**：功能齐备 ≠ 体系可用。27 工具 + 循环 + 护栏都有，agent 依然闭箱失忆被动——缺的不是能力，是**运行时**。诊断要先问"它有什么结构性缺失"，而不是"它少哪个功能"。
- **过度设计要敢废弃**：T 阶段初版定义 5 根脊柱，过度设计（`AgentProfile` 独立 DAO 层 / `AgentSenses` expect-actual / Scheduler 复活 / `FallbackOrchestrator` 独立类），被第二轮重写完全取代。**定案比初稿重要**。
- **`ContextBudget` 两层混为一谈是设计事故**：一个管"上下文窗口"、一个管"能不能跑"，职责完全不同却长期被当成一回事。拆开后 F2/F3 才立得住。
- **`AgentContextBudget` 的 `estimatedTokenCount` 只累加用户侧**——`callLlmText` 不把 assistant 回复追加到 history。对 Enrich 无碍（context 全手动拼），但将来要做精确 token 成本控制时需补（详见 F6）。
- **聚合查询优先 Kotlin 侧 `groupBy`**：不新增 DAO SQL，避免三端平台层同步成本。代价是数据量大时内存占用，本项目量级可接受。
- **自封日志是隐性技术债**：三套 `object XxxLog` 长得几乎一样、底层都是 println，谁也没先统一。这类"每人自建小工具"的债拖久了会变成事实标准。
