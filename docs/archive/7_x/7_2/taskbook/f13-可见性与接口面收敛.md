# F13 · Agent 工作收尾（可见性收敛与测试覆盖）

> **设计依据**：[`../design/agent-architecture.md`](../design/agent-architecture.md) §「可见性与接口面」
> **性质**：**收尾章** —— 方向 B（agent-build）的最后一章。F1–F12 建完了能力面，
> 本章不加任何能力，只回答"能不能放心收工"：**分层要有编译期保证 / 结论要能复跑成证据 /
> 新增代码要盖上测试**。不改任何对外行为契约。
> **依赖**：F5（多 Agent 运行时与 SubAgent 体系）+ F12（Token 计量的收口经验）。与 F10 无依赖，可并行。

***

## 0. 为什么收尾

F1–F12 已把 agent 的能力面建完（对话 / 电台 / 富化 / Hello / 报告 / 设置 / 后台保活 / Token 治理），
2026-09-20 又完成包结构全量重整（分层单调 / 0 反向边）。但"能跑"不等于"能收工"，
收尾章盯住三个可维护性问题：

1. **影响面谁说了算** —— 包分层只是约定，不是强制：Kotlin 的可见性只有
   `public` / `internal` / `protected` / `private` 四级，**没有「包内可见」**
   （Java 的 package-private 被官方去掉）。`package` 纯属组织手段，不携带任何访问控制能力 ——
   包名写得再准，也拦不住一句 `import`。实测 `internal` 仅占全部声明的 **5.3%**（30 处 / 565 处）。
   后果有二：
   - **重构没有把握**：改一个方法前只能"全局搜一下谁在用"，而该搜索**不可靠** ——
     字符串字面量（`title = "RadioSubAgent"`）与 KDoc 交叉引用会污染结果，
     全限定名引用又会被漏掉。搜索不可靠 ⇒ 不敢动 ⇒ 代码僵化。
   - **坏依赖会合法长出来**：`HelloSlideCards` 直接依赖 `EnrichSubAgent.EnrichProgress`、
     `ChatAgentGateway` 直接调 `ContextAssembler` —— 都是 public，无人拦截，且会继续扩散。

2. **结论怎么变成证据** —— "0 反向边""编译绿""测试全绿"这类结论必须能**复跑**，
   且脚本本身要先被质疑（本章两次被自己写的正则坑出假阴性/假阳性，见 §3.3.6 / §3.6.2）。

3. **新增代码有没有盖测试** —— 多个阶段新增的引擎件与抽取物零测试覆盖；
   盘点时还出现过"32 个 agent 类零覆盖"的**误报**（既有测试实际已覆盖大部分），
   说明覆盖结论本身也需要工具化核实（Glob 交叉比对 75 源文件 × 既有测试类）。

**本阶段的产出不是"更整齐的代码"，而是三样东西：判断影响面的能力（编译器回答"谁在依赖我"）、
可复跑的证据链（反向边复测 / DI 图核对 / 六任务编译 / 测试 XML 计数）、以及收口时的
desktopTest **961 例全绿（119 类）**。**

**伴随线：结构对齐与清理** —— domain 侧按分层重排的同时，shared-ui 同步重组为 `agent/`
子包（`chat` / `config` / `monitor` / `shell` / `cards` / `port`），与 domain 分层镜像；
顺带清掉死代码与假控件：`DailyRefreshConfig`（日刷新已由 HelloSubAgent 自管）、
`AiExtraEnrichPort`、`EngineConfig`（拆为 `config/` 叶子包）、
`LoadMusicExtraInfo`·`DailyRefreshSettings`（零调用方孤儿函数）、
`WindowedBundle.narrative`（恒空死字段）。

## 1. 判据（两条，勿混）

1. **可见性看「跨不跨模块」，不看「重不重要」。**
   `AgentScheduler` 很关键但 shared-ui 永远不需要 → `internal`；
   `RadioTrack` 只是 19 行数据类但 `RadioConsole` 要渲染队列 → 必须 `public`。
2. **`internal` 的边界 = Gradle 模块边界 = `:shared`。**
   无需新建模块 —— `:shared` / `:shared-ui` 的边界早已画好，本阶段只是让访问权限**跟上既有边界**。

## 3. 阶段

> 阶段 1–6 为**可见性主线**（把分层升级为编译期保证，并把每个结论做成可复跑证据），
> 阶段 7 为**测试覆盖**（给新增代码盖测试）。结构对齐与清理伴随线见 §0、修订史与 README 2026-09-20 各条。

| 阶段 | 内容 | 产出 | 状态 |
|---|---|---|---|
| **1** | 收口 runtime 实现层「仅模块内使用」的 38 个顶层声明 | **越界清单**（编译报错即真实依赖） | ✅ 2026-09-20（随 `ba25365` 落库） |

**核心手法 —— 编译反推法**：判断「哪些是门面」不靠人工读代码，而是
**先把候选全部标 `internal` → 编译 → 报错处即「确实存在跨模块调用者」→ 改回 `public`，
其余保持 `internal`**。边界由编译器算出，而非猜测。

> 实际执行时该手法比预期更有效：38 个候选一次性全标 `internal` 后，编译器只报出
> **23 处**问题（而非 38 处失败），这一轮编译就把「谁在依赖谁」的事实全部摊开了。
>
> 阶段 3b 里它再次证明有效：55 个候选一次性全标 `internal`，编译器报 **67 处**（去重后
> **33 个成员名**）⇒ 一次编译直接得到"最终门面清单"。**该手法能替代人工审计，是它最大的价值。**

## 3.1 阶段 1 实况（2026-09-20）

**结果：38 个候选 → 净收口 18 个 / 被迫公开 20 个。三端编译绿。**

**净收口 18 个**：

- **电台内部词汇表 10 个**（内聚性最好的一组，`RadioSession` 一家占 9 个）：
  `RadioSession` + `RadioTriggerCause` / `RadioAction` / `RadioVerdict` / `RadioQueueEntry` /
  `RadioContextSnapshot` / `RadioConversation` / `RadioSessionArchive` / `REUSE_BACKSTOP_MS`
  + `RadioSubAgent`
- **引擎循环件 4 个**：`ReActLoop` / `ToolCallExecutor` / `LlmCallExecutor` / `CollectedLlmResult`
- **其余 4 个**：`AlwaysRunningStopSignal` / `HelloMemory` / `DefaultSystemConditions` / `L10N_PROMPTS`

**被迫公开 20 个**（登记为阶段 3 的输入）：

- MasterAgent 公开面顶起的**调度/计量词汇表**：`AgentScheduler` / `AgentPriority` /
  `AgentRegistration` / `GlobalTokenCounter` / `TokenMeter` / `SystemConditions` /
  `StopSignal` / `SchedulerStopSignal` / `AgentResult`
- UI 直接订阅或继承相关的：`RadioCardState` / `RadioTrigger` / `RadioMessage` /
  `HelloSubAgent` / `SubAgent` / `AgentContextBudget` / `ToolRegistryView` /
  `RadioTrackSource` / `GlobalAgentConfig` / `Lang` / `detectSystemLang`

**两条关键发现（修正了原计划）**：

1. **`MasterAgent` 的装配位于 shared-ui** —— `ChatKoinModule.kt:89` 直接 `MasterAgent(...)`，
   UI 模块 new 领域对象并**注入 `GlobalTokenCounter` / `TokenMeter` 等引擎内部件**。
   这是 20 个「被迫公开」的主因，也是真正的耦合点。
   ⇒ 它对应 §5 已登记约束「装配位置本身是否合理是独立议题」。
2. **类的可见性带动整簇相关类型** —— `AgentScheduler` 一旦 public，`AgentPriority` /
   `AgentRegistration` 就必须跟着 public。**不能只收口簇内的一部分**；
   收口单位是「可见性簇」而非单个类型。
   ⇒ 这也解释了为什么 `MasterAgent` 不动，调度/计量一整簇就都收不了口。

**验收**：Desktop / Android / iOS 三端 `BUILD SUCCESSFUL`（0 error）。

## 3.2 阶段 2 预演（只读分析，未落地）

对 `MasterAgent` 的 **46 个公开方法（47 处含重载）+ 12 个公开属性 = 58 个公开成员**
做调用面分析：

| 分类 | 数量 | 含义 |
|---|---|---|
| 跨模块在用 → 必须留在门面 | **37** | 有真实外部调用者 |
| 跨模块零用 → 可降 `internal` | **21** | `batteryLevel` / `capabilities` / `enrichStatusSummary` / `isEnrichActive` / `isWifiConnected` / `pauseRadio` / `resumeRadio` / `queryHelloCards` / `querySubAgents` / `startHello` / `stopHello` / `shutdown` / `subAgents` / `systemConditions` 等 |

**关键判断：37 个"外部在用"里，并不都是合理接口。** 需要再分两类：

- **合理的 UI 接口**（状态订阅与用户操作）：`radioState` / `radioCardState` / `radioPlaylist` /
  `helloAgent` / `enrichProgressState` / `handleUserMessage` / `startRadio` / `stopRadio` /
  `getGlobalAgentConfig` / `saveAgentPolicyConfig` 等 ⇒ 留在门面。
- **引擎内部机制泄漏**（UI 不该碰）：`lifecycleScope`（`ChatKoinModule` 取引擎生命周期作用域）、
  `scheduler`（测试取调度器）、`tokenCounter`（看板取计量内部件）、
  `initialize`（UI 触发引擎初始化）、`ensureProfileReadyForFirstTurn`（引擎内部准备逻辑）
  ⇒ **这才是阶段 3「抽门面」真正的靶子**。

## 3.3 阶段 3 实况（2026-09-20）

### 3.3.1 先做装配迁移（用户选"彻底版"）

**动作**：把 `MasterAgent` 的整套 Koin 装配从 `shared-ui/.../chat/ChatKoinModule.kt`
（删除 80 行）迁到 `shared/.../di/SharedModules.kt`（新增 86 行 + 注释）。

**为什么必须先做它**：阶段 1 已查明 20 个「被迫公开」里，**调度/计量词汇表一整簇**
是被 UI 模块的装配顶起来的（UI 直接 `MasterAgent(...)`，注入 `GlobalTokenCounter` /
`TokenMeter`）。**只要装配还在 shared-ui，这一簇就永远收不了口。**

**迁移后不需要改的**：`ChatKoinModule` 仍是 shared-ui 的模块，只是不再 new 领域对象。
装配中经**端口接口**解析的 bean（`PlaybackCommandPort` / `NowPlayingContextProvider` /
`AiExtraEnrichPort` 适配器、`ToolRegistry` / `PolicyGuard` / `SessionStore` / `PresenceBus`）
仍由 shared-ui 注册 —— Koin 惰性求值，与模块加载顺序无关，故跨模块解析成立。
**注释里显式写下了这个前提**，避免后人误以为"装配在 shared 就必须在 shared 注册全部依赖"。

**验证**：`:shared:compileKotlinDesktop` + `:shared-ui:compileKotlinDesktop` 双绿（0 error）。

### 3.3.2 收口结果（编译反推法，一次性摊开）

**结论二：两个"隐藏的第三个模块"暴露了 —— 只扫 shared-ui 会得到假结论。**

`:android:app` 与 `:desktop:app` 都调 `MasterAgent.close()`（进程退出兜底）。
**首次只编译 shared-ui 时它是绿的，编译 Android 才炸。**
⇒ 教训：**跨模块可见性判断必须把所有消费模块都编一遍**，否则"编译绿"不是证据。

### 3.3.3 抽门面的范式（本阶段唯一一处方法级门面）

`GlobalTokenCounter` 是**写入侧**（`recordTokens` / `shouldStop` / 日滚动），
UI 只需要**读取形状**。做法：把 `TokenSnapshot` 从内部类里**提为公开顶层数据类**，
`MasterAgent` 增一条只读门面：

```kotlin
val tokenUsage: StateFlow<TokenSnapshot> get() = tokenCounter.snapshot
```

UI 改读门面后，计数器本体收敛为 `internal`。

**判据（可复用）**：**外部要的是"看到什么"而不是"能做什么"时，抽数据形状比抽方法更省事、也更难被滥用。**
同法用于三个构造器：`AgentContextBudget` / `EnrichSubAgent` / `HelloSubAgent` 的构造器
收为 `internal` —— 类保持 public（可被传递与读取），但**外部造不出来**，装配权归领域模块。

### 3.3.4 阶段 3c 实况：拆巨型类（2026-09-20）

**先前的判断（保留，作为"该不该拆"的依据）**：3c 一度被判为独立后续 ——
拆类的收益是"可读性"，而本阶段目标（判断影响面）已由可见性达成；且拆类必须先冻结接口面。
接口面既然已冻结（门面清单由编译产出、可复跑校验），3c 遂在同日开工。

**结果：4 个巨型类 → 7 个新文件；「纯逻辑 / 词表」部分全部外移。**

| 巨型类 | 拆前 | 拆后 | 外移物 |
|---|---|---|---|
| `EnrichSubAgent` | 1179 | **591** | `EnrichPrompts`（304）· `EnrichResponseParser`（275） |
| `HelloSubAgent` | 1969 | **1801** | `HelloGreetingProfiles`（236） |
| `RadioSubAgent` | 1869 | **1734** | `RadioModels`（113）· `RadioSeedKeywords`（49） |
| `MasterAgent` | 1811 | **1753** | `ChatIntentRules`（106） |
| （三 Agent 共用） | — | — | `runtime/JsonText`（79） |

> 上表是 **3c 当时的快照**。阶段 5 又改了三个数（§3.5）：
> `MasterAgent` 1753 → **1751**（表驱动）、`HelloSubAgent` 1801 → **1844**（会话状态收进 `HelloSessionState`，
> 含说明性 KDoc，**行数增加是刻意的**）、`AgentContextBudget` 274 → **307**（新增 `callOnce`）。
> 权威行数见 `../design/agent-architecture.md` §源码位置索引。

**手法 —— 只搬"没有状态"的东西。** 这四个类里真正纠缠的是**状态**
（`MutableStateFlow`、生命周期 mutex、run loop job、实例配置），而**状态搬不走**：
搬它就得把开关它的方法一起搬，等于把 Agent 整个复制一遍。
因此 3c 的切分线定在「**这段代码需不需要这个对象的状态**」：

- 不需要 → 外移成 `object`（纯函数 / 常量表）
- 需要 → 留在类里

这条线让每一步都是**机械移动 + 编译验证**，没有一处需要重新设计逻辑。

**由此得到一条判据（本轮最有复用价值的一条）**：

> **`private` 保护的是「不变量」，而无状态纯函数与常量表没有不变量。**
> 因此把一个纯函数从类里搬到同模块的 `object`（`private` → `internal`）**不构成可见性回退** ——
> 没有状态可被破坏。反过来说：**带状态的成员不能这样搬**，那才是真正的回退。

**顺手修掉的三处重复**（都是"写着共用、实则各抄一份"）：
1. `extractJsonBlock`：`EnrichSubAgent` 与 `HelloSubAgent` 各一份，后者注释还写着
   "与 EnrichSubAgent.extractJsonBlock 同逻辑，工具型 Agent 共用" ⇒ 合并为 `JsonText`。
2. 电台风格词表：`isRadioIntent` 与 `extractSeed` 各内联一份**逐字相同的 13 行**。
   改一处漏一处不报错，只会让"判为电台意图"与"抽出的种子"对不上 ⇒ 合并进 `ChatIntentRules`。
   （另：原停止电台表里 `"stop radio"` 重复出现两次，一并去重。）
3. 问候类型的属性：原先散在**四个平行分支**里（写作要求 / 角色 prompt / 温度 / 兜底文案池），

### 3.3.5 3 处已知越界点的最终处置

| # | 越界点 | 处置 | 理由 |

| 1 | `ChatAgentGateway` → `ContextAssembler` | ⏸ **判为正当接口** | `ContextAssembler` 是 118 行**无状态纯格式化**工具（`buildNowPlaying` / `buildRecognitionProgress` / `buildLibraryOverview` / `buildTimeOfDay`）。`ChatAgentGateway` 组装首轮上下文时**必须与引擎用同一套格式化**，否则同一份"正在播放"会被两处渲染成不同文本。收口的正解不是把它标 internal，而是**把首轮上下文组装整体移进 MasterAgent**（让 UI 只传原始数据、不再自己拼 prompt 片段）—— 那是独立重构，不在本阶段。**判为正当接口并记录理由**（验收条件允许） |

**结论**：3 处越界点 **1 修 2 判**。两条判定都遵循同一原则 ——
**「同源一致性」优先于「可见性纯净」**：当外部必须与内部产生**逐字一致**的结果时，
强行收口只会催生复制品，那是比多一个 public 更坏的结局。

### 3.3.6 复测反向边时发现并修掉 1 条既存反向边（勘误）

复测脚本报出 `tool.spec → tool` —— `tool/spec/ToolRegistry.kt:72` 的成员方法

2. **`package` 声明行会被误判**：`package com.hmp.domain.agent.tool.spec` 按"取最后一段之前的包"处理后

既会漏掉函数体里的全限定名，又会把 `package` 行误判成依赖 ——
**结论依赖脚本，脚本本身要先被质疑。**

### 3.5.2 ⚠️ 单测抓出的真缺陷：`EnrichResponseParser` 裸对象兜底是死代码

`extractJsonArrayElements` 判断"输出是否被数组包裹"时只看 `indexOf('[') >= 0`。
而 Round 1 的三个字段（genre / mood / scenario）**本身就是数组** ⇒ 裸对象里必然含 `[`
⇒ 恒被判为"有数组包装" ⇒ 切出 0 个对象 ⇒ **兜底分支永不执行**。

后果不是崩溃，而是**静默**：模型偶尔漏掉外层 `[...]` 时，整轮富化结果无声丢光。
（`parseEnumBatch_acceptsBareObjectWithoutArrayWrapper` 首次运行即抛
`NoSuchElementException`，正是这个死分支。）

**修复**：

```kotlin
val firstBrace = cleaned.indexOf('{')
val hasArrayWrapper = firstBracket >= 0 && lastBracket > firstBracket &&
    (firstBrace < 0 || firstBracket < firstBrace)      // '[[' 必须出现在第一个 '{' 之前
```

并同时修掉兜底分支把**对象序列**当成单个对象的问题（改走 `JsonText.splitJsonObjects`）。

> **这条印证了"先补测"的排序理由**：纯函数最容易出**"不报错、只是安静地算错"**的缺陷，
> 而这类缺陷永远不会在集成测试里显形 —— 因为没有异常、没有崩溃，只是结果变少。

## 3.6 阶段 6：人工核对 DI 图（2026-09-21）

**为什么要单独做这一步**：本阶段全部收口结论都建立在「编译器会拦住越界」之上，
而 **Koin 是运行时容器** —— 如果它走反射或代码生成，编译期可见性就可能被绕过，
「编译绿」也就不再是充分证据。验收条件把它单列为一项，正是为此。

### 3.6.1 核对结论：**Koin 不会绕过编译期可见性**

三条实证（任一不成立则需要更重的处置）：

| # | 待验证的绕过路径 | 实测结果 |
|---|---|---|
| 1 | **注解 + 代码生成**（`@Module` / `@Single` ，或 `koin-annotations` + KSP/KAPT） | ❌ **不存在** —— 全仓零 Koin 注解，`libs.versions.toml` 只声明 `koin-core` / `koin-android` / `koin-compose*`，**无 `koin-annotations`，无 KSP/KAPT 处理 Koin** |
| 2 | **反射按类型名解析** | ❌ **不存在** —— 全部装配为 `module { single { … } }` DSL，`get<T>()` 是**泛型函数**（`inline fun <reified T> get()`），类型以 `reified` 在**编译期**实例化，不是字符串查表 |
| 3 | **按字符串/动态加载模块** | ❌ **不存在** —— 三端 `startKoin { modules(…) }` 全部传 **Kotlin 对象引用**（`sharedModule` / `androidPlatformModule` / `playerModule` / `uiModule` …），无 `getBean`、无 `loadModule`、无字符串键 |

**推论（本项验收的实质结论）**：
因为 `get<T>()` 的 `T` 参与编译期解析，**一个 `internal` 类型若被 `:shared` 之外的模块 `get<T>()`，
编译器必然报错**（与阶段 3b 的 `'public' function exposes its 'internal' return type` 同理）。
⇒ **F13 全部可见性收口的结论成立，"编译绿"在 Koin 这一点上是充分证据。**

> 附带确认：唯一的 `by inject()` 用法在 `MainActivity`（`MusicController` / `UserSettingsUseCase`），
> 两类型均为 public 门面，合规。

grep -rhoP "single<\K[A-Za-z_]+(?=>)" --include="*.kt" shared/src shared-ui/src android desktop | sort -u
# ② internal 顶层类型集合

它来自 `single { GlobalTokenCounter(…) }` 的**推断类型注册**，被 ① 的第二个正则误捕；
实际类型正确为 `internal`，且只在 `:shared` 内以 `get()` 解析，**合规**）。

> ⚠️ **又一次印证 §3.3.6 的教训**：这个假阳性是自己写的正则造出来的，
> 与当初「`package` 行被误判成依赖」同一性质。**结论依赖脚本，脚本本身要先被质疑** ——
> 但凡报出问题，必须回到源码逐条确认，不能直接采信工具输出。

### 3.6.3 顺带抓出的真缺陷：`Json` 被重复注册（已修）

核对过程中逐模块比对 bean 集合，发现 **Android 端 `Json` 被注册了两次**：

| 注册点 | 写法 | 实际 |
|---|---|---|
| `sharedModule`（commonMain，三端共用） | `single { createJson() }` | 推断类型 = `Json` |
| `androidPlatformModule`（androidMain） | `single<Json> { Json { ignoreUnknownKeys = true; isLenient = true; encodeDefaults = true } }` | 显式 `Json` |

两处**逐字等价**，且 `MusicApplication` 在同一次 `startKoin` 里同时装载两个模块。

**为什么今天不出事**：Koin 默认 `override = true`，后者**静默覆盖**前者 —— 行为无差异，测试全绿。
**为什么仍是缺陷**：

1. **漂移不可见**：一旦有人只改一处（例如给 `createJson()` 加个 `explicitNulls = false`），
   **Android 与 Desktop/iOS 就会用上配置不同的 `Json`**，而这在编译期、运行期**都不报错** ——
   只会在某个平台的解析行为上悄悄分叉。这正是本项目反复出现的「静默故障」模式（同 F12 的超窗静默）。
2. **假证据**：`override` 让"注册了两份"这件事在日志与测试里都看不出来，掩盖了模块职责重叠。
3. 它是 **F13 阶段 1 那条改动的残留** —— `git log` 显示该注册随 F12 收尾（`07ab544`）加入，
   当时正做装配迁移，两份定义被同时留下。

**处置**：删除 `androidPlatformModule` 中的重复 `single<Json>`（含随之失效的 `kotlinx.serialization.json.Json` import），
留注释说明「`Json` 由 `sharedModule` 统一提供」。
**消费者不受影响**：全仓无 `get<Json>()` 显式调用，消费者均为构造注入 `json = get()`，
现在三端统一解析到 `sharedModule` 那一份（= Desktop/iOS 原本的行为，Android 行为不变）。

**验证**：`:shared:compileAndroidMain --rerun-tasks` **BUILD SUCCESSFUL / 0 error**
（已确认任务确实执行，非 UP-TO-DATE 跳过）；
三端 `Json` 真实注册数：`AndroidModules` 0 · `DesktopModules` 0 · `IosModules` 0 · `sharedModule` 1 ⇒ **唯一提供者**。

**判据沉淀**：**「重复定义 + override 静默覆盖」是比「缺失定义」更危险的形态** ——
缺失会当场报错，重复则表现为"一切都好"，直到两份定义漂移的那天。
