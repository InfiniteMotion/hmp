## 0. 为什么要有这个模块

`agent-architecture.md` 有两处承诺，代码里一处都没兑现：

| 位置 | 承诺 | 实际 |

| `agent-architecture.md:130` | Master system prompt = persona + **偏好画像** + 曲库概况 + 认识进度 | `ContextAssembler.assembleFirstTurnBlock()` 只有 persona / 称呼 / 当前曲目 / 时段 / 曲库概况 / 认识进度 —— **画像缺席** |

**现状不是"画像完全不存在"，而是「只剩账本、没有认识」**：agent 能拿到的用户信息只有 `library_stats` 工具的**全时段累计**（总播放/跳过/时长/喜爱 + topGenres/Moods/Artists）与 `library_recent_history` 的原始流水。缺时间窗、漂移、置信度、审计、跨会话累积。

本文把这条线正式认领为一个模块。

## 1. 定位

| 项 | 定义 |
|----|------|
| 归属 | 隶属 `MasterAgent`，是其持有的**常驻模块**（与 `HelloSubAgent` 同级，但生命周期贯穿应用而非按需创建） |
| 形态 | 独立模块 `domain/agent/profile/`，对外暴露读写两个面；**不是** SubAgent（不派活、不参与 Scheduler 竞态） |
| 输入 | ① **曲库内容**（扫描 / 富化两阶段）② **播放记录**（定时聚合）③ **状态快照**（收藏 / 歌单 / 标签编辑 / 隐藏文件夹）④ **对话** ⑤ **用户操作**（设置页修正与否决） |
| 输出 | 侧写集合（产品面）+ 证据行集合（审计面），两者均持久化 |
| 用途 | 为 agent **构建依据**：首轮上下文注入、子 Agent 决策参考、设置页「伙伴对你的认识」、消费面人格卡 |

### 1.1 与既有概念的分界

| 概念 | 认识的对象 | 落点 | 关系 |
|------|-----------|------|------|
| 富化（`EnrichSubAgent`） | **每首歌** | `MusicLabel` + `MusicExtra` | 兄弟层：一个认识世界，一个认识用户 |
| 画像（本模块） | **用户** | `user_profile_evidence` + `user_profile_portrait`（§2.4） | 本模块 |
| `HelloMemory` | **今天的卡片** | `hello_card_cache` | 不是画像：当日卡池的防重复缓存，无用户模型语义 |
| `CompanionProfile` | **伙伴自己** | DataStore | 反向：那是伙伴的人格，这是对用户的认识 |
| `TrustLedger` / `AgentPolicyConfig` | **用户对伙伴的授权** | DataStore | 可受画像影响，但本身是策略不是认识 |
| `SessionStore` | **本次会话** | 内存 | 对应 L1 层；画像是跨会话的 |

### 1.2 三条不可协商的边界

1. **画像只提供依据，不下发动作。** 模块内不产生播放指令、不建歌单、不改标签。
2. **证据行必须可审计**（§2.6）；**侧写是派生物、不参与审计四问** —— 它是从证据算出来的，删掉重算即可。
3. **画像不出设备**（对齐 `agent.md` 产品边界「伙伴只属于你 —— 记忆只存设备」）。唯一对外发生在用户自填端点，配置时给一句提醒（§9）。

### 1.3 数据流总览（一张图看懂这个模块）

```
流入（6 个源，按性质分）                模块内部                           流出（4 个消费面）
──────────────────────                 ────────                           ──────────────
【一次性事件】
  扫描完成        ┐
  富化完成        │
【定时聚合】      │                   证据层 ──► PortraitComposer ──► 侧写层 ──┬──► Master 上下文块
  播放记录        ├──────────────►   user_profile_   纯函数 ·        user_profile_│   （L3 全部 + L2 高分）
  状态快照        │                  evidence        唯一派生点      portrait    ├──► 子 Agent
【会话事件】      │                  （四列溯源）     （§4.6）       （L2 / L3）  │   （只读工具 profile_read）
  对话结束        │                                                             ├──► 设置页
【用户操作】      ┘                                                             │   （侧写分组 + 证据反链）
  设置页修正/否决                                                               └──► 消费面
                                                                                   （音乐人格卡 · 不得回流决策面）

未来流入（不占 F9-T0 范围）：搜索关键词
待议：曝光未播（出现在推荐/卡片/队列但未被点 —— 唯一能反映"沉默的偏好"的源）
```

**四条纪律在这张图上的位置**：

| 纪律 | 在图上的含义 |
|------|-------------|
| 所有建模器只**产证据**、不直接写侧写 | 六个源**全部指向证据层**，没有一条绕过它直连侧写层 |
| 侧写**只有一条派生路径** | 证据层与侧写层之间**只有** `PortraitComposer` 一个节点；用户改的是证据，不是侧写 |
| 消费面**不得回流决策面** | 流出侧最下面那条与最上面那条**之间没有连线** |
| 上传给 LLM 的是**侧写渲染**，不是证据原文 | 流出的四条全部从**侧写层**取值，证据层不外发 |

**流入按性质分四类的意义**（§10.1 展开）：**一次性事件**触发全量建模；**定时聚合**是持续流与状态快照，靠**累积**而非事件订阅；**会话事件**与**用户操作**是显式表达。**状态快照这一类最容易被漏** —— 收藏、歌单、设置都不"发生事件"，它们是状态，价值在**变化**，必须靠 diff 而非订阅。

## 2. 数据模型

### 2.1 为什么是两层

| 方案 | 判定 |
|------|------|
| **侧写层 + 证据层** | ✅ 采用 |
| 纯条目（扁平谓词直接面向产品） | ❌ 太逻辑向，没有"整体印象" |
| 一张快照（每次重算存一行 JSON） | ❌ 不可审计、不可单条撤销、设置页无从逐项展示，且违反「记忆变更也是工具调用」纪律 |

- **侧写层（Portrait）** = 用户与 agent 面向的**压缩印象**。预设骨架 + 槽位闭集 + 证据反链 —— 即"预设半条目"。
- **证据层（Evidence）** = 支撑侧写的**可审计事实行**。

侧写负责"整体印象"，证据负责"可追问"。**侧写永远能回答「你凭什么这么说」** —— `evidenceRefs` 指向具体证据行，设置页可展开。

### 2.2 侧写层

```kotlin
/**
 * 一个侧写 = 一个预设骨架 + 若干槽位取值 + 支撑它的证据反链。
 *
 * 为什么槽位必须闭集：开放槽位会让侧写退化成自由文本，
 * UI 没有稳定形态、LLM 没有稳定输入、设置页无法逐项展示与删除。
 */
data class Portrait(
    val type: PortraitType,                    // 闭集，见 §5
    val tier: PortraitTier,                    // L2 情境态 / L3 性情态（§3）
    val slots: Map<SlotKey, SlotValue>,        // 槽位闭集，取值从证据归纳
    val evidenceRefs: List<Long>,              // 反链到证据行
    val confidence: Double,
    val createdAt: Long,
    val updatedAt: Long,
)
```

### 2.3 证据层

```kotlin
/**
 * 一条证据 = 一个可审计的事实行。
 *
 * `predicate` 用**槽位限定名** `"<portraitType>.<slotKey>"`：
 * 谓词闭集不再单列一套 —— 它**就是** §5 的槽位闭集。
 * 两套闭集互相映射只会产生漂移（v1 的「谓词闭集 7 条」已被此替代）。
 *
 * 主键是自增 `id`（侧写反链要引用它）；`(subject, predicate, value)` 降为**唯一索引**，
 * 保证同一事实只累积、不重复建行。
 */
@Entity(
    tableName = "user_profile_evidence",
    indices = [Index(value = ["subject", "predicate", "value"], unique = true)],
)
data class UserProfileEvidenceEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val subject: String,          // v1 恒为 "USER"
    val predicate: String,        // "<portraitType>.<slotKey>"，闭集见 §5
    val value: String,
    val source: String,           // 见 §2.5 来源分档
    val confidence: Double,
    @ColumnInfo(name = "created_at") val createdAt: Long,
    @ColumnInfo(name = "updated_at") val updatedAt: Long,
    /** 审计四问·被确证过吗 —— 该事实被观察到的**总次数**（含首次） */
    @ColumnInfo(name = "evidence_count") val evidenceCount: Int = 1,
    /** L1→L2 晋升用 —— 出现过的**不同会话数**（同一会话内反复不计，§3.1） */
    @ColumnInfo(name = "distinct_sessions") val distinctSessions: Int = 1,
    /** 最近一次观察到它的会话 id，用于累计 `distinct_sessions` 时去重 */
    @ColumnInfo(name = "last_session_id") val lastSessionId: String? = null,
)
```

**两个计数器，两个用途，不得合并**：

| 字段 | 含义 | 服务于 |
|------|------|--------|
| `evidence_count` | 被观察到的**总次数** | 审计四问「被确证过吗」 |
| `distinct_sessions` | 出现过的**不同会话数** | §3.1 的 L1 → L2 晋升（**同一会话内高频不算**） |

**与 `MusicLabel` 刻意同构**（`source / confidence / created_at / updated_at` 四列）—— 两者受同一条纪律约束。

### 2.4 表结构（Room v5 → v6）

```kotlin
@Entity(tableName = "user_profile_portrait", primaryKeys = ["type"])
data class UserProfilePortraitEntity(
    val type: String,                      // PortraitType
    val tier: String,                      // L2 / L3
    @ColumnInfo(name = "slots_json") val slotsJson: String,
    @ColumnInfo(name = "evidence_refs") val evidenceRefs: String,   // 证据行 id（Long），CSV
    val confidence: Double,
    @ColumnInfo(name = "created_at") val createdAt: Long,
    @ColumnInfo(name = "updated_at") val updatedAt: Long,
    /** 内容建模的覆盖率快照，用于 confidence 折扣与重做判定（§4.1.4） */
    @ColumnInfo(name = "coverage_at_modeling") val coverageAtModeling: Double? = null,
)
```

**`evidenceRefs` 存的是证据表的 `id`**（不是 `subject/predicate/value`）—— 这正是 §2.3 加自增主键的原因：`Portrait.evidenceRefs: List<Long>` 必须有 Long 可指。

**迁移 DDL**（v5 → v6：两张新表 + 一个唯一索引，**无列变更**）：

```sql
CREATE TABLE IF NOT EXISTS `user_profile_evidence` (
  `id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  `subject` TEXT NOT NULL, `predicate` TEXT NOT NULL, `value` TEXT NOT NULL,
  `source` TEXT NOT NULL, `confidence` REAL NOT NULL,
  `created_at` INTEGER NOT NULL, `updated_at` INTEGER NOT NULL,
  `evidence_count` INTEGER NOT NULL, `distinct_sessions` INTEGER NOT NULL,
  `last_session_id` TEXT
);
CREATE UNIQUE INDEX IF NOT EXISTS `index_user_profile_evidence_subject_predicate_value`
  ON `user_profile_evidence` (`subject`, `predicate`, `value`);

CREATE TABLE IF NOT EXISTS `user_profile_portrait` (
  `type` TEXT NOT NULL, `tier` TEXT NOT NULL,
  `slots_json` TEXT NOT NULL, `evidence_refs` TEXT NOT NULL,
  `confidence` REAL NOT NULL,
  `created_at` INTEGER NOT NULL, `updated_at` INTEGER NOT NULL,
  `coverage_at_modeling` REAL,
  PRIMARY KEY(`type`)
);
```

- **`slots_json` 需要序列化**（`Map<SlotKey, SlotValue>` → JSON）：项目已带 `kotlinx-serialization-json`（`serialization = "1.7.3"`），沿用既有 `HelloCardConverters` 的 TypeConverter 习惯。
- **迁移注册**：`AppDatabase` 的 `version` 5 → 6，`MIGRATION_5_6` 加进既有 `companion object`（与 `MIGRATION_1_2` ~ `MIGRATION_4_5` 并列），两个 DAO 加进 `abstract fun` 列表。
- **迁移测试先行**：`shared/src/desktopTest/.../database/AppDatabaseMigrationTest.kt` 已有 1_2 ~ 4_5 的用例可照抄。

**为什么 `evidenceRefs` 用 CSV 而不是关联表**：规模是「≤8 个侧写 × ≤10 条反链」，关联表的 join 与 DAO 复杂度不划算。若将来需要"按证据反查侧写"，再升关联表（那时会有真实查询需求驱动）。

### 2.5 来源分档与置信度

| 来源 | 含义 | confidence 起点 | 可信度依据 |
|------|------|----------------|-----------|
| `T1_USER` | 用户显式给的（收藏 / 评分 / 对话明说 / 设置页改） | **0.9** | 用户主动表达的意图，最高 ground truth |
| `T0_BEHAVIOR` | 无意识播放行为（定时聚合） | **0.6** | 行为不会表演 |
| `LIBRARY_CONTENT` | 曲库内容建模（富化完成） | **0.55** | 聚合抵消个体噪声，但仍是"拥有" |
| `LIBRARY_SHAPE` | 曲库形态建模（扫描完成） | **0.4** | 只有结构，可能失真 |
| `T2_DIALOGUE` | 从对话推断的偏好 | **0.35** | 只是假设，等行为确证（§4.3） |
| ~~`T2_MODEL`~~ | ~~模型的歌曲认识~~ | — | **已删（2026-09-15）**：它始终没有写入时机 —— 曲库侧用 `LIBRARY_*`、对话用 `T2_DIALOGUE`，留在表里就是个空档（PF15 落地） |

**两条修正规则**：

1. **同类冲突走信任链**：`T1_USER` 手改的条目不被 T0 聚合覆盖（作用域仅限同类证据冲突）。
2. **覆盖率折扣**：内容建模的 `confidence = base × 标签覆盖率` —— 覆盖率 0.9 与 0.3 的「爵士占 38%」显然不是一回事（后者意味着库里 70% 的歌还没被认识）。一个乘法解决，不需要额外规则。

### 2.6 审计四问的适用范围

| 对象 | 是否吃审计四问 | 落点 |
|------|--------------|------|
| **证据行** | ✅ 是 | 来源 `source` / 何时 `created_at` / 被确证过吗 `evidence_count` + `updated_at`（**不是** `distinct_sessions` —— 那个只服务于晋升，不入审计口径）/ 被谁修正 `agent_audit_log`（被覆盖的旧值进审计不消失） |
| **侧写** | ❌ 否（派生物） | 但必须能经 `evidenceRefs` **向下追溯**到支撑它的证据行 |

## 3. 分级记忆

| 层 | 时间尺度 | 内容 | 载体 | 寿命 |
|----|---------|------|------|------|
| **L1 当下态** | 分钟~小时 | 在听什么、刚跳了什么、暂停没 | 内存（`SessionStore` / 观测面） | 会话结束即散 |
| **L2 情境态（短时人格）** | 天~周 | 「最近在循环这张」「这阵子偏民谣」 | Room + 衰减 | 2~4 周无新证据自动失效 |
| **L3 性情态（人性）** | 月~年 | 「夜里听歌的人」「不太爱跳歌」 | Room 长期 | 需长期背离才降权，**不自动删除** |

### 3.1 跨层流动规则（分级真正的价值所在）

| 流动 | 规则 | 承载字段（§2.3） |
|------|------|----------------|
| L1 → L2 | 同一事实在**不同会话**里重复出现 ≥ N 次（默认 3）。**单次会话内的高频不算** —— 那是场景，不是偏好 | `distinct_sessions ≥ N`（靠 `last_session_id` 去重累计） |
| L2 → L3 | L2 条目持续存在 ≥ M 周（默认 3），且**每次聚合都有新证据续期** | `created_at` 距今 ≥ M 周，且 `updated_at` 每轮刷新 |
| L3 降权 | 连续 K 周无证据（默认 4）+ 行为背离 → 降 `confidence`；低于阈值不再进上下文，**但不删除**（设置页仍可见） | `updated_at` 距今 > K 周 |
| 任意层 → 覆盖 | `T1_USER` 直接覆盖任意层 | 同 `(subject, predicate, value)` 的旧行按 §2.5 规则一处理 |
| **对话推断** | `T2_DIALOGUE` 默认落 L2，**不自动升 L3** —— 必须被播放行为确证才升（§4.4） | 来源判断 + 上表的 L2 → L3 条件 |

### 3.2 反例保护（分级记忆存在的首要理由）

**单次极端行为（一首歌循环 50 遍）只进 L2，不升 L3。** 一次情绪化行为不该变成人设 —— 这比"节省存储"重要得多。

### 3.3 与来源分档是正交的两个维度

- **分级（L1/L2/L3）** = 时间稳定性：同一份认识能活多久
- **来源分档（T1_USER / T0_BEHAVIOR / …）** = 证据可信度：这份认识有多硬

曲库形态证据可以进 L2 也可以进 L3，取决于它稳定了多久。**别把两者混起来。**

**为什么 L1 不落库**：它就是当前会话的上下文，`SessionStore` 已有。

## 4. 建模器

两个**平级**建模器，都只产出**证据**，不直接写侧写 —— 侧写统一由 `PortraitComposer` 算出（保证"只有一条派生路径"）。

```
曲库建模  ── 按【认知深度】成熟：形态（扫描完成） → 内容（富化完成）
行为建模  ── 按【数据积累】成熟：播放记录 / 状态快照，定时聚合
对话侧写  ── 按【被行为确证】成熟：L2 假设 → 行为确证 → L3
                    ↓ 三者汇聚
                 侧写层
```

**注意这个不对称**：曲库导入即全量（第 1 天和第 100 天信息量一样），所以必须显式给**两个采样点**；而行为与对话没有这个需求 —— 它们的成熟靠**累积**，由 §3 的分级晋升规则表达。

### 4.1 曲库建模（两阶段）

#### 4.1.1 两个采样点各产出什么

| | **阶段一 · 形态建模** | **阶段二 · 内容建模** |
|---|---|---|
| 触发 | **扫描完成** | **标签覆盖率跨过目标线** |
| 输入 | `Music(id,title,artist,album,duration,path)` | 阶段一全部 + `MusicLabel`（全量）+ `MusicExtra(language,date)` |
| 回答 | 你有**多少**、**怎么组织**、集中在谁身上 | 你的世界由**什么类型**构成 |
| 产出 | 规模 / 歌手集中度（前 1·3·5 占比）/ 专辑完整度 / **路径分类结构** / 时长倾向 | 流派分布 + 宽度（熵）/ 情绪分布 / 年代分布 / 语言构成 / **标签覆盖率（= 认识进度）** |
| 来源 | `LIBRARY_SHAPE` 0.4 | `LIBRARY_CONTENT` 0.55 |

#### 4.1.2 阶段二是「纠正」不是「补全」

```
形态建模：前 5 个歌手占 40% 的曲目  →  判「口味集中」
富化完成后：这 40% 横跨 6 个流派、4 个年代  →  改判「人集中，风格分散」
```

**这两种说法在形态阶段根本无法区分** —— 手里只有歌手名和专辑名，看不出"集中"是因为这人只听一种风格，还是听的风格极广但都出自同几个大牌。只有分类分布能分辨。

所以内容建模产出时**按槽位覆盖**形态建模的同名槽位（不是叠加），旧结论进审计不消失。

#### 4.1.3 它是「先验」，不是「证据」

| | 曲库建模 | 行为证据 |
|---|---|---|
| 回答 | 用户**拥有**什么 | 用户**选择**听什么 |
| 语义 | 涉猎**广度** | 实际**取向**（深度） |
| confidence | 0.4 / 0.55 | **0.6** |

**为什么整体低于行为**：曲库 ≠ 偏好。搬家式批量导入 5000 首不代表当下爱听。

> **冲突时行为赢** —— 曲库说「他拥有 40 张爵士专辑」，行为说「三个月一首爵士没听」，取向以行为为准。**且不做加权平均**（加权会得出"半信半疑"的结论，不如显式让位）。

**但两者的张力本身就是高价值信息**：「库很宽，但反复听的只有那么几首」既指导推荐（推库里从没听过的），又指导消费面叙事。这条张力**只能由两者共同产生**。

**落层：曲库侧写直接落 L3，且不随时间衰减**（2026-09-15 实现时定）。

理由：§3.1 的晋升规则是为**行为**设计的 —— "跨几个会话重复出现"回答的是"这是场景还是偏好"。但曲库不是行为：**导入即全量，第 1 天和第 100 天信息量一样**。它的成熟机制是**认知深度**（形态 → 内容），不是跨会话计数。所以：

- 曲库侧写 `maturity = LIBRARY` → **直接 L3**，跳过 L1 → L2 → L3 的晋升
- **不随时间衰减** —— 曲库没变，不等于这份认识过期了（行为侧写才会因长期无证据降权）
- 形态 → 内容的"纠正"不走分层，走**同槽位选优**（内容建模 0.55 > 形态 0.4，见 `PortraitComposer`）

#### 4.1.4 触发条件（工程约束）

| 阶段 | 触发 | 说明 |
|------|------|------|
| 形态建模 | **扫描完成事件** | 增量扫描时只更新变化部分 |
| 内容建模 | **覆盖率首次跨过目标线** | ⚠️ **不是 100%** —— 总有歌富化失败，100% 可能永远达不到。判据 = `getEnrichHealth().coverageRate ≥ 目标线`，目标线默认 **0.9** |
| 内容建模重做 | 覆盖率**显著回落**时 | 新歌入库会拉低覆盖率 → 重做。靠 `coverage_at_modeling` 判断（回落阈值待定，§13 PF14） |

**目标线的真实来源（2026-09-15 核正）**：**不存在**名为 `enrichTargetCoverage` 的常量。真实参数是 `EnrichTask.targetCoverage`（默认 `0.9f`），挂在**每一次富化任务**上（`EnrichSubAgent.kt:59` 构造参数、`MasterAgent.startEnrich()`），**不是全局可读配置**。

→ 本模块需要一个自己的可读来源：归入 `UserProfileConfig`（DataStore，默认 0.9，与 `EnrichSubAgent` 的构造默认值对齐）。**不去持有 `EnrichTask` 实例** —— 画像模块不该依赖某次富化任务。

**为什么不放进每日聚合**：用户导入 3000 首后若等到次日凌晨才建模，**整整一天 agent 面对的是空画像**。两个阶段都必须事件驱动、即时触发。

#### 4.1.5 `path` 是被低估的宝藏

用户把音乐放进什么文件夹结构，就是他自己建立的分类 —— `/Music/爵士/`、`/Music/深夜/`、`/Music/2024收藏/`。**完全本地、零成本、不需要任何 LLM**，且比歌单更普遍（很多人不建歌单，但所有人的文件都有路径）。这是**阶段一**最早有货的信号之一。

#### 4.1.6 明确拿不到的（受表结构限制）

- ❌ **流派构成** —— `Music` 表**没有 genre 字段**（只有 `title / artist / album / duration / path / albumArtUri`）
- ❌ **年代分布** —— 同样无 year 字段
- ❌ **语言构成** —— `MusicExtra.language` 是富化产物
- → 在**阶段二之前**，口味侧写的 `genreBreadth` 用「艺术家集中度」近似，渲染时**如实说明**（「我还在认识你的曲库」），不假装知道

> 💡 **一个例外**：用户**手工编辑过 ID3** 的歌，其 genre/year 是 `T1_USER` 级，可直接采信并优先于系统标签。

### 4.2 行为建模（定时读播放记录）

**原则（评审决定）：不细致到单个操作，用播放记录定时更新。**

`PlaybackHistory(playedAt, playDuration, isCompleted, source)` 四个字段足够算出行为侧写需要的全部信号 —— **不需要动播放器、不需要新埋点**：

| 侧写槽位 | 从哪来 |
|---------|-------|
| 主时段 / 次时段 / 时段稳定性 | `playedAt` 的小时分布 |
| 跳过点位置 | `playDuration ÷ 曲目时长` 的分布 —— **「前奏就跳」与「听一半才跳」是两种完全不同的信号** |
| 完播倾向 | `isCompleted` 比例 |
| 重复度 | 同一 `musicId` 的短周期重复 |
| ~~来源构成~~ | ❌ **取消** —— `source` 不是这个语义，见下 |

**⚠️ `source` 的真实语义（2026-09-15 核正）**

契约 v3 把它写成「推荐来的 / 自己点的 / 电台来的」，**这是错的**。实际写入的是**播放切换原因**：

| 端 | 写入值 | 位置 |
|----|--------|------|
| Android | `"Resume"` / `"Order"` / `"Shuffle"` / `"Next"` / `"Previous"` / `"Manual"` / `"HeartMode"` / `"Release"` | `MusicController.kt:416–791` |
| Desktop | `"direct"` | `DesktopMusicController.kt:274` |

两端取值**不一致**，且都是「怎么切过来的」，不是「从哪来的」。

→ **「来源构成」槽位移出本模块**；`exploration_portrait` 的同名槽位一并取消（它本就依赖跨曲目序列，属 §12 的后置项）。若将来要这个信号，正确做法是给 `source` 定一套真实枚举（手动 / 推荐 / 电台 / 队列），那是播放器侧的事。

> 📌 **顺带查出的既有缺陷**（不在本模块范围，建议单独立项）：`PlayList.kt:82` 的 `countPlaybackForPlaylist` 按 `PlaybackHistory.source == 歌单名` 统计，被 `MusicRepositoryBase.kt:952/982` 真实调用（歌单的「累计播放次数」展示）。但**全仓没有任何地方把歌单名写进 `source`** → 这个数字**恒为 0**。

**实现落点（2026-09-15）**：`BehaviorModeler`（纯函数）+ `PlaybackHistoryDao.getPlayRowsSince()`（一条 JOIN 查询带出**曲目时长**，否则"听了 30 秒"在 3 分钟歌和 8 分钟歌里含义完全不同）+ `MusicRepository.getBehaviorSnapshot(windowDays = 90)`。三条实现纪律：

- **数据太少就不说**：`totalPlays < 20` 或 `activeDays < 3` 直接返回空 —— 三次播放推不出习惯，只能推出一晚的心情
- **跳过点只在样本够时说**：跳过次数 < 5 时不下"前奏就跳"的结论（噪声）
- **"定时"落地为「低频闸门 + 事件触发」**：本项目没有常驻调度器，所以每次调用先看证据表里 `T0_BEHAVIOR` 的最新 `updated_at`，不足 20 小时就跳过。**不为它新建状态表** —— 证据行本身就是"上次什么时候算过"的记录，效果等于"每天最多一次"

**取数层要新写**：F9-T1 曾实现过一版「日期窗 + 区间聚合」，**该实现已整笔回退、不留档**，故本模块从头写。需要覆盖的聚合项：**时段分布、完播率、活跃天数、跳过点分布、重复度** —— 一次写全，不再分批。（原列第六项「来源构成」已随本节核正取消。）

### 4.3 状态快照（定时 diff）

收藏 / 评分 / 歌单 / ID3 编辑 / 隐藏文件夹**不产生事件**，它们是状态 —— 价值在**变化**，所以要 diff 而非订阅事件。

| 快照 | 落点（字段已核正） | 强度 |
|------|-------------------|------|
| 收藏 / 明确不喜欢 / 评分 | `UserInfo.liked` / `disLiked` / `userRating` | `T1_USER` 0.9 |
| 手工歌单（名称 + 置顶 + 曲序） | `Playlist.name` / `Playlist.isPinned` ＋ **`PlaylistItem.itemOrder`** | `T1_USER` —— **歌单名就是用户自己的分类语言**（「深夜开车」「失恋循环」暴露他按场景还是按情绪组织音乐） |
| 标签修正 | `MusicLabel.source = USER` | `T1_USER` —— 暴露分类偏好 **+ 模型的系统性错法**（可反查调富化 prompt） |
| ID3 手工编辑 | `MusicTagEditor`（三端 actual 均在） | `T1_USER` —— 用户手写的 genre/year 可补 §4.1.6 的缺口 |
| 隐藏文件夹（负向） | **`Music.isDeleted`**（软删除，按 `Music.path` 的目录聚合） | 负向 `T1_USER` —— 「这类他不想要」比"喜欢什么"更能收紧推荐 |

**两处核正（2026-09-15）**：

1. **`itemOrder` 不在 `Playlist` 上** —— 它在 `PlaylistItem`。`Playlist` 的字段是 `name / coverUri / playCount / createdAt / updatedAt / lastPlayedAt / description / songCount / totalDurationMs / isPinned`。
2. **`hideFolder` 不是 domain / repository API** —— 它是 UI 层的 `LibraryViewModel.hideFolder(...)`（`shared-ui/.../library/viewmodel/LibraryViewModel.kt`），底层做的是**把整个目录下的歌软删除**（`getDeletedMusicIdsGroupedByFolder()` 按 `path` 聚合）。→ 本模块读的是 **`Music.isDeleted`**，与 UI 入口解耦。

**⚠️ 由此追加一条硬纪律：一切建模与聚合必须排除软删除的歌。** `Music.isDeleted = 1` 的行不算曲库内容 —— 否则"用户隐藏了一个文件夹"会被误读成"曲库变小了"或"口味变了"。代码既有口径：`musicDao.getAllActiveIds()`（`SELECT id FROM music WHERE isDeleted = 0`）。

**与行为建模共用同一个定时任务**（反正已经要跑，多读四张表不增加机制）。

**这些信号落到哪些槽位（2026-09-15 补 —— 本节原先只列了来源、没定槽位）**：全部挂在 `library_portrait` 下，因为它们的共同语义是「**关于他曲库的显式事实**」，与「他选择听什么」是两个层面。

| 来源 | 槽位 | 取值 |
|------|------|------|
| 收藏 | `likedShare` | `NONE` / `SOME` / `MANY`（占曲库 ≥10% 算 MANY） |
| 明确不喜欢 | `dislikedShare` | 同上 |
| 隐藏文件夹 | `hiddenFolders` | 同上 |
| 用户改过的标签 | `userTagFix` | 同上 |
| 手工歌单名 | `playlistNames` | 脱敏后的歌单名 CSV（≤5 条、≤12 字、含分隔符的一律丢弃） |

> **为什么不需要"diff 表"**：原文说状态快照"靠 diff 而非订阅"。落到库里，**唯一索引 + 计数累加本身就是变化记录** —— 重算一遍，值变了就多一行、没变就只是 `evidence_count + 1`。所以既不需要额外快照表，也不需要事件订阅。

> **配对洞察（如「收藏了 100 首但只播过 12 首」）不进侧写**：侧写是单个类型内的槽位集合，跨"收藏"与"播放"的组合属于**渲染层 / 消费面**的事。硬塞进侧写会让它变成两源求交的派生，破坏"侧写只有一条派生路径"的简单性。

### 4.4 对话侧写（门槛已放开）

**决定：从对话中推断音乐偏好是允许的**（不再只认"用户显式陈述"）。但放开的**边界**必须写清：

| 约束 | 内容 |
|------|------|
| **落点** | 推断结果**必须写进闭集槽位**，不能自由发明谓词 |
| **来源** | `T2_DIALOGUE`，confidence 起点 **0.35** |
| **默认层** | 落 **L2 情境态**，**不自动升 L3** |
| **升 L3** | **被播放行为确证**（同向证据累积达标）才升 |
| **证伪** | 行为背离即降权 / 失效 |

**"不自动升 L3"是最要紧的一条**，因为它复用已有的 L2→L3 晋升规则，并给了它一个新用途：

> **对话给假设，行为给确证。**

用户说「我喜欢爵士」 → 进 L2 的假设；接下来三个月真的在听爵士 → 升 L3，成为"人性"的一部分；三个月一首没听 → 降权退出。**"他说的"和"他做的"自动分出可信度层级，不需要额外判断逻辑。**

**底线：放开的是「从对话推断音乐偏好」，不是「从对话推断人」。**

- ✅ 他说"想找点适合加班的" → 推「工作时段偏好安静」
- ❌ 他自己没说，模型推断"他最近压力大" → 然后给他推治愈系

**推断的对象必须是「音乐选择」，不能是「他的处境」。** 与 §5.4 拒绝类型学同一条理由 —— 不可确证、不该由播放器持有。差别在于：音乐偏好能被后续行为验证，处境不能。

### 4.5 用户操作

设置页的**修正**与**否决**都写成 `T1_USER` 证据（否决 = 写 `pref_denied` 证据），下一轮重算生效。

**侧写不存在"手工改"的路径** —— 用户改的是**证据**。这样"删除"与"修正"走同一条路径，无特例代码。

- `profile_forget` 除了写否决证据，还要**删掉侧写行**：否则设置页会显示"伙伴记得你不喜欢被这样理解"，那行本身就是被否决的对象
- `profile_read` **复用 `renderForContext()`**，不另开一条渲染路径 —— 读出去的必须是侧写渲染而非证据原文（§7）
- 审计的 `reason` **只放条数与来源**，绝不放画像内容或标签名（§9.2 工程卫生；有测试断言）

## 5. 认知清单

**唯一准入标准：这条认知能不能改变 agent 的某个具体动作？** 不能改变任何动作的不建。

### 5.1 A 类 · 可硬确证

| 侧写 | 槽位 | 证据来源 | **指导什么动作** |
|------|------|---------|----------------|
| `library_portrait` 曲库侧写 | 规模 / 艺术家集中度 / 专辑完整度 / 路径分类结构 / 时长倾向 + **阶段二追加**流派-情绪-年代-语言分布 | `Music` 表（扫描即得）+ 富化后分类分布 | **冷启动的地基**；库宽而实际窄时挖「从没听过的」；DISCOVER 卡候选池；人格卡的启动态 |
| `time_portrait` 时间侧写 | 主时段 / 次时段 / 时段稳定性 | 播放记录小时分布 | 时段适配（深夜不推高能量）；问候语选型；电台开播种子 |
| `taste_portrait` 口味侧写 | 主导流派 / 风格宽度 / 语言构成 / 年代倾向 / 常听歌手前 3 / **不喜欢风格（T0b 新增 `dislikedStyles`，value 为自由短语如"快歌"，对话抽取写入）** | `MusicLabel` × 播放权重；**标签未就绪时宽度退化为艺术家集中度** | 推荐与电台种子；生成歌单的主导风格；DISCOVER 卡的标签选取 |
| `habits_portrait` 听法侧写 | 完播倾向 / 跳过点位置 / 重复度 | `playDuration ÷ 时长` 分布、`isCompleted` | **歌单前几首的选曲策略**（爱跳的人要把钩子提前）；不推长曲给低完播率用户；电台 refill 阈值 |
| `exploration_portrait` 探索侧写 | 新歌比例 / 老歌回归率 | **首次播放时间戳**（`MIN(playedAt) GROUP BY musicId`） | 推荐里「安全 vs 冒险」的比例；DISCOVER 卡是否出现；富化强度。⚠️ 原「来源构成」槽位已随 §4.2 取消 —— `source` 不是那个语义 |

### 5.2 B 类 · 可弱确证（**只能降级表达**）

| 侧写 | 槽位 | 为什么弱 | 指导什么动作 |
|------|------|---------|-------------|
| `order_portrait` 秩序偏好 | 确定性（重复同一批 vs 追逐新歌）/ 结构容忍度 | 需会话内顺序与专辑内序交叉，单源不足 | 播放模式默认值建议；推荐排序是稳定输出还是每轮不同 |
| `intensity_portrait` 情绪强度 | 能量倾向 / 情绪一致性 | `MOOD` 标签本身是 T2，需与时段交叉校验 | 时段—能量匹配；夜间歌单能量上限 |
| `attention_portrait` 注意力模式 | 单次收听时长 / 碎片化程度 | 会话边界需推断 | 推「整张专辑 / 长歌单」还是「短歌单」；睡眠定时默认时长 |

**降级表达的硬约束**：只能以「**你在音乐里表现出的…**」表述。

- ✅「你在音乐里倾向于反复听熟悉的那批」 ／ ❌「你是个有秩序偏好的人」
- ✅「你近期在音乐里偏向低能量」 ／ ❌「你最近情绪低落」

**实现状态（2026-09-16 T0b 落地时如实登记，不假装知道）**：

| 槽位 | 状态 | 说明 |
|------|------|------|
| `attention_portrait.sessionLength` / `fragmentation` | ✅ | 会话 = 播放间隔 > 30 分钟的推断边界；**会话数 ≥ 3 才说**；净听时长按 `playDuration` 累加（不含切歌间隙） |
| `order_portrait.determinism` | ✅ | 重复度 × 新歌比例**交叉**（两个单项都到不了阈值才敢下结论），复用 `BehaviorModeler` 同一套分档阈值 |
| `intensity_portrait.moodConsistency` | ✅ | 曲库 MOOD 分布的近似（`moodMix`），来源 `LIBRARY_CONTENT` + 覆盖率折扣；**覆盖率 < 0.3 或无 MOOD 标签不写** |
| `order_portrait.structureTolerance` | ⏸ | 需会话内顺序 × 专辑内序，两源都未采集 —— 硬造等于编 |
| `intensity_portrait.energyTendency` | ⏸ | MOOD 标签没有能量维度；等标签体系给出能量值再接 |

B 类行为侧写由 `BPortraitModeler`（与主行为建模同一份快照顺手算）；其上下文渲染由 `UserProfileRenderer` 按 `weakEvidence` 强制加降级前缀，不依赖调用方自觉。

### 5.3 与消费面的展示分层

**A 类可进入人格卡正面；B 类默认收在设置页二级。** 理由不是隐私，是**呈现层级** —— 卡片正面空间有限，且弱确证的倾向描述不该与可硬确证的结论并列呈现。

### 5.4 C 类 · 明确不做

> **范围**：拒绝的是把类型学当作**agent 的内部知识骨架**（驱动决策）。作为**给用户看的消费包装**是另一回事，见 §6。

| 不做 | 理由 |
|------|------|
| MBTI / 九型 | ① **不可确证**：听 300 小时古典推不出 INTJ ② 重测信度低、维度二分化人为，落到决策面上就是**巴纳姆效应** ③ **信任是一次性透支**：错一个标签比不说更糟 |
| 大五人格 | 量表效度更好，但**同样无法从播放行为确证**；要做必须有问卷，那是另一个产品形态 |
| 情绪状态 | 不可确证，误判代价高（深夜低能量 ≠ 情绪低落） |
| 人口属性 / 生活事件 | 不可从本地行为得出，且播放器不该持有 |

**替代方案**：需要"整体印象"时用**侧写的组合**，不用类型学。侧写天然是压缩表示，且每个分句都能反查到证据：

> 「你是个深夜听歌的人，偏向民谣和独立，喜欢把熟悉的那批翻来覆去听，很少跳到一半 —— 更像在环境里待着，而不是在挑选。」

对比「你是 INFP」：信息量更具体、每个分句可追问、错了只需重算而非推翻一个人格标签。

## 6. 消费面（音乐人格卡）

### 6.1 两个面，单向隔离

| | 认知面（给 agent） | 消费面（给用户） |
|---|---|---|
| 取值 | 侧写**槽位原值** | 侧写组合 → **人格化命名** + 人话 + 「凭什么」 |
| 去向 | 上下文 / 工具 → 驱动推荐、电台种子、歌单选曲 | 人格卡、分享、动态对照 |

**共用同一份可确证数据，只是包装不同。**

> **边界：消费面不得回流决策面。** 理由不是道德，是**产品退化** —— 如果「夜航者」这个称号让 agent 只推深夜歌，用户的白天就会被系统性地服务得更差。**称号是他消费的，不该变成他被服务的枷锁。** 这条成本极低：两面共用同一份数据，消费面只多一层命名与文案。

### 6.2 换轴，不是换皮

**分类的维度直接从可确证的侧写槽位映射出来：**

| 轴 | 两极 | 来源槽位 |
|----|------|---------|
| 时段倾向 | 日行 ↔ 夜行 | `time_portrait.primaryPart` |
| 口味宽度 | 专精 ↔ 广谱 | `taste_portrait.genreBreadth` |
| 听法 | 沉浸 ↔ 筛选 | `habits_portrait.completionRate` / `skipPoint` |

**3 轴 → 8 型**，命名表是预设常量（见 PF10）。

**命名表（2026-09-16 T0b 定稿，落在 `PersonalityCardComposer`）** —— 全部是"听音乐的方式"，不是"你是什么人"：

| 时段 | 宽度 | 听法 | 命名 |
|------|------|------|------|
| 夜行 | 专精 | 沉浸 | 夜航者 |
| 夜行 | 专精 | 筛选 | 夜巡者 |
| 夜行 | 广谱 | 沉浸 | 月下漫游者 |
| 夜行 | 广谱 | 筛选 | 午夜调频师 |
| 日行 | 专精 | 沉浸 | 老唱片 |
| 日行 | 专精 | 筛选 | 点唱机 |
| 日行 | 广谱 | 沉浸 | 拾光者 |
| 日行 | 广谱 | 筛选 | 冲浪者 |

**实现补充的两条规则**：① **缺轴不命名** —— 三轴不全时卡片只出有依据的几句人话，不硬凑类型（不假装知道）；② **PF16 落地** —— 宽度轴优先读 `genreBreadth`，标签未就绪时退化用歌手集中度近似并**标「初步」**，近似也能参与命名但「凭什么」里必须写明是近似。另：`MEDIUM` 档的槽位（如完播率中等）不定轴 —— 轴是二分的，硬把中间值塞进某一极就是编。

**为什么不借 MBTI**（查证于 2026-09-15，官方条款）：

1. `MBTI` / `Myers-Briggs` **均为注册商标**，官方明确「使用 MBTI 商标只能指向真正的 MBTI 产品与服务」，且「获得 MBTI 类型结果的唯一方式是使用官方量表」
2. 官方销售条款禁止「**利用收集到的数据创造用于商业销售的产品**」—— 即使买了量表，做成 App 内功能也在禁止之列
3. MBTI 属**受限量表**，官方要求传输结果时**必须由人提供互动式同期咨询** —— 与 App 内自动化功能天然冲突

**但更要紧的是内容层面（与版权无关）**：MBTI 的四组二分是心理学构造，**从播放行为根本推不出来**。换个名字、换个字母，"4 组二分"这个结构在我们数据上依然没有证据支撑 —— 等于用合规的壳装编造的内容。

**自有方案的好处不止"没版权"**：每个轴都有行为证据可反查；能**随 L2 情境态漂移**（类型学测一次就定死）；轴名说的是「**你怎么听**」而不是「你是谁」—— 对音乐播放器这才贴题。

### 6.3 允许 / 禁止清单

**允许**：侧写组合的人格命名（可系列化）；人格卡（命名 + 3~4 句人话 + 可展开的「凭什么」）；**动态对照**（L2 与 L3 的差异：「在夜航者的底子上，这阵子偏向了民谣」）；**时间对照**（三个月前的你 vs 现在的你）；明示为**音乐范围**的娱乐化表达。

**禁止**：使用 `MBTI` / `Myers-Briggs` / `九型人格` / `大五` / `16Personalities` 等专名或**混淆性近似**（含英文缩写、`N 型人格` 这类数字+型命名、把四组二分换名后沿用）；任何"科学人格测评"宣称；消费面产物回流决策输入。

## 7. 读取面

| 消费点 | 内容 | 配额 |
|--------|------|------|
| **Master 首轮上下文** | `ContextAssembler` 新增「对你的认识」块，紧随 persona | 只取 L3 全部 + L2 中 `confidence` 最高的若干；**L1 不进**；N=8、阈值 0.5、硬字数上限；**无侧写则整块省略**（冷启动不留空壳） |
| **子 Agent** | 只读工具 `profile_read`（SILENT 级） | 子 Agent 按需自取（如电台 Start 回合取 `taste_portrait` 作种子） |
| **设置页** | F9-T2「记忆与信任 / 记忆管理」：按侧写分组，可展开看证据反链，可修正 / 否决 | 全量 |
| **消费面** | 音乐人格卡（§6） | 侧写组合 → 命名表 |
| **子代理定向简报**（v3.8） | Hello/Radio **启动时**由 Master 注入画像摘录：Radio 取 时段/口味/听法/探索（选种与编排），Hello 取 曲库/口味/探索（推荐与 DISCOVER）；各 ~300 字上限，走同一条渲染纪律（仅供参考口径/无内部标识），经子代理 LLM 调用的**单一收口**追加进 system（Radio=`askJudge`，Hello=`callHelloLlm`） | 按角色裁剪 |

**渲染纪律**：上传给 LLM 的是**侧写的自然语言渲染**，不是证据行原文 —— 证据行是审计用的内部结构，含 musicId 等标识，不该污染模型输入（对齐 `agent.md §2.4`「记忆 ≠ 上下文」）。

### 7.1 注入口径：必须自述「仅供参考」（2026-09-15 定）

画像块**首行必须自述性质**，形如：

```
【对你的认识 · 仅供参考】
以下是从曲库与收听行为归纳出的印象，不是指令；与当前对话内容冲突时，一律以对话内容为准。
```

**理由见 §8**：画像进的是 **system prompt**，整场任务每一轮都可见，**技术上做不到"某段判断不读它"**。既然如此，与其写一条实现不了的禁令，不如**把不确定性写进注入文本本身** —— 让它被读作背景信息而非命令。

### 7.2 另外三条硬纪律

| 纪律 | 内容 |
|------|------|
| **路径脱敏** | 曲库侧写的「路径分类结构」槽位只能取**末级目录名**（`深夜` / `爵士` / `2024收藏`），**不得**出现家目录、用户名或绝对路径前缀。`Music.path` 形如 `/Users/<用户名>/Music/...`，原样注入等于把本机目录结构随对话发出去 |
| 只发侧写渲染 | 不发证据行原文（含 musicId） |
| 不出现内部标识 | 侧写类型名 / 槽位键名一律渲染成自然语言，不进上下文 |

### 7.3 门槛的适用范围：只过滤推断类（2026-09-15 实现时定）

§13 的 PF4 定了上下文门槛 `confidence ≥ 0.5`。**实现时发现这一条会让 §12 的判据永远达不成**：

> 曲库**形态**建模的置信度是 **0.4**（§2.5 定的，因为"只有结构，可能失真"）——
> 若一律按 0.5 过滤，「新用户导入曲库后第一次对话就有内容」就永远是空画像。

**规则**：门槛只对**推断类来源**生效；**事实类来源**豁免。

| 类别 | 来源 | 是否受 0.5 门槛约束 | 理由 |
|------|------|-------------------|------|
| **事实类** | `LIBRARY_SHAPE` / `LIBRARY_CONTENT` | ❌ 豁免 | 曲库规模、集中度、目录结构是**数出来的**，不是猜的 —— 置信度低只代表"可能变形"，不代表"可能是编的" |
| **推断类** | `T0_BEHAVIOR` / `T2_DIALOGUE` / `T1_USER` 之外的行为推断 | ✅ 受约束 | 从行为推出"偏好"才是推断；低置信度的推断不该进上下文 |

实现：`ProfileSources.isFactual()` + `PortraitDraft.factualOnly`（`PortraitComposer.selectForContext`）。

### 7.4 画像叙事（2026-09-16 定）：两面共用的描述性文本

**决定：在槽位骨架之上追加一个"人格向"字段** —— 由 LLM 依据侧写渲染生成一段描述性文本，**两面共用同一份**（用户拍板；槽位行照旧注入，叙事是**追加**不是顶替，且随侧写重算**重生成**，不存在"过时散文误导 agent"的问题）。

| 项 | 定稿 |
|----|------|
| 落点 | 新表 `user_profile_narrative`（Room v6→v7，单行 REPLACE）；`facts_hash` 存生成时的侧写指纹，不一致即过期 |
| 生成输入 | **只有槽位事实句**（`renderBody`，无免责句、无称号、无旧叙事）—— 铁律：**叙事只能是事实的复述，一个新事实都不许有** |
| 写入闸门 | `ProfileNarrative.validate`：长度 20~200 字、单段、禁人格命名（8 型名独占消费面，防称号回流 §6.1）、禁类型学专名（§6.3）；越界**拒收并保留旧文本**（宁旧勿假） |
| 生成时机 | MasterAgent 每次对话启动检查指纹，过期即异步重生成（不阻塞本轮，本轮用旧叙事）；失败静默保留旧文本；从未生成过 → 消费面退回模板句（P18 不破） |
| 认知面注入 | 画像块内以「整体印象：…」一行插入免责句之后，同处「仅供参考」口径、共享 500 字上限（v3.5 由 400 上调） |
| 审计 | 只记 `regenerated`，不记文本内容（§9.2） |

**为什么两面共用是安全的**：共用的风险从来不是"多一段文字"，而是"文字里出现槽位没支撑的断言"。生成输入只含事实渲染 + 禁词闸门把这两个口都堵死之后，叙事进 system prompt 只是同一批事实换了个说法；真正有回流失效的**称号**（夜航者等 8 名）被排除在生成输入与写入闸门之外，仍独占消费面。

## 8. 与 C2 的关系

电台 F6 拍板 **C2：只做会话内、不写长期偏好**。本模块要"从对话中持续更新并持久化"，表面冲突。

**解决方式：明确 C2 的适用范围，而不是推翻它。C2 经两次修订后定稿如下。**

> **C2 修订（2026-09-15 定稿）**
>
> **C2 = 画像可以进入会话上下文，但不作为指令 —— 电台对"这一档怎么编排"的判断，由会话内上下文与用户当下反馈决定。**
>
> - 电台**开播时的种子选择**可以读画像 ✅
> - 电台**会话内**也能看到画像 ✅ —— **放开**（原 v3 的「这条守死」作废）
> - 但画像块以**「仅供参考」**口径注入（§7.1），不被当作指令执行
> - 画像侧：对话推断已放开，但受 §4.4 的三条约束

**为什么把「会话内不读」改成「读了但不当指令」**：v3 那条禁令**在实现上做不到** —— 画像块进的是 `ContextAssembler.assembleFirstTurnBlock()` → `buildChatSystemPrompt()`（`MasterAgent.kt:1408`），而它产出的是 **system prompt**，**整场任务的每一轮都是同一份**，电台的逐步判断自然也看得见。

一条做不到的纪律比没有更糟：它会让人以为存在一道并不存在的隔离，后人照着它写代码时才发现无从实现。改在**注入文本**里声明"仅供参考"，是把这件事交给模型的语言理解，而不是交给一句不存在的架构约束。

## 9. 隐私口径

> **本节不是设计约束。** 决定：**先抛开隐私问题** —— 本模块不承担隐私设计。

### 9.1 唯一动作

**Agent 端点是用户自行配置的（BYOK）。** 用户在填 URL 与 Key 时就知道数据去哪，所以：

> **端点配置页加一句提醒即可**：「伙伴对你的认识会随对话发送到上面这个端点。」

不做境内外区分、不设独立开关、不做额外弹窗。**本模块的隐私设计到此为止。**

### 9.2 三条保留的纪律（理由都不是隐私）

| 纪律 | 真正的理由 |
|------|-----------|
| B 类弱确证侧写不进人格卡正面 | **呈现层级**（§5.3） |
| 画像内容不进日志 / 埋点 / 崩溃上报 | **工程卫生** —— 顺手一句 `Logger.d { "portrait=$portraits" }` 就把画像刷进 logcat 或崩溃报告，排查时反成噪声源 |
| 上传 LLM 的是侧写渲染，不是证据行原文 | **上下文纪律**（§7） |

### 9.3 备查（不作为设计约束）

以下为 2026-09-15 查证结果，**留档以免将来重查**：

- 音乐画像**不属《个人信息保护法》第 28 条**列举的敏感个人信息（生物识别 / 宗教信仰 / 特定身份 / 医疗健康 / 金融账户 / 行踪轨迹 / 不满十四周岁未成年人）
- 第 24 条：自动化决策应「保证决策的透明度和结果公平、公正」，且信息推送须「提供不针对其个人特征的选项，或者向个人提供便捷的拒绝方式」
- 第 39 条：向境外提供个人信息须告知 + 单独同意
- 既有设计中**证据反链**刚好对上第 24 条的「透明度」，**可修正 / 可否决**对上第 46 / 47 条与第 15 条 —— 但这层对应关系是真的，而**我们做它们的理由本来是产品（"凭什么"要能追问），不是合规**

**T0b 实现时的三条决定（回写 2026-09-16）**：

1. **人格卡命名只认三轴全定** —— 8 型每格由三轴定义，缺轴硬凑就是编；`MEDIUM` 档不定轴（轴是二分的）。
2. **对话抽取"先闸后抽"** —— 绝大多数消息一个 LLM 调用都不花；抽取 prompt 的菜单只有三个音乐选择槽位，「不推断人」由闭集结构保证，解析器再挡一道（拒收不计入写入数）。
3. **B 类的"弱"由渲染层强制** —— `UserProfileRenderer` 按 `weakEvidence` 加「你在音乐里表现出的…」前缀，不依赖建模器自觉；`structureTolerance` / `energyTendency` 无写入方是**如实登记**，不是遗漏。

**测试覆盖（v3.8 后）**：全绿 821 例（T0a 时 779 + T0b 人格卡 11 / B 类 10 / 对话抽取 8 / 集成 3 + 叙事 9（含迁移）+ 定向简报 1）；T0b 之后追加了画像叙事（v3.5）· 归属收编 Master 定名 UserMemory（v3.6/v3.7）· Hello/Radio 定向简报（v3.8），详见 §14
